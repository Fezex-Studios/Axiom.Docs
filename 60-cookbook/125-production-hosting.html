Production Hosting: HTTPS, DDoS and AWS#

This page answers three questions: - Which way of doing HTTPS is right for production? - How do I protect the servers from DDoS attacks? - How do I host on AWS?

Local development needs none of it (HTTPS for Auth, Mode 1).

The industry standard: a proxy in front of Auth#

In production, the app does not hold the certificate. A reverse proxy or load balancer sits in front of Auth, does the HTTPS, and passes requests on to Auth over a private connection. Microsoft's ASP.NET Core guidance recommends the same for Kestrel servers that face the internet.

Player ──https──► proxy / load balancer ──http (private)──► Auth (Kestrel)

Kestrel is the web server built into every ASP.NET Core app, Auth included. It always runs. With a proxy in front, it simply doesn't need a certificate.

Three ways to do HTTPS#

Reverse proxy (Caddy or nginx) Cloud load balancer (AWS ALB, Azure Application Gateway) Certificate on Kestrel
Where your own server or a VPS AWS, Azure or Google Cloud anywhere
Who runs it you the cloud provider you
Certificate Let's Encrypt, automatic (Caddy) the provider's, free and automatic Let's Encrypt via certbot or win-acme
Renewal automatic automatic the tool renews; Auth must restart to load the new certificate
Several Auth servers yes (reverse_proxy auth1:3000 auth2:3000) yes, and it can add servers under load every server needs its own copy
Updating Auth with no downtime yes: traffic goes to the instances still running yes no: a restart drops connections
Auth reachable from the internet no no yes, directly
Cost free about $20+/month per load balancer, plus traffic free
Use it for self-hosting: the default for Axiom hosting on a cloud provider one small server where you can't run a proxy

All three work with Axiom without code changes:

Set-up Auth settings
Proxy on the same machine TrustForwardedFor: true
Proxy or load balancer on other machines TrustForwardedFor: true plus TrustedProxies
Certificate on Kestrel the Https endpoint

You can switch later.

Is Caddy fine for a high-performance production server? Yes. - It's fast enough. Caddy (written in Go) handles thousands of requests per second on modest hardware. Auth's traffic (logins, the world list, character counts, the game-data download) is tiny next to that. - The real limit is the login. Each password check (BCrypt) takes about 250 ms of CPU, plus a MySQL query, and those run out long before Caddy does. - Game traffic never touches it. Movement, combat and chat go straight from the client to the World server over UDP, so Caddy has no effect on in-game performance.

nginx would do the same job at the same speed. If Auth ever struggles, add Auth instances and tune MySQL; a different proxy won't help.

DDoS protection#

A DDoS (distributed denial of service) attack floods your internet connection with junk traffic from thousands of machines.

Caddy, Auth's rate limits and anything else on your machine cannot stop it. The connection fills up before the traffic ever reaches them. Rate limits protect against abuse, such as password guessing; they don't stop floods. Protection has to come from the network in front of your server, which absorbs or filters the flood before it reaches you.

What needs protecting How
Auth (HTTPS) Cloudflare, free plan. Move your domain's DNS to Cloudflare and turn on the orange-cloud proxy for the Auth name. Floods stop at Cloudflare. Caddy keeps running behind it (see Cloudflare in front of Caddy).
World server (UDP 7777) Cloudflare's free plan does not carry UDP game traffic. Use a host whose network filters game traffic: OVH game servers (protection included) or a game-DDoS specialist such as Path.net. Cloudflare Spectrum covers UDP but is costly.
On AWS AWS Shield Standard is free and automatic for every AWS service and covers common network-level attacks. Shield Advanced (about $3,000/month) adds more for large targets.

For an MMO, the World server is the usual target. Knocking it offline kicks every player, while a slow login server is merely annoying. Your DDoS plan is mostly about choosing a host that protects UDP.

Hosting at home is fine for testing, not for launch. Players learn your home IP, and an attack takes down your whole internet connection, not just the game.

Cloudflare in front of Caddy#

Player ──https──► Cloudflare ──https──► Caddy ──http──► Auth
  1. Add your domain to Cloudflare (free plan) and change its nameservers to Cloudflare's. A free DuckDNS name can't do this: you need a real domain, about $10/year.
  2. Create an A record for auth → your server's IP, with Proxied (orange cloud) on.
  3. Under SSL/TLS, choose Full (strict). Caddy keeps its own certificate, so the link from Cloudflare to Caddy is encrypted too.
  4. Pass the player's real IP to Auth. Otherwise Auth sees Cloudflare's address, and every player behind the same Cloudflare server would share one rate limit. Caddy needs two additions:

``` { servers { # Cloudflare's ranges: the current list is at https://www.cloudflare.com/ips/ trusted_proxies static 173.245.48.0/20 103.21.244.0/22 103.22.200.0/22 ... 2400:cb00::/32 ... client_ip_headers CF-Connecting-IP } }

auth.yourgame.com { reverse_proxy 127.0.0.1:3000 { header_up X-Forwarded-For {client_ip} } } ```

  • trusted_proxies and client_ip_headers tell Caddy to read the player's IP from Cloudflare's CF-Connecting-IP header. Caddy only does this for requests that really come from Cloudflare.
  • header_up hands that one address to Auth.

Auth needs no changes beyond TrustForwardedFor: true. 5. The World server's address (UDP) must not go through the orange cloud. Give it its own DNS name with the proxy off (grey cloud), or use its IP directly.

Recommended launch set-up (self-hosted)#

                         ┌───────────── one OVH game server ─────────────┐
Player ──https──► Cloudflare ──► Caddy :443 ──► Auth 127.0.0.1:3000      │
Player ──UDP 7777──────────────► World (OVH game DDoS protection)        │
                         │       Persistence 127.0.0.1, Auction, MySQL   │
                         └────────────────────────────────────────────────┘
Piece Choice Why
Machine an OVH game server (or any host with game UDP protection) protects the World server, the real target
HTTPS for Auth Caddy, on the same machine free, automatic, nothing to maintain
DDoS for Auth Cloudflare free plan absorbs floods at the login server
Auth settings TrustForwardedFor: true, Kestrel on http://127.0.0.1:3000 real player IPs; Auth only reachable through Caddy

Steps: Deploy a Shard for the services, and HTTPS for Auth for Caddy.

Hosting on AWS#

On AWS you don't run Caddy. The Application Load Balancer (ALB) does its job, with a free certificate from AWS Certificate Manager (ACM).

                      ┌──────────────────────── AWS (one VPC) ─────────────────────────┐
Player ──https 443──► │ ALB (ACM certificate) ──http 3000──► EC2: Auth                 │
                      │                                       EC2: World ◄── UDP 7777 ──┼── Player
                      │                                       Persistence, Auction      │
                      │                                       MySQL (EC2 or RDS)        │
                      └─────────────────────────────────────────────────────────────────┘

The ALB only carries web traffic (HTTP and HTTPS). The World server's UDP does not go through it. Players reach the World server directly on its public address.

AWS terms#

Term What it is
EC2 a virtual server you rent; your services run on it
VPC your private network inside AWS
Security group a firewall attached to a server or load balancer
Elastic IP a fixed public IP address for an EC2 server
ALB Application Load Balancer: HTTPS in front of Auth
ACM AWS Certificate Manager: free certificates for the ALB
Target group the list of Auth servers the ALB sends requests to
RDS managed MySQL (optional; MySQL on your EC2 server works too)
Route 53 AWS's DNS (optional; any DNS provider works)

Step 1: The server#

  1. EC2 → Launch instance: Ubuntu, for example a c6i.large or larger (compute-optimised types suit game servers). Pick the region closest to your players.
  2. Elastic IPs → Allocate, then Associate it with the instance. This is the World server's public address and never changes.
  3. Install .NET and MySQL and publish the four services, as in Deploy a Shard. RDS → Create database (MySQL) is the managed alternative to MySQL on the server; point the connection strings at its address.

Step 2: Security groups (the firewall)#

Create two:

axiom-alb (for the load balancer):

Inbound Port From
HTTPS 443 0.0.0.0/0 (everyone)
HTTP 80 0.0.0.0/0; the ALB only redirects it to HTTPS

axiom-server (for the EC2 server):

Inbound Port From
Custom TCP 3000 (Auth) the axiom-alb security group only
Custom UDP 7777 (World) 0.0.0.0/0 (players)
SSH 22 your own IP only

The rule that matters is 3000 from axiom-alb only: nobody can reach Auth without going through the ALB's HTTPS. Persistence, Auction and MySQL get no inbound rules at all, because they only talk over 127.0.0.1 on the same server.

Step 3: The certificate (ACM)#

  1. Certificate Manager → Request → Public certificate, domain auth.yourgame.com.
  2. Choose DNS validation. ACM shows a CNAME record. Add it at your DNS provider (Route 53 can add it for you with one click).
  3. Wait for Issued, usually a few minutes. ACM renews it automatically, for as long as the CNAME stays in place.

ACM certificates are free, but they only work on AWS services such as the ALB.

Step 4: The target group#

  1. EC2 → Target groups → Create: type Instances, protocol HTTP, port 3000, your VPC.
  2. Health check: path /worlds, success code 200. The ALB calls it to know Auth is alive.
  3. Register your EC2 instance. For several Auth servers later, register each one here.

Step 5: The load balancer#

  1. EC2 → Load balancers → Create → Application Load Balancer: internet-facing, at least two availability zones (AWS requires it), security group axiom-alb.
  2. Listener HTTPS:443 → forward to your target group, with the ACM certificate.
  3. Listener HTTP:80 → redirect to HTTPS:443.
  4. When it's active, copy its DNS name (like axiom-alb-123.us-east-1.elb.amazonaws.com).

Step 6: DNS#

Point auth.yourgame.com at the ALB: - Route 53: an A record → Alias → your load balancer. - Another DNS provider: a CNAME to the ALB's DNS name.

Give the World server its own name too: world.yourgame.com → an A record with the Elastic IP.

Step 7: Axiom's settings#

Auth appsettings.Local.json:

{
  "Auth": {
    "InternalSecret": "...",
    "TrustForwardedFor": true,
    "TrustedProxies": [ "10.0.0.0/16" ]
  },
  "Kestrel": { "Endpoints": { "Http": { "Url": "http://0.0.0.0:3000" } } }
}
  • TrustedProxies = your VPC's address range. It's shown in VPC → Your VPCs, as "IPv4 CIDR"; 172.31.0.0/16 is the default VPC.
  • The ALB is on a different machine from Auth, so it isn't trusted automatically the way Caddy on 127.0.0.1 is.
  • With this setting, Auth believes the ALB's X-Forwarded-For (the player's real IP) and X-Forwarded-Proto: https.
  • Without it, Auth refuses every login as plain HTTP, because the ALB's address isn't a trusted proxy.
  • Health checks. The ALB's health check comes from the ALB itself, with no forwarded headers. Auth lets a trusted proxy's own requests through, so the check passes once TrustedProxies is set.
  • 0.0.0.0:3000, not 127.0.0.1. The ALB connects over the network. The security group from Step 2 is what keeps everyone else out.

World appsettings.Local.json:

Setting Value
World:AuthServerUrl http://127.0.0.1:3000 when Auth runs on the same server; otherwise https://auth.yourgame.com
WorldDirectory:PublicHost world.yourgame.com (or the Elastic IP)
WorldDirectory:PublicPort 7777

Client / launcher: -auth-url https://auth.yourgame.com.

Step 8: Test#

  1. Open https://auth.yourgame.com/worlds on your phone, on mobile data. You should get the world list with a padlock.
  2. Auth's start-up log: HTTPS: expected from a reverse proxy (Auth:TrustForwardedFor)….
  3. Log in from the launcher. Auth's log should show your real IP, not a 10.x address.
Problem Cause
ALB returns 502 / 503 The target is unhealthy. Check the target group's health status: Auth isn't running, isn't on 0.0.0.0:3000, or port 3000 isn't open to axiom-alb.
Login: "only accepts secure (HTTPS) connections" TrustedProxies is missing or doesn't contain the VPC range.
World list works but the game can't connect UDP 7777 isn't open in axiom-server, or PublicHost is wrong.
Certificate stuck on "Pending validation" The ACM CNAME record isn't in your DNS yet, or was typed wrong.

DDoS on AWS#

  • Shield Standard is on automatically, free, for the ALB and the Elastic IP. It covers common network floods.
  • For the login side, Cloudflare can also sit in front of the ALB. Point Cloudflare's proxied record at the ALB's DNS name.
  • UDP game traffic on AWS gets only Shield Standard unless you pay for Shield Advanced. For a game that's likely to be targeted, a host with built-in game UDP protection (OVH and similar) is the cheaper route, at the cost of fewer managed services.

Roughly what it costs#

Prices change; check the AWS pricing pages for your region.

Piece Ballpark
ALB about $20+/month plus traffic
ACM certificate, Shield Standard free
EC2 server depends on size: tens to a few hundred dollars a month
Elastic IP small monthly charge
RDS (optional) from about $15–30/month for small sizes
Data out to players per GB; the biggest variable for an MMO

Which to choose#

Situation Choice
Developing nothing (Mode 1)
Friends test from their homes Caddy on your PC (Mode 3)
Public launch, best value an OVH-style game server + Caddy + Cloudflare free
Public launch, managed services, room to scale AWS: ALB + ACM + EC2 (+ RDS)
One small server, no proxy allowed a certificate on Kestrel
