Client & Editor Notes
Feature note, kept next to the code it describes. Source: docs/notes/client/CONTENT_STUDIO.md

Axiom Content Studio#

The data authoring suite for Axiom. It edits every content table in worldserver.db as records rather than SQL: items, NPCs, skills, statuses, effects, loot, quests, achievements, doodads, recipes, shops, trade, factions, territories, world events, vehicles and so on.

To open it, use Axiom → Content Studio (Ctrl+Alt+E), or the Content Studio tab in Dev Tools.

Making something new (an item, NPC, world object or loot table)? The Tools > Axiom > Create wizards are quicker: they build every related row in one window and commit it as one patch. See EDITOR_SUITE.md.

Requires Unity 2022.3 or newer (UI Toolkit editor windows, Painter2D).

The workflow#

 edit  ──►  pending changes  ──►  validate  ──►  commit
            (undo/redo, kept       (Problems,     ├─ worldserver.db (one transaction,
             across reloads)        live)         │   backed up first)
                                                  └─ SQL/patches/0NN_content_<title>.sql
  1. Edit. Nothing touches the database while you work. Every edit is staged in a changeset with full undo and redo. - Edits survive script reloads and editor restarts (Library/Axiom/ContentStudio.pending). - Setting a field back to its original value removes the change.
  2. Validate. The inspector shows the selected record's problems live. Problems in the dock lists everything. F5 re-checks all tables.
  3. Commit (Ctrl+S). Content Studio does three things: - Backs up worldserver.db to Library/Axiom/WorldDbBackups (the newest 15 are kept). - In one transaction, runs the patch against the database and records it in schema_versions, so the server's patcher won't run it again. - Moves the patch into the server's SQL/patches.

If any step fails, nothing is changed. The server reads content at start-up, so restart it to see the changes in game.

Write patch only is for when the world server is running and holding the database. It writes the patch and nothing else; the server applies it the next time it starts.

Patches are ordinary numbered SQL files, so content changes go through git like code. A fresh worldserver.db built from SQL/patches gets them automatically.

  • New rows are written as INSERT OR REPLACE.
  • Edits are written as UPDATE … SET on only the changed columns. Two designers changing different fields of the same item don't overwrite each other.
  • Removed rows are written as DELETE.

The window#

Area What it does
Sidebar (left) Tables grouped by category: Items, NPCs, Combat, Quests & Progression, Loot & Economy, Crafting, World, Factions & PvP. Each shows its row count, pending changes (•n) and a problem dot. Tables the schema doesn't annotate are under Other Tables, still fully editable.
Records (middle) Virtualised list. Sort by clicking a column header. Coloured stripes mark new, edited and deleted rows; dots mark problems. Right-click a row to Duplicate (with or without children), Revert, Delete, Copy as SQL or Copy id. Also has CSV export / import.
Inspector (right) Header with icon, name and state, plus actions. Below it: live problems, a preview for the table, the fields (grouped), child rows editable in place, and Where used.
Dock (bottom) Problems (filter by severity or text; click to jump), Changes (each pending row with before → after per field, and per-row Revert), Activity (the log).

Search syntax (records list)#

Query Matches
iron sword every word appears in the row (name, values, reference names)
rarity:epic that column contains the text (reference and enum names count)
Kind=11 that column is exactly the value
#new #modified #deleted #changed pending edits
#error #warning #issues validation results

Fields#

Each column gets the editor that fits it:

  • References show the target's name and id. Click to pick from a searchable list, → to jump to the row, or type the raw id. Some references depend on another column: Effects.RefId follows Kind, QuestObjectives.TargetId follows ObjectiveType, and Achievements.TargetId follows Kind. Special values are named, for example DoodadFuncs.NextPhaseId −1 "Remove the doodad" and 0 "Stay".
  • Enums use dropdowns with the server's names: EffectKind, EquipSlot, InteractionActionType, AchievementKind and about 30 others.
  • Flags (CrowdControl) use a checklist.
  • Icons show a preview and open a browser over Resources/Icons. Icon columns resolve relative to their folder, so DoodadFuncs.IconName uses Icons/Actions.
  • Model keys (ModelType) list the keys registered in the scene's WorldObjectPrefabRegistry, show a prefab preview, and flag unknown keys. Open main_world for this.
  • Colours use a hex field and a colour picker.
  • Durations and percentages show a readable hint next to the value (90000 ms = 1 min 30 s).
  • Keys of saved rows are read-only. Duplicate a row to get a new key.

Previews#

Table Preview
Items The item as players see it (rarity colour, stats, use effects). Also where it comes from (loot tables with chances, shops, recipes, quests, fishing, treasure, effects that give it) and what it's used for (materials, keys, objectives, trade routes, collections).
Loot Tables Odds per entry, expected items per kill, chance of no item, which NPCs drop it, and a 1,000-kill simulator.
Recipes Materials → station → output and grades. Also material cost at vendor prices against the output's sell price.
Doodads The state machine: phases as nodes, F/G actions and timers as edges, the start and broken phases marked, unreachable phases flagged, and "Removed" as an end state. Click a phase to open it.
World Events The next six starts in local time and UTC, plus a 24-hour timeline of announce and run windows.
Quests The chain before and after this quest, giver and turn-in, objectives, rewards, and XP as a share of the level.
NPCs Health, damage per second, aggro, faction, ability rotation by priority, spawners with positions, and world events that use it.
Skills, Statuses, Doodad Actions Their Effects rows as sentences ("Deal 10-14 Fire damage + 0.6× power"), plus cast, duration and stat modifiers.
Trade Packs Payout at full demand to every outlet by distance, and fixed routes.

Record operations#

  • New (Ctrl+N) takes the column defaults, the annotated starting values and the next id. It also fills the parent link when added from a child grid, including filters such as OwnerType = 1 for item effects.
  • Duplicate (Ctrl+D) copies the row.
  • Duplicate + children (Ctrl+Shift+D) copies the whole tree with new ids. For example, a doodad copies with its phases, actions, timers and their effects, and an NPC with its abilities and phases. Every reference between copied rows is re-pointed at the copies, so the duplicate doodad starts in its own first phase. The whole copy is one undo step.
  • Delete also removes the rows that belong to the record. Before deleting, it tells you how many rows elsewhere will become broken links.
  • CSV import shows what it will do first: new rows, changed rows, and rows missing from the file (optionally deleted). The whole import is one undo step.

Undo, redo, commit, Go to and the duplicates can be rebound under Edit → Shortcuts → Axiom/Content Studio.

Validation#

Generic checks come from the schema annotations and run on every column:

  • References to missing rows (or rows being deleted).
  • Required references left at 0.
  • Enum values the server doesn't know.
  • Numbers out of range.
  • NOT NULL columns left empty.
  • Missing icons (warning).
  • Unregistered model keys (info).

Domain rules mirror what the server's catalogs check when they load, so a row the server would skip shows up here first:

Area Checks
Doodads Start, broken and next phases must belong to the same doodad. Flags unreachable phases. A gate or wall needs health.
Quests No quest may require itself, and chains must not loop. Flags quests with no objectives and quests with no giver.
World events The schedule rules (interval ≥ 5, duration and announce below the interval). A boss or rift needs its NPCs.
Vehicles Flags kits with no PlaceDoodad effect.
Effects Apply Status, Cast Skill, Summon and Place Doodad need a target. Flags a heal or damage that does nothing.
Achievements A collection needs items, and no more than 62. Count must be at least 1.
Loot, recipes, statuses, factions, territories Min ≤ max. Recipes need materials. Flags a status that ticks less often than it lasts. Only player factions can be playable. Siege hour is 0-23.

Uniqueness:

  • One gear-stats, treasure-map or trade-pack row per item.
  • One climb route per spawn.
  • One relation row per faction pair.
  • One action per doodad phase slot.

Experience curve: no gaps.

Errors don't stop you working. They're shown again at commit time, and committing with errors needs a second confirmation.

Extending it#

  • A new server table shows up on its own, under Other Tables, and is editable straight away. To give it a category, references, enums and children, add a T("Table", "Display", "Singular")… entry to Schema/ContentSchema.Definitions.cs.
  • A new column shows up on its own. Naming conventions describe it until you annotate it:
Column name Treated as
…ItemId a reference to Items
…NpcTemplateId a reference to NpcTemplates
…StatusId a reference to StatusTemplates
Is… / Has… / Can… a checkbox
…Ms milliseconds
IconName an icon
ModelType a model key
  • A new server enum value: add it in Schema/ContentEnums.cs. Until then, unknown values show as "57 (unknown)" and are kept.
  • A new validation rule: add an entry to Rules (per row) or TableRules (per table) in Validation/ContentValidator.cs.
  • A new preview: add a class deriving from VisualizerBase under UI/Visualizers. It's found by reflection, with nothing to register.

Layout#

Editor/ContentStudio/
  Data/          SqlBackend (the only SQLite code), DbValue, TableSchema,
                 ContentDatabase (schema + rows from disk), Changeset (staged
                 edits, undo/redo, persistence), WorkingSet (disk + edits),
                 CommitService (patch SQL, transaction, backup)
  Schema/        ContentSchema (annotations + conventions), Definitions,
                 ContentEnums (the server's enums)
  Validation/    ContentValidator (generic + domain rules)
  UI/            ContentStudioWindow, Sidebar, RecordList, RecordInspector,
                 FieldFactory, Pickers, DockPanels, RecordOps, StudioContext,
                 StudioAssets, ContentStudio.uss, Visualizers/

The data, schema and validation layers have no UnityEditor dependencies; only SqlBackend touches SQLite. They were verified outside Unity against a worldserver.db built from the server's migrations and SQL/patches. That run covered:

  • Editing, undo and redo, and pending changes surviving a reload.
  • Deep duplicate with re-pointed links.
  • Cascade delete.
  • CSV round trips.
  • Committing to the database and schema_versions.
  • Replaying the generated patch on a fresh database.

The editor UI was compile-checked against the Unity API surface it uses.
