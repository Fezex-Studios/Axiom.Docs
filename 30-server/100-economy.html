Economy: Shops, Mail, Auction & Cash Shop#

Piece File Job
CoinMoney Core/Economy/CoinMoney.cs Money is copper: 100 copper = 1 silver, 100 silver = 1 gold.
ShopManager Core/Shops/ShopManager.cs NPC merchants (gold) and currency shops (item currencies, honor).
CurrencyShopCatalog Core/Shops Currency shop offers from Data/currency-shops.json.
ShopInventoryExchange Core/Shops Plans a whole purchase on a copy of the bag first.
MailManager Core/Social/MailManager.cs The front door to mailboxes: list and claim.
AuctionManager, AuctionClient Core/Economy, Core/AuctionServer The auction house as the World server sees it.
CashShopManager Core/Economy Cash shop: ask Persistence, tell the player.
MarketAccess Core/Economy Auctioneer and mailbox must be an NPC/object you're standing at.
WorldOutbox Core/Services Obligations still owed to another service (Persistence flow).

Money#

Every gold field in packets, tables and APIs is a total in copper. PlayerManager.TryAddGold(peer, delta) is the only place gold changes (Players); the client formats copper as g/s/c (CoinMoney on both sides). Item base values are Items.vendor_price.

Balances vs amounts. A character's purse and warehouse are long copper (protocol 46, MySQL BIGINT), capped at CoinMoney.MaxBalance = 10¹⁵ copper (100,000,000,000g). The cap stays below 2⁵³ so Lua numbers and JSON stay exact, and far below long.MaxValue so adding two balances can never overflow. Every change goes through CoinMoney.TryAdd(balance, delta, out result), which refuses a negative or over-cap result. A single amount (a price, mail gold, a trade offer, a bid, a reward, one warehouse deposit) stays int: at most 214,748g 36s 47c per transaction. A new feature that sums many amounts sums them as long and checks them with TryAdd.

NPC merchants#

A shop (Shops: Id, NpcTemplateId, Name) belongs to an NPC template, so "the blacksmith" is one list however many blacksmiths stand in the world. ShopItems: ItemId, BuyPrice (player pays; 0 = not for sale), SellPrice (merchant pays; 0 = won't buy; overrides the item's vendor_price at that shop), SortOrder. Stock is unlimited.

Flow: interact with the NPC's Trade action → W2CShopOpen (the list) → C2WShopBuy { NpcNetworkId, ItemTemplateId, Quantity, ShopId, RequestId, Lines[] } (a cart: several lines bought atomically) / C2WShopSell { Slot, Quantity } → W2CShopResult. Every request re-checks that you're still next to that NPC. Selling anything to any merchant pays vendor_price × count unless the shop overrides it.

Currency shops#

Offers priced in item currencies (Guild Crests, Aether Crystals, Loyalty Tokens) or honor live in Data/currency-shops.json (edited with Tools ▸ Axiom ▸ Content ▸ Currency Shops): currency definitions (item id, name, icon, bound, no-trade) and shops with their offers. C2WCurrencyShopBrowse opens one remotely when the shop allows it.

Mail: how players receive things#

Everything a player receives when they might be offline or have a full bag arrives by mail: auction proceeds and purchases, unsold listings, refunds, cash shop goods, GM gifts, loot rolls won with a full bag.

  • Stored in Persistence (mail): sender, subject, gold, one item stack (with its instance), and a mailbox (general, or marketplace mail which can be opened remotely).
  • Posting is done by whoever sends: the World server (PersistenceClient.W2PMail.Send or WorldOutbox.SendMailAsync), the Auction server's outbox worker, the cash shop transaction, or SQL (MySQL). Every delivery has a delivery key (mail_receipts) so a retried post is never delivered twice.
  • Claiming is one transaction: the contents go into the character in memory, then one save (/characters/save-full with ClaimMailId) writes the character holding them and deletes the mail. The database can never hold both (a dupe) nor neither (a loss).
  • Opening a mailbox is gated by MarketAccess (you must be at a mailbox). Packets: W2CMailList, C2WMailClaim { MailId } (0 = all, negative = just list), W2CMarketResult.

Auction house#

Listings live in the separate Auction server and its own database. The World server owns players, so it does the two things that service can't: take an item out of a bag and gold out of a purse. Nothing is done there until the character's database row agrees with what was done here (a write-through SaveNowAsync before every call):

Action Order
List take the item and a deposit here → save (with an outbox entry) → create the listing there (idempotent receipt). Not confirmed → both go back. Listing refused → item mailed back.
Buy read the listing → charge the buyer here → save → take the listing there under a fresh purchase key. The take queues the seller's gold and the buyer's item as mail in the same transaction. Refused → buyer refunded by mail. No answer → ask again with the same key until the service says taken or not.
Bid take the bid here → save (bid stored as owed) → place it there under a bid key. Outbid, buy-now or withdrawn → the service mails the coins back. At the end the top bid pays the seller and the winner gets the item by mail.
Cancel take the listing there (seller-checked, not once it has bids); the service mails the item home.

Because everything received comes by mail, a full bag never stops or loses a sale. Packets: C2WAuctionBrowse, W2CAuctionList, C2WAuctionCreate { Slot, Quantity, Price, StartBid, Hours }, C2WAuctionBuy, C2WAuctionBid, C2WAuctionCancel, W2CMarketResult. Bound and no_trade items can't be listed. A listing deposit is kept; the service takes Auction:FeePercent from sales.

Cash shop#

Catalogue (cash_shop_items), credit balances (account_credits) and mailboxes all live in Persistence, so a purchase is one transaction there: check balance, deduct, post the goods by mail. There's no moment where an account was charged and nothing was sent. Credits are per account and have nothing to do with gold; nothing in the game can mint them (top up outside the game, e.g. from your payment system writing to account_credits). The cash shop button works anywhere; the goods arrive in marketplace mail. Packets: C2WCashShopBrowse, W2CCashShopList, C2WCashShopBuy, C2WCashShopGift.

Player trade#

Two players trade directly through a trade window (C2WTradeCommand: request, accept, offer item/gold, lock, confirm; W2CTradeState). When both confirm, both characters are saved in one transaction (/characters/save-pair), so a crash can't give both sides the goods. TradeManager (Core/Trade/TradeManager.cs). Lua OnTrade fires.

The pattern for new economy features#

  1. Change memory first, but don't tell another service until a save confirms it. Use SaveNowAsync.
  2. Put what you owe in the same save (OutboxEntryDto), delete it when settled.
  3. Make every downstream call idempotent by a key you generate (purchase key, bid key, delivery key).
  4. Deliver by mail whenever the player might be offline or full.
  5. Ask again with the same key on timeout; never guess.

Give everyone online a gift (Lua)#

Server:RegisterCommand("gift", function(player, args)       -- ".gift" in chat; check staff yourself
    if player:GetName() ~= "Aidan" then return end
    for _, p in ipairs(Server:Players()) do
        p:GiveItem(4, 5)                                     -- 5 Healing Potions (fails if the bag is full)
        p:SendMessage("A gift from the team: 5 Healing Potions.")
    end
end)

For guaranteed delivery to everyone, offline included, mail them with SQL instead (MySQL).
