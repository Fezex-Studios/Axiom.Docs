Feature note, kept next to the code it describes. Source: src/Tools/Axiom.LoadTest/VALIDATION.md

Validation record#

31 Oct 2026: zone spread, settle, ladder, navmesh routes#

Built with the .NET 10 SDK; selftest 29/29 and selftest-network pass (with the shared protocol at 45, which the runner requires).

End to end against a stand-in World server (real UDP, the real character motor over this repo's collision files, positions kept across logins, a TickHealth line per zone host):

  • 60 bots, one process, zone spread from the spawn point: 30 sent to each of zone_test1 and axiom_wilds, 95% reached their zone during warmup, CONFIGURED CHECKS PASS.
  • fleet-settle with 80 accounts in two batches: 38/40 home in each batch; positions saved.
  • Ladder [40, 80] with 20 bots per generator, after the settle: both steps PASS, 20+20 and 40+40 in the two zones from the first second, per-zone-host server ticks read from the log.

The stand-in is not the real World server: no NPCs, no other players' snapshots, no persistence service. The first real run should be a small ladder (for example [250, 500]) on your own server.

Found on the way, in your data (not changed here): * The navmesh (Data/navmesh/default) was baked from an older collision export than Data/world_collision. Routes may cross things built since; bots skip blocked corners, and the run prints a warning. Rebake it. * Axiom.LoadTest/Data/world_collision is an older export than the server's. Presets that use it will be refused (collision hash mismatch); the run now warns. The new presets read the server's folder. * Shared/Axiom.Network/Shared/ProtocolVersion.cs says 44, but MotorProfileData.SurfaceSwimOnly is protocol 45 and this runner expects 45. Bump Current to 45 when that change is done.

The supplied runner targeted protocol 33. This update targets the current protocol 34 network and shared movement source from the Axiom crowd performance patch.

Checks actually run here#

See the archive's root SOURCE_VALIDATION.json for recorded results. Checks cover C# lexical delimiters/literals/comments, PowerShell lexical structure, project XML and shared-project API/source consistency, JSON preset parsing/known field names, report JavaScript syntax/DOM initialization, deterministic assignment/ramp policy models, preserved session-secret exclusions, file hashes and ZIP readback integrity.

Lexical checks and separate mathematical policy models are not C# compilation or native test execution. No .NET SDK/runtime, PowerShell or Unity execution was available. There is no live server run or player-capacity result from this environment.

Native checks included but not run here#

selftest includes 23 checks: the original configuration/password/histogram/spawn/snapshot/input-codec/NPC-frame/prediction/replay/scenario checks plus launch protocol, wave pacing/stall behavior, shared-anchor/radial assignments, generator partitions, authoritative stuck detection, hold-only metrics, bounded floor-safe steering, NPC snapshot positions, offered quest/reply matching, server-log parsing and new option limits.

selftest-network binds a real synthetic loopback UDP server and exercises authentication/selection, collision baseline, delayed world-entry release, two-stage spawn ACKs, input commands and reconciliation. It rejects input/prediction before entry is released. This is not an Auth HTTP load test or a real world simulation.

The Windows startup command runs Release build and both test commands before the console menu. A local failure stops startup; preserve the first error. Run a ten-bot staging pilot only after those checks pass.

Staging checks still required#

  1. Verify protocol 34, matching movement collision hashes and successful single-bot entry.
  2. Run the ten-bot pilot and inspect actual server positions, navigation around walls/ledges, NPC interaction replies and respawn/reconnect behavior.
  3. Check initial entry, return-to-selection, speed/profile epoch changes, transfers and collision-file loading. Confirm deferred/reordered entry data does not start prediction early.
  4. Validate waypoints/absolute centers with a few bots before using them for geographically broader tests. Do not hide blocked routes by counting intended destinations.
  5. Measure 100, then 250, then 500 with a real Unity client observing and World tick/stage logs. Compare distributed launch and hotspot/surge tests separately.
  6. Use fresh eligible characters for quest-acceptance coverage, or explicitly label a browsing-only run. Check denial/timeouts and actual quest-update confirmations.
  7. Compare the same server workload with the generator on a separate machine when possible. A saturated local generator, Unity rendering cost and an overloaded server are distinct measurements.

No test here establishes full human behavior, combat/economy workload, Unity rendering capacity or a production concurrent-player limit.
