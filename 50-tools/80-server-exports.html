Tools

Server Exports#

The servers have no Unity. Everything they need to know about the world is exported from the Unity project into files. If an export is stale, client and server disagree about the world - the most common source of "rubber-banding", "NPC under the ground" and "can't log in: collision mismatch". The file formats are in World files.

Movement collision Tools ▸ Axiom ▸ Server Exports ▸ Movement Collision ▸ Export StreamingAssets/World/MovementCollision Data/world_collision
NPC collision Server Exports ▸ NPC Collision ▸ Export StreamingAssets/World/NpcCollision Data/npc_collision.json

Movement collision#

The triangles players (and the server's movement simulation) collide with, plus water volumes, from:

  • every scene named main_world, tile_*, dungeon* or world_*;
  • every prefab in the WorldObjectPrefabCatalog, once per doodad visual state that can block (full, depleted, open, closed, foundation, walls, built, crop stages...), so a closed gate blocks and an open one doesn't;
  • colliders on the layers in the exporter's collision mask (the Player prefab's mask). Actor bodies stay interaction-only.

Incremental: each scene's and prefab's baked result is cached in Library/AxiomCollisionCache, keyed by a hash of the asset and everything it depends on (prefabs, meshes, terrain data, scripts, the movement DLL). Only changed scenes are opened. The output is byte-identical to a full rebuild - the collision hash (SHA-256 of manifest.acm) that clients are checked against doesn't change for nothing. Verify Incremental Export proves it; Export (Full Rebuild) throws the cache away.

Deploy: after exporting, the files are copied to the server's Data/world_collision and every built copy under its bin/**/Data (what a server started from the IDE actually reads), so a restart picks it up without a rebuild. Set the server's Data folder once (Dev Tools ▸ NavMesh, stored in EditorPrefs Axiom.Server.DataDir); otherwise copy the folder yourself.

Build machine / CI:

Unity -batchmode -quit -projectPath <client> \
  -executeMethod Axiom.Client.Axiom.Client.Editor.Netcode.MovementCollisionExporter.ExportFromCommandLine \
  [-axiomFullRebuild] [-axiomNoDeploy]
# exit code 0 = success

When: after any change to static colliders, terrain, water or blocking doodad prefabs. The World server disconnects a client whose C2WMovementReady.CollisionHash differs from its own (AuthoritativeMovement) - it would be corrected constantly otherwise, so ship the client and server copies together.

NPC collision#

npc_collision.json (version 3, shapes only) gives the server a body per model key, scanned from catalogue prefabs in order: a collider named Body (capsule or box) → an upright CapsuleCollider → (creatures) a box collider → (creatures) a capsule measured from the mesh. Once the World server has run, it writes npc_model_types.json next to the file, and the export then includes only the model types NPC templates actually use (trees and ore are left out).

Per-template shape overrides live in Content/NpcCollisionProfiles.asset (NpcCollisionLibrary: a TemplateId with a source capsule or box). Blocking rules (does this NPC block players?) are in worldserver.db ▸ NpcTemplates, not here. Set Server File… chooses the server's npc_collision.json so every export is copied there; Show NPC Bodies In Scene previews the shapes.

Terrain heightmaps#

.achtmap at the terrain's own heightmap resolution (no downsampling - the server loads it once, not per tick). Used for NPC ground snapping, spawn placement, y = 0 teleports, digging and line of sight. Re-export as the last step of every sculpting pass; a stale heightmap is the "server thinks you're underground" bug.

The shared DLLs#

Axiom.Network.dll (packets, opcodes, MessagePack types) and Axiom.Movement.dll (the motor, collision formats, WorldGrid, ZoneMap) are compiled in the server solution and copied into Assets/AxiomMMOKit/Plugins:

cd src/Shared/Axiom.Network  && dotnet build -c Release
cd ../Axiom.Movement         && dotnet build -c Release
# copy bin/Release/netstandard2.1/Axiom.Network.dll and Axiom.Movement.dll into client Assets/AxiomMMOKit/Plugins

Do this after every change to either project. Symptoms of forgetting: "Could not read X packet (Axiom.Network.dll out of date?)", protocol mismatch on connect, or movement corrections everywhere.

Validate Netcode Build#

Tools ▸ Axiom ▸ Server Exports ▸ Validate Netcode Build checks the shared DLLs against the server source, the MessagePack version, the NPC collision export and that the movement collision export is current. It also runs automatically before every client build.
