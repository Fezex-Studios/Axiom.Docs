Architecture

Movement & Netcode#

Axiom's movement is server-authoritative with client-side prediction, the model used by most modern action games (Source, Overwatch, Rocket League). The client never tells the server where it is. It sends its inputs; both ends run them through the same code; the server's answer wins.

Some classic MMO servers trusted client positions, which is why they were famous for speed and teleport hacks. Axiom deliberately doesn't.

The pieces#

Piece Where Job
CharacterMotor Axiom.Movement (shared DLL) Step(state, input, profile, dt) → state. Capsule collide-and-slide, steps, slopes, gravity, jump, swim, fly.
MoveState shared Everything the motor carries between steps: position, velocity, mode, grounded, coyote time, jump buffer... A plain struct, copied freely.
MoveInput shared One step of intent: sequence, wish direction (x, z), yaw, pitch, buttons (jump, walk, ascend, descend...).
MovementProfile shared The numbers: capsule size, walk/run/swim/fly speeds, acceleration, slope limit, step height, gravity, jump height, coyote time...
ICollisionWorld shared interface The only way the motor sees the world. Server: WorldCollisionSet (exported triangles, heightmaps, water, doodads, NPC capsules). Client online: the same WorldCollisionSet. Client offline: UnityCollisionWorld over PhysX.
FixedStepClock shared 60 Hz fixed timestep (Delta = 1/60).
AuthoritativeMovement World Core/Movement Runs every player's motor on the server.
ServerInputQueue World Core/Simulation Per-player jitter buffer of inputs.
LocalCharacterMotor client Movement Runs the motor locally at 60 Hz, keeps a prediction history, reconciles.
MovementPredictionClient client Networking Loads the client's collision set, applies W2CMovementConfig / W2CMovementState to the local motor.
RemoteEntityInterpolator client Gameplay Draws other players and NPCs from snapshots, 100-ish ms in the past.

The motor's three rules#

From the top of CharacterMotor.cs; break any and prediction stops working:

  1. Fixed timestep only. Always Step(..., dt: 1/60). Never Time.deltaTime. Different dt → different results on two machines → reconciliation impossible.
  2. No state outside MoveState. The motor holds no per-character fields. A hidden timer wouldn't be rewound when the client replays inputs from an older state.
  3. No engine calls. Everything about the world comes through ICollisionWorld.

Same inputs + same profile + same collision + same start state ⇒ same result on client and server. That's the whole design.

A movement round trip#

client frame:  read keys ─▶ MoveInput #812 ─▶ motor.Step (predict) ─▶ history[812]
                                         └──▶ C2WMovementInputs { epoch, inputs 809..812 }   (Control channel, unreliable)

server tick:   ServerInputQueue ◀── inputs ── jitter buffer ── one input per 60 Hz step
               motor.Step(serverState, #812) ─▶ serverState, Ack = 812
               W2CMovementState { epoch, serverTick, ack=812, state }                       (unreliable)
               snapshot to everyone else who can see you

client:        Reconcile: take server state at #812, replay history[813..], compare

1. Configuration: W2CMovementConfig#

When a player enters the world (and whenever their movement setup changes: mounting, a speed buff, death, a stun, a GM freeze, a layer change), AuthoritativeMovement.Reset sends W2CMovementConfig:

  • Epoch: a new number. Inputs and states from an older epoch are ignored on both sides. That's how a teleport cleanly cuts off in-flight inputs.
  • Profile: the server-built MovementProfile (CreateProfile): base values from World:Movement* config, times the move-speed stat, times the mount multiplier; zero speed if dead, immobile or frozen. The client must use this profile; it can't choose its own speed.
  • State: the starting MoveState.
  • CollisionHash: hash of the server's collision export. The client loads its own copy (StreamingAssets/World/MovementCollision) and disconnects with "Client and server world collision versions differ" if the hashes don't match.
  • CollisionLayer (0 = open world, otherwise a dungeon instance or house layer), NeedsWorldEntry (show a loading screen: first entry, a layer change, or a teleport over TeleportLoadingScreenMeters, 256 m).

The client answers C2WMovementReady { Epoch, CollisionHash } once its collision is loaded. Not ready within MovementReadyTimeoutSeconds (30 s) → disconnect.

2. Inputs: C2WMovementInputs#

LocalPlayerInput turns keys and camera into a MoveInput once per 60 Hz step (Movement & camera (client)). The motor steps it immediately (prediction) and appends it to the PredictionHistory.

Inputs are sent about 20 times a second in a hand-packed binary packet (MovementInputCodec, 22 bytes per input, max 16 per packet). Every packet repeats recent inputs redundantly, so a lost UDP packet costs nothing: the next one carries the same inputs again. Duplicates are dropped by sequence number.

Inputs carry intent, never outcomes. WishDirection is "which way I'm pressing", clamped to length 1 by MoveInput.Sanitize(). Speed comes from the profile, so a hacked client can only press harder in a direction, not go faster.

3. Simulation on the server#

Every tick (TickStage.MovementAndAoi), AuthoritativeMovement.TickAsync:

  1. Advances its own FixedStepClock by real elapsed time (typically 3 steps per 50 ms tick, at most 6).
  2. For each player, checks the profile is still current (stats, mount, death) and re-sends config if not.
  3. Makes sure collision around the player is loaded (async, CollisionPrefetchMeters ahead plus 3 s of travel). If it isn't, the player waits rather than falling through the world.
  4. Pulls one input per step from the player's ServerInputQueue and runs CharacterMotor.Step. Players in different zones are simulated in parallel (MovementZoneWorkers); see Parallel stages.
  5. Commits the result (PlayerManager.CommitMotorMove): position into the session, the interest grid and the snapshot dispatcher.
  6. Sends the owner W2CMovementState { Epoch, ServerTick, Ack, State } (unreliable).

The jitter buffer (ServerInputQueue). Inputs arrive in bursts. If the next input hasn't arrived yet, the server waits for it (that step isn't simulated) instead of guessing, from a budget of up to 15 steps that refills slowly, so holding inputs back can't freeze you in mid-air. If an input is truly lost, it's skipped, but a jump in a skipped or late input is carried to the next step. A jump is one input (the press): losing it would make the server's character not jump while yours did. Every input costs exactly one step, and no more than real time's worth of steps run per tick, so none of this lets anyone go faster.

Players driving a vehicle, sitting on furniture or climbing a house part are managed: their position comes from that system and inputs are ignored.

4. Reconciliation on the client#

MovementPredictionClient.Pump hands the newest W2CMovementState to LocalCharacterMotor.Reconcile:

  1. Drop history up to and including Ack.
  2. Start from the server's state and replay every remaining input in history through the motor.
  3. Use the result as the new predicted state. Any visual difference is smoothed out over a few frames (a visual offset), not snapped.

If both sides agree (the normal case) the replay lands exactly where the client already was and nothing visible happens. If the server disagrees (a stun, a wall the client didn't know about, a cheat), the client corrects.

If the replay would walk into an area whose collision hasn't loaded yet, reconciliation is deferred until it has.

Collision data must match#

Because both sides step the same motor, they must collide with the same world. The Movement Collision export (Unity: Tools ▸ Axiom ▸ Server Exports ▸ Movement Collision ▸ Export) bakes the walkable geometry of every tile scene and prefab into a set of files:

  • written to the client's StreamingAssets/World/MovementCollision;
  • copied to the World server's World:MovementCollisionDirectory (Data/world_collision).

Both load them into a WorldCollisionSet and compare its Hash. Re-export after changing any walkable geometry (terrain sculpt, a new building, a river) and restart the World server. World files describes the formats; Server exports the tool.

On top of the static set:

  • Doodads that block (fences, gates, placed houses) are added and removed at runtime on both sides from the doodad spawn/state packets (MovementPredictionClient.DoodadSpawn/DoodadState).
  • NPC bodies (capsules or boxes from npc_collision.json) are streamed to each client in W2CNpcCollisionFrame packets, numbered by CollisionRevision, so prediction collides with the same NPCs the server does.
  • Water comes from the HDRP Water Surfaces in the scenes, exported as WaterVolumes with the collision. Swimming starts at SwimDepthThreshold metres of water. While riding, MovementProfile.SurfaceSwimOnly is set (the server's CreateProfile from Mount.IsMounted, sent in MotorProfileData): Swim Down is ignored, so the mount swims on the surface.

Remote characters#

Other players and NPCs are not predicted. They're drawn from snapshots (Interest & replication):

  • W2CWorldSnapshot carries quantised position (1/64 m), yaw, the MovementState bitfield (running, airborne, jumping, swimming, flying, in combat...) and optionally velocity and lean.
  • RemoteEntityInterpolator buffers them and renders a fixed delay in the past, interpolating between the two snapshots around the render time (Valve's Source approach). It never extrapolates on arrival timing, which jitter makes useless.
  • RemotePlaybackClock advances at the server's measured tick rate, not the nominal one, so a server running at 19 Hz doesn't make everyone stutter.
  • Jumps are a separate reliable event (JumpEventBroadcaster): the rising edge of the Jumping bit is sent once, and observers integrate the arc themselves with the shared MovementConstants.Gravity and JumpVelocity, so the arc is smooth even at a low snapshot rate.

MovementState is client-reported and presentation-only (it picks animations). MovementStateRules strips bits a player can't legitimately have (Flying without a flying mount). If you ever gate gameplay on one of those bits, verify it server-side first.

Tuning movement#

Want to change Where
Run/walk speed, gravity, jump height, slope limit for players World:MovementRunSpeed, MovementWalkSpeed, MovementGravity, MovementJumpHeight, MovementSlopeLimit in the World's appsettings.json. Sent to clients in the profile; no client rebuild.
Mount speed, flying the mount's data in worldserver.db (Mounts & pets)
A speed buff an effect that changes StatId.MoveSpeedPct (Combat)
Swim depth, buoyancy, step height, capsule MovementProfile defaults in Axiom.Movement (rebuild both DLLs)
Remote jump arc MovementConstants (shared, rebuild both)
Control schemes, key bindings client Movement/ (Movement & camera)

Debugging movement#

Symptom Look at
Constant small corrections on slopes Collision export out of date, or terrain heightmap differs; re-export both.
"collision versions differ" on connect Client and server collision files differ. Export and copy, restart World.
Rubber-banding under load World log [MovementInput] (waits/skips) and [ParallelStages] movementMs.
Falling through the world Collision not exported for that tile, or a terrain hole.
Can't walk up a gentle incline MovementSlopeLimit / StepHeight, or a collider edge in the export.
Remote players stutter RemoteEntityInterpolator delay; snapshot budget (SnapshotEntitiesPerPeer), Interest & replication.
