Data & Databases

gamedata.bin#

The client needs some content before it's in the world (inventory tooltips, the character creation preview, gear on the body) and in bulk. That content ships as gamedata.bin: an encrypted binary package of item display data and gear visuals, generated from worldserver.db.

Everything else the client knows about content (skills, statuses, item stats and grades, quests, recipes, shops, trade, achievements) is sent as catalogue packets when a character enters the world (Data overview).

Life cycle#

World server boot (step 0d)
  ClientContentExporter.Run(worldserver.db, World:ClientContent)
    ├─ ReadItems()        Items ⋈ ItemCategories ⋈ ItemRarities (+ ItemUses flags)
    ├─ ReadGearVisuals()  GearVisuals ∪ GearVisualSlotDefaults (+ WeaponSheaths, ItemStats.WeaponKind)
    ├─ Build()            plaintext AGDB v4
    ├─ ContentHash = SHA-256(plaintext)            → sent to clients in W2CEnterWorld
    └─ Encrypt(key)  → write to every OutputPaths entry (only if bytes changed, atomically)
                          ├─ Assets/StreamingAssets/GameData/gamedata.bin   (ships in client builds)
                          └─ Axiom.Server.Auth/…/gamedata.bin               (served by Auth)

Client start (server_select scene)
  GameDataBootstrap
    ├─ copy StreamingAssets copy → persistentDataPath/GameData/ if newer or missing
    ├─ GET Auth /gamedata/version  → { "Hash": "…" }   (SHA-256 of the encrypted file)
    ├─ different from gamedata.hash? GET /gamedata/db → replace the cached file
    └─ GameDataDatabase.Initialize(path): decrypt in memory, parse, expose Items + gear visuals

Configuration (World server)#

World:ClientContent (Utils/Config/ClientContentConfig.cs):

Key Default Meaning
Enabled true Build the package and hash at boot.
OutputPaths [] Where to write the encrypted file. Relative paths are relative to the World exe. Typically the client's Assets/StreamingAssets/GameData/gamedata.bin and the Auth server's folder.
KeyHex "" The AES-256 key as 64 hex characters. Must equal the client's GameDataCrypto.Key bytes. Put it in appsettings.Local.json. Missing or wrong length → file not written (warning logged).
RequireMatch false Sent to clients as ContentMustMatch. Intended: a client whose content hash differs is sent back with an explanation. (The client doesn't check it yet; see below.)

Auth: Auth:GameDataPath (default gamedata.bin next to the Auth exe) is the file it serves. It re-hashes the file automatically when it changes on disk, so Auth needs no restart.

Log line to look for at World start:

[Content] Client package: 101 items, 37 gear visuals, content hash 4be1…; 1 file(s) written, 1 already current.

Binary layout (AGDB v4)#

All integers little-endian; strings are .NET BinaryWriter strings (7-bit-encoded length prefix, then UTF-8).

"AGDB"              4 bytes  magic
version             byte     4
itemCount           int32
repeat itemCount:
    ItemId          int32
    Name            string
    Description     string
    Category        int32    ItemCategories.Id
    IconName        string   resolved under Resources/Icons
    CategoryName    string
    RarityId        int32
    RarityName      string
    RarityColor     string   "#RRGGBB"
    RequiredLevel   int32
    IsUsable        bool     has an ItemUses row
    ConsumeOnUse    bool
visualCount         int32
repeat visualCount (sorted by ItemId, EquipSlot; ItemId 0 = slot default):
    ItemId          int32
    EquipSlot       int32
    PrefabKey       string
    AttachType      int32    0 skinned to the body, 1 attached to a socket
    DrawnSocket     string   where a weapon is held
    SheathSocket    string   where it's carried
    HideBodyParts   int32    GearBodyParts flags
    PositionX/Y/Z   float ×3
    RotationX/Y/Z   float ×3
    Scale           float
    SheathScale     float    v4

Validation on both ends: item ids positive and unique, at most 1 000 000 items and 100 000 visuals, a visual must reference an existing item (or 0), one visual per (item, slot). The client reads v1–v4 (GameDataBinaryFormat.ReadPackage) and refuses a newer version ("update the client and server together").

The exporter's queries (ClientContentExporter.ItemQuery, GearVisualQuery) are public constants; Dev Tools' gear visual export runs the same query. Keep them identical.

Encryption#

file = IV (16 bytes) ‖ AES-256-CBC(plaintext, key, IV, PKCS7)
IV   = first 16 bytes of HMAC-SHA256(key, plaintext)
  • The IV is derived from the content, so the same database always produces byte-identical files: the Auth hash doesn't change and clients don't re-download after a restart with no content changes.
  • Files are written to path.tmp then moved over, so Auth never serves half a file.
  • This is a deterrent, not security: the key is in the client. Anyone determined can extract it. Treat item names in the file as public. Rotate the key (change both GameDataCrypto.Key and KeyHex) if you want old extracted keys to stop working.

Never put the key in a shared document or a screenshot. It belongs in appsettings.Local.json and in GameDataCrypto.cs.

On the client#

File (Scripts/GameData/) Job
GameDataBootstrap In the server_select scene: copy bundled → cache, check Auth's hash, download, initialise. Falls back to the bundled file if Auth is unreachable.
GameDataCrypto The AES key and Decrypt.
GameDataBinaryFormat Reader (and writer, for editor tools).
GameDataDatabase Decrypts straight into memory (no plaintext on disk), parses once, exposes Items and gear visuals, raises Changed.
ItemRepository, ItemNames, ItemIcons, InventoryItemCatalog Lookups the UI uses. An unknown id shows as #<id>.
GearCatalog, GearVisualRecord What the character equipment system reads to put gear on bodies.

Cache location: Application.persistentDataPath/GameData/gamedata.bin + gamedata.hash.

GameDataBootstrap.AuthServerUrl is a constant (http://127.0.0.1:3000). For a public build, change it (or read it from the same -auth-url argument WorldDirectoryClient uses).

Content hash check#

The World server sends ContentHash (SHA-256 of the plaintext) and ContentMustMatch in W2CEnterWorld. The client doesn't compare them yet. To enforce matching content, hash the decrypted plaintext in GameDataDatabase.Initialize, store it, and compare in W2CEnterWorldHandler; on mismatch with ContentMustMatch, disconnect with "Your game data is out of date. Restart the game to update."

Common problems#

Symptom Cause
New items show as #90123 Client is using an old gamedata.bin. Restart the World server (rebuilds it), check the [Content] line wrote to the client path, restart the client. In the editor, the StreamingAssets copy is used if newer than the cache.
[Content] … KeyHex is missing Set World:ClientContent:KeyHex (64 hex) in appsettings.Local.json.
Client: decryption/padding error KeyHex ≠ GameDataCrypto.Key.
Client: "Unsupported game data version" Server writes a newer format than the client reads. Update the client.
Auth /gamedata/version answers 503 No file at Auth:GameDataPath. Add Auth's path to OutputPaths.

Extending the package#

To ship more content in the file (say, NPC display names for nameplates before they're spawned):

  1. Bump ClientContentExporter.FormatVersion and GameDataBinaryFormat.CurrentVersion to 5 together.
  2. Server: add a query and a Read… method; append a new section at the end of Build() (after the gear visuals), with a count first.
  3. Client: in ReadPackage, read the section only if (version >= 5), so v4 files still load.
  4. Expose it from GameDataDatabase and use it.

If the data is only needed in the world, prefer a catalogue packet instead: no format version, no file distribution, and it's always in sync with the server (Add a packet).
