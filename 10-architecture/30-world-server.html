Architecture

The World Server#

Axiom.Server.World is the game. It owns every player session, every NPC, every doodad and every rule. The other services store data (Persistence, Auction) or check identities (Auth), but only the World server decides what happens.

It is a .NET 10 console app built on the generic host (Microsoft.Extensions.Hosting). The interesting code is one class: Core/WorldServer.cs. It is an IHostedService, so the host calls StartAsync at boot and StopAsync on Ctrl+C. It is also LiteNetLib's INetEventListener, so every network event comes into it too.

Read this page before writing any server feature. The threading rules are the most important thing in the codebase. Breaking them causes bugs that only appear under load.

Start-up, in order#

Program.cs builds the host. It reads configuration from appsettings.json, then World.Performance.json, then appsettings.Local.json (for your secrets, git-ignored), then environment variables, in that order; later sources win. Then it calls UseWorldServer() (Bootstrap/ServerBootstrap.cs), which:

  • sets up NLog from nlog.config
  • binds the World, Network, Database and WorldDirectory config sections to WorldServerConfig, NetworkConfig, DatabaseConfig and WorldDirectoryReporterConfig
  • registers an EF Core IDbContextFactory<WorldDataDbContext> on the SQLite file Database:WorldDb (Data/worldserver.db)
  • registers the hosted services WorldServer and WorldDirectoryReporter, plus a few singletons (AuthService, QuestManager, ItemManager, SpawnPointService, GameDataPatchRunner)

WorldServer.StartAsync then runs these steps. The order is load-bearing, and each step says why.

Step What happens Why here
0a _world.Validate(), PacketSerialization.Configure() Refuse a broken config before anything opens a socket.
0b db.Database.MigrateAsync() EF Core migrations create or alter worldserver.db tables.
0c GameDataPatchRunner.RunAsync() Runs every SQL/patches/*.sql file not yet in schema_versions, in name order. This is how content reaches the database (worldserver.db).
0c+ NpcCollisionBehaviorMigration.ApplyAsync One-time import of old NPC collision behaviour into the database.
0d ClientContentExporter.Run(...) Builds gamedata.bin from the database it just patched and writes it to every ClientContent:OutputPaths entry. Its hash goes to every client on entering the world (gamedata.bin).
0d+ CharacterRaceCatalog.Load Races and body types are data; character creation is checked against them.
1 PersistenceClient.Start() Opens the HTTP link to the Persistence service and says hello.
2 Construct every manager (phase 1) See two-phase start-up. The terrain, navmesh and zones go first because the movement validator needs them.
3 BuildServiceContainer() then InitializeAll() (phase 2) Managers look each other up.
3b Load game data from the database Items first: quests, shops, loot and recipes check item ids against ItemManager. Then quests, spawn points, F/G actions, shops, loot, abilities and classes, skill plots, progression, NPC combat AI, mounts, effects, statuses, climates, doodads, interaction skills, crafting, instances, housing, fishing, trade, factions and territories.
4 Packet registration PacketDispatcher.AutoRegister builds one instance of every [PacketOpcode] handler from the service container. The set of client opcodes is remembered, and anything else a client sends is rejected.
5 NetManager.Start(Network:Port) The UDP socket opens with ChannelsCount = PacketChannels.Count (4). From here clients can connect.
6 Spawner definitions, NPC collision validation, pets, siege data NPCs stay dormant until a player is near.
6b DoodadManager.SpawnWorld() Every world doodad (ore, herbs, chests) goes into the interest grid.
6c Exploration catalog, achievements World events and treasure maps name NPC templates and items, so those must be loaded first.
7 DemoService.RunService() Development helper.
8 WarmWorldCatalogues(), NpcAiManager.Start(), start the tick loop The world goes live.
9 Background restores Player-placed doodads, trade demand, territories and world events come back from Persistence. Each one retries every 10 s until Persistence answers, then hands the result to the tick thread.

Every LoadFromDatabase() call reads its tables through a short-lived WorldDataDbContext from the factory. Catalogs are read once at boot and kept in memory, so a content change needs a World server restart.

Two-phase start-up#

The constructors in step 2 take only what a manager needs to exist: the config, the db factory, the shared interest grid. They never take another manager that might not have been built yet.

// Core/Services/IInitializable.cs
public interface IInitializable
{
    void Initialize(ServiceContainer services);
}

After every manager is registered, ServiceContainer.InitializeAll() calls Initialize on each one that implements IInitializable, in registration order. That is where a manager fetches the others it talks to:

public sealed class MyFeatureManager : IInitializable
{
    private PlayerManager _players;
    private ItemManager _items;

    public void Initialize(ServiceContainer services)
    {
        _players = services.Get<PlayerManager>();
        _items   = services.Get<ItemManager>();
        // Do NOT load data or touch the network here. That is step 3b.
    }
}

ServiceContainer (Core/Services/ServiceContainer.cs) is deliberately not a general DI container. It holds one instance per type, registered by hand in WorldServer.BuildServiceContainer(). It has two jobs:

  1. Packet handlers are built from it. A handler's constructor parameters are resolved from the container, so every handler gets the PlayerManager, never a second empty copy.
  2. Managers find each other through it in Initialize, instead of through static Current singletons.

A handler that asks for a type nobody registered fails at boot with No instance registered for X. Add a services.Register(...) call for it in WorldServer. That's intended: you find out immediately, not when a player first sends the packet.

The tick loop#

RunTickLoopAsync runs the whole simulation on one thread, at World:TickRate (20 Hz, 50 ms by default).

It is paced by TickPacer, not PeriodicTimer. On Windows a .NET timer wakes on the 15.6 ms system clock, so a 50 ms period became 62.5 ms (16 Hz). TickPacer uses absolute deadlines (start + n × interval), raises the Windows timer resolution to 1 ms while the server runs, sleeps most of the gap and spins the last ~1.5 ms. If the server falls more than two ticks behind (a debugger pause, a huge GC), it resynchronises instead of bursting through the missed ticks.

Each tick runs these stages in this order. TickHealthMonitor times every stage and logs a report periodically.

Stage (TickStage) Calls What it does
(pre) PlayerManager.AdvanceTick, InterestManager.BeginTick, admission sweep Advance the tick clock (movement packets are timestamped with it) and drop connections that never authenticated.
Actions PlayerManager.DrainActions() Run work queued from other threads (threading rule). Bounded by Performance.ActionsPerTick and Performance.ActionMilliseconds.
Packets NetManager.PollEvents() Every C2W packet handler runs here, via OnNetworkReceive.
Entries PlayerManager.PumpWorldEntries() Characters finishing their enter-world sequence.
Timers Scheduler.RunDue() Every timer in the game: corpse expiry, respawns, harvest completion, buffs and DoTs, auction sweeps.
MovementAndAoi AuthoritativeMovement.TickAsync(tick) Re-simulate every player's inputs with the shared motor, validate them, update the interest grid. Parallel by zone (see Parallel stages).
NpcAi NavMeshService.Tick(), NpcAiManager.Tick() Navmesh pages in/out, finished path searches, NPC brains, spawner activation.
WorldSystems interaction skills, doodads, crafting, storage, warehouse, fishing, InstanceManager.Tick() Timed actions; walking away cancels them. Dungeons run on their own threads; their results are applied here.
Maintenance WorldTerrainService.Tick(), PlayerManager.RunAutosave(tick) Unload unused heightmaps; spread periodic saves of dirty characters across ticks.
Spawns ReplicationManager.Spawns.Flush(tick) Send spawn and despawn packets for everything that entered or left each player's view.
Snapshots PlayerManager.FlushSnapshots(tick) The only place position packets leave the server: one batched, quantised W2CWorldSnapshot per player.

Any exception inside a tick is logged ([TickLoop] Unhandled exception in tick — continuing.) and the loop carries on. One bad handler can't stop the world.

What the health report means#

Every report window (5 s) each zone host logs its tick health:

[zone_test1] [TickHealth] work p50=13.80ms p99=31.74ms max=52.40ms startGap p99=62.19ms max=70.00ms overrun=2/100 lateStart=1/100 GC=3/1/0 gcPause=43.8ms allocated=330.1MiB managed=1100.2MiB workingSet=1600.5MiB rate=20.0Hz target=50.0ms
[zone_test1] [TickStages] average/max ms Actions=0.02/0.18 Packets=1.38/2.50 ... MovementAndAoi=6.08/41.69 ... Spawns=1.49/18.28 Snapshots=4.66/27.26
[zone_test1] [TickAlloc] this thread, KiB per tick average/max Actions=0.1/1.7 ... Snapshots=228.5/270.0 total=300.0KiB/tick
  • work p99 is the number capacity is judged on: at 20 Hz each tick has 50 ms, and the load test's pass limit is 40 ms.
  • GC=gen0/gen1/gen2, gcPause, allocated, managed and workingSet are process-wide, not per zone. gcPause is the total time the runtime paused for GC in the window; a few tens of ms per 5 s is normal.
  • [TickStages] is the average and slowest time of each stage on that zone's tick.
  • [TickAlloc] is the KiB each stage allocated on the zone's tick thread (parallel workers and the network thread are not counted). A stage that finishes on another thread after an await counts as 0 rather than a wrong number.

The other lines:

[AoI] window updates=… recomputes=… work=…ms knownLinks=… pending=…
[ParallelStages] movementWorkers=… movementMs=… aoiBatch=… snapshotWorkers=…
[SpawnWork] lastTick recipients=… ops=… sendMs=…
[CrowdWork] pendingActions=… pendingSpawns=… snapshotBytes=… gameplayPackets=… busyRequests=…
[NavMesh] pages=default:12/40 paths=… failed=… maxSearchMs=…

pendingActions rising and never falling means something floods the action queue. busyRequests > 0 means the server is refusing gameplay packets because it hit Performance.GameplayPacketsPerTick: players get "The server is busy". maxSearchMs over a few milliseconds means navmesh path searches are too long (check NavMeshWorkers).

The threading rule#

Everything that touches game state runs on the tick thread. Sessions, the interest grid (InterestManager / SpatialGrid), the Scheduler, catalogs that can change, entities: none of them are thread-safe, by design.

Packet handlers already run on the tick thread (inside PollEvents), so a handler that only reads and writes game state needs nothing special.

The trap is await. Anything that waits on the network (Persistence, Auth, Auction) finishes on a thread-pool thread. After the await you are off the tick thread. Hop back with PlayerManager.EnqueueAction:

// Inside a packet handler (tick thread)
public void Handle(NetPeer peer, NetPacketReader reader)
{
    var packet = MessagePackSerializer.Deserialize<C2WMyRequest>(reader.GetRemainingBytesMemory());
    if (!_players.TryGetSession(peer, out var session)) return;

    _ = LoadAndApplyAsync(peer, session, packet);   // fire and forget - never block the tick
}

private async Task LoadAndApplyAsync(NetPeer peer, PlayerSession session, C2WMyRequest packet)
{
    // An HTTP round trip to Persistence: when it returns we are on a thread-pool thread.
    var reply = await _persistence.W2PMail.List(session.CharacterId, session.AccountId, countsOnly: true);

    await _players.EnqueueAction(() =>                                    // back on the tick thread
    {
        if (peer.ConnectionState != ConnectionState.Connected) return;   // they may have left meanwhile
        W2CInteractDeniedPacketSender.Send(peer, $"You have {reply.WorldMailCount} letters waiting.");
    });
}

The action queue (WorldActionQueue) is a bounded channel with a single reader (the tick). EnqueueAction waits for space if it's full; it never drops accepted work. TryEnqueueAction returns false instead of waiting. Many managers take _playerManager.EnqueueAction as a constructor argument for exactly this (DoodadManager, GuildManager, MailManager, TerritoryService...).

Rules of thumb:

  • Never block the tick. No .Result, no .Wait(), no synchronous HTTP, no Thread.Sleep. Start the async work and return.
  • Re-check after the hop. The player may have disconnected, the NPC may have died. Look the session up again inside the action.
  • Timers use the Scheduler, not Task.Delay. Scheduler callbacks run on the tick thread, so they may touch anything.
  • Cooldowns are timestamps, not timers. Store "ready at" and compare when the key is pressed.

The Scheduler#

Core/Simulation/Scheduler.cs is the one timer system.

var handle = _scheduler.In(12_000, () => ExpireCorpse(corpse));   // once, in 12 s
_scheduler.Cancel(handle);                                         // looted early
_scheduler.Every(60_000, SweepAuctions, "auction sweep");          // repeating
_scheduler.At(absoluteServerMs, () => StartSiege(id));             // at a ServerClock time

Times are ServerClock milliseconds (monotonic). Resolution is one tick: "in 100 ms" fires on the first tick at or after it's due, never early. Timers are not persisted. Anything that must survive a restart (a siege on Saturday at 20:00, a world event's next start) stores its due time in Persistence (shard_state) and re-schedules on boot. TerritoryService and WorldEventService do exactly this.

Network events#

WorldServer implements INetEventListener:

Event What happens
OnConnectionRequest Rejects payloads over 512 bytes. Reads the connection key string and compares it to ProtocolVersion.ConnectionKey ("Axiom/45"). A different key gets a readable rejection ("Your client is out of date (protocol N, server M)"). Admission control (Admission.ReserveConnection) caps connections per address and in total.
OnPeerConnected Admission bookkeeping. The peer has no PlayerSession yet, so the only packet it may send is Authenticate.
OnNetworkReceive The packet gate. See below.
OnPeerDisconnected PlayerManager.HandlePlayerDisconnected saves the character and despawns it; rate limiter and selection-return state are cleared. With zone threads the clean-up is queued on the owning zone host and rate-limited: at most Performance.DisconnectsPerTick (32) per tick, stopping early after Performance.DisconnectMilliseconds (4 ms; at least one always runs). A mass logout of 1,000 players is spread over about 30 ticks instead of stalling one tick for 300–1,300 ms. Shutdown drains the queue without limits, so nobody is left unsaved.

OnNetworkReceive checks every packet in this order, before any handler sees it:

  1. The peer is still connected.
  2. Traffic budget per peer (PacketRateLimiter.CheckTraffic); persistent floods disconnect.
  3. Size: over PacketSerialization.MaxClientPayload (16 KiB) disconnects.
  4. At least 2 bytes (the opcode).
  5. The opcode is a known client opcode, and the peer has a session (or the opcode is Authenticate).
  6. Busy gate: if this tick already handled Performance.GameplayPacketsPerTick packets or the action backlog is high, the player gets "The server is busy". Movement, spawn acks, cancel-cast, target focus, respawn and selection-return are exempt ("continuation" packets).
  7. Per-opcode token bucket (PacketRateLimiter.Check): drop, or disconnect on sustained flooding.
  8. Payload validation (PacketSerialization.ValidateClientPayload): MessagePack depth ≤ 32, arrays ≤ 1024, maps ≤ 512, ≤ 4096 nodes, no trailing bytes.
  9. PacketDispatcher.Handle calls the handler.

A MessagePackSerializationException (malformed packet) disconnects the client. Any other exception is a handler bug: it's logged with the opcode, the packet is dropped and the player stays connected.

Shutdown#

StopAsync saves everything before dropping a single connection:

  1. Stop the directory heartbeat, NPC AI and navmesh workers.
  2. Cancel the tick loop and wait for it, so nothing else touches sessions during the saves.
  3. Drain every queued action (DrainActions(drainAll: true)).
  4. Park every vehicle that's being driven.
  5. Save territories, treasuries and declared sieges (5 s budget).
  6. Final save of every online character and every character returning to selection (10 s budget, ShutdownSaveTimeout).
  7. Only then stop the socket and dispose the Persistence client.

Close the World server with Ctrl+C, not by killing the process, or step 6 never runs. The autosave (AutosaveIntervalSeconds, 120 s by default) limits what a crash can lose.

Logging#

NLog writes to the console and a rolling file (nlog.config). Every Axiom.* logger logs at Info and above. Change minlevel to Debug there while debugging a system. Each class takes a logger with LogManager.GetCurrentClassLogger().

Useful log prefixes: [Net] (connection and packet problems), [TickLoop] (exceptions inside a tick), [Tick] (pacing), [Movement] (collision and corrections), [Zones], [NavMesh], [Doodads], [Trade], [Shutdown].
