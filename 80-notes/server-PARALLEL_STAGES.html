Server Notes
Feature note, kept next to the code it describes. Source: docs/notes/server/PARALLEL_STAGES.md

Parallel zone stages#

The world still runs one authoritative tick at 20 Hz on one thread. Every rule, every packet handler, every change to game state happens there, in a fixed order. Inside that tick, the three stages that cost the most in a crowd now spread their heavy, read-only work over worker threads:

Stage (TickHealth name) What runs on workers What stays on the tick thread Since
MovementAndAoi: movement Character motor physics, grouped by zone Applying the results, hooks, W2CMovementState before (MovementZoneWorkers)
MovementAndAoi: view range Grid query, pair-range tests, entered/left lists Applying the changes to both sides of each pair, spawn/leave packets this patch
Snapshots Choosing and serializing each observer's datagrams Sending them (LiteNetLib), stats this patch

Why not one thread per zone? A zone thread owning its own players would need every cross-zone thing (chat, parties, guilds, trade, auction, the border between two zones, a player walking across it) to become messages between threads. That is a rewrite of most managers. Parallel stages get most of the CPU win without touching game rules, and the result of a tick does not depend on how many workers ran it.

The rule every parallel stage follows#

  1. Prepare on the tick thread: collect the work, warm any caches.
  2. Compute on workers: reads only. Nothing in the game may change while workers run, and the tick thread waits for them.
  3. Apply/send on the tick thread, in a fixed order.

InterestManager.BeginParallelReads / EndParallelReads bracket phase 2: during it, the read queries (GetKnownBy, IsProtectedForSnapshot, DensityOf, LayerOf...) stop writing their small caches.

If you add a new stage, follow the same rule. If code in a compute phase needs to write, record what it would write and replay it in phase 3 (see InterestManager.Batch.cs, Protects).

Snapshots (SnapshotDispatcher)#

Same rules as before (critical pass first, then up to SnapshotDatagramsPerPeer ordinary rounds, rotation so everyone is served under a tight budget, shared byte budget). Workers claim observers in rotation order; each observer's datagrams go into its own outbox; the tick thread sends every outbox in order afterwards.

Tested against a copy of the old dispatcher: 600 players + 300 NPCs, 40 ticks, 63,983 datagrams and 1.77 M entity updates - byte-identical (0 mismatches old-vs-new, 0 sequential-vs-parallel). On a 2-core test box the build went 20 ms -> 12 ms; on 8+ cores expect much more.

View range (InterestManager.Batch.cs)#

When at least ParallelAoiMinimumMovers players moved this tick, the movement commit loop defers their recomputes:

  1. Mark (DeferUpdate): moves the entity in the grid at once and does the cheap checks UpdatePosition does (fast path, density refresh, recompute budget). If a recompute is due it is queued.
  2. Compute (workers): candidates, pair-range tests, parents, entered and left - against the known set as it is now.
  3. Apply (tick thread, queue order): if the known set has not changed since compute (the common case), the answer is used as-is; if the other side of a pair already applied, old members keep their decision and new members are tested live. Then the symmetric adds/removes, priority marks, and the spawn/leave packets (PlayerMovementBroadcaster.DeliverAwareness).

One difference from the old path: everyone in the batch is compared against this tick's final positions, where the old one-at-a-time path saw earlier movers at their new spot and later movers at their old one. Both are valid; the batch is the more consistent. Pairs can differ only inside the spawn/despawn dead band.

Tested (500 and 1500 players, 300 NPCs, 60 ticks, crowd tiers, parties, cast targets, combat pairs, passengers with parents, budget-limited and unlimited): - 1 worker vs 4 workers: identical known sets (order included) and identical enter/leave event streams. - Replaying the enter/leave events rebuilds every known set exactly: no lost spawn, no double spawn, no leave for something never entered. - Every known pair is symmetric; nothing stays known beyond the despawn range (any more than with the old path).

Speed: about 60% of the recompute cost moves to workers; applying changes stays serial. On 2 cores the gain is small (1500 players: ~8 ms -> ~6 ms); on 8 cores expect roughly half the old AoI time.

Snapshot buffers#

Every datagram of a tick is held until the send phase (~600 at 500 players). ArrayPool<byte>.Shared keeps only about 32 buffers per core, so most were allocated and thrown away every tick: the server's allocation rate doubled after the parallel build (32 -> 64 MiB per 5 s at 500 bots). The dispatcher now rents from its own pool (ArrayPool.Create(1024, 8192), at most 8 MiB). Measured on the 600-player test: 1,527 KiB -> 9 KiB allocated per tick for ~1,550 datagrams, still byte-identical output.

Spawn delivery: backfill scan skip#

SpawnDeliveryQueue.Flush visits every player every tick and checks up to 64 of the entities it knows for two things: a known entity missing from its spawn queue (backfill), or a waiting spawn that became important (promote). It now skips that scan for a player when nothing can come of it: no spawn of theirs is still waiting for an ack, and every entity they know has been checked clean since their known set and their spawn queue last changed (InterestManager.KnownVersionOf, Observer.Version). Result is identical; only the wasted lookups go.

[SpawnWork] (each TickHealth window, last tick; numbers below are an example) shows where the Spawns stage goes:

[SpawnWork] lastTick recipients=500 scansSkipped=470 entitiesScanned=1900 backfills=0 ops=30 scanMs=0.20 queueMs=0.40 sendMs=1.10

scanMs = backfill scan, sendMs = building and sending the spawn packets themselves, queueMs = everything else (the retry queue, budget checks).

Not parallel, on purpose#

  • Spawn delivery (SpawnDeliveryQueue): every operation builds and sends a packet through the replication senders, which are stateful. It is budgeted instead (SpawnMilliseconds, now 6).
  • NPC AI: ~0.2 ms at 500 players. Not worth the risk yet.
  • Packets, actions, timers, world systems: game rules. They stay on the tick thread so the game stays deterministic.

Settings (World.Performance.json, section World:Performance)#

Key Default Meaning
SnapshotWorkers 0 Snapshot build threads. 0 = half the cores, max 8. 1 = single-threaded.
ParallelSnapshotMinimumPlayers 64 Fewer observers than this: built on the tick thread.
AoiWorkers 0 View-range compute threads. 0 = half the cores, max 8.
ParallelAoiMinimumMovers 64 Fewer movers than this: the old immediate path. Set very high (1000000) to turn batching off.
MovementZoneWorkers 0 Movement physics threads (unchanged).
SnapshotMilliseconds 16 Snapshot time cap per tick (wall time).
SpawnMilliseconds 6 Spawn delivery time cap per tick.

World.Performance.json overrides the defaults in CrowdPerformanceOptions. Change the JSON, not just the C# defaults.

Reading the log#

Every TickHealth window adds:

[ParallelStages] movementWorkers=4 movementMs=1.40 aoiBatch=180 aoiWorkers=4 aoiComputeMs=0.90 aoiApplyMs=0.70 snapshotWorkers=4 snapshotBuildMs=3.10 snapshotSendMs=0.60

Values are for the last tick of the window. *Workers=1 means that stage ran on one thread; aoiBatch=0 means view range ran the old immediate way (fewer movers than ParallelAoiMinimumMovers, or nothing needed a recompute). snapshotBuildMs should sit well under SnapshotMilliseconds; if snapshotBudgetHit=true still appears in [CrowdWork], the byte budget (SnapshotBytesPerTick) is the limit, not CPU.
