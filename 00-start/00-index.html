Axiom Engine Documentation#

Axiom is a foundation for an sandbox MMORPG: seamless open-world shards with no loading screens, instanced dungeons, world events, housing and farming, trade packs, crafting, factions and sieges. It is a set of .NET 10 servers and a Unity client that share one networking and movement library.

This documentation was written from the current source code of both the server solution (AxiomCore) and the Unity client (Axiom.Client). It explains how every part works, where every piece of data lives, how to use the tools, and how to extend each system with real code.

🚀Quick startInstall, configure the databases and secrets, start the four servers and log in from Unity. 🏛ArchitectureThe five programs, how they talk, who owns which data, and how a session flows end to end. 🗃worldserver.dbThe SQLite content database: migrations, SQL patches, every table family. 🐬MySQL databasesAccounts, player state and auctions: setup, tables and admin tasks. 📦gamedata.binThe encrypted client content package: layout, encryption, download and loading. 📡NetworkingLiteNetLib, opcodes, MessagePack packets, channels, protocol versions. 🧪CookbookAdd a packet, a system, a table, a saved field, content, a UI window, a Lua script, a zone… 🛠ToolsThe Unity Axiom menu: Content Studio, Create wizards, Dev Tools, exports, validation. 📚ReferenceGenerated: every opcode, endpoint, table, column, config option, menu item and source file.

The ten things to know first#

  1. The World server is the game. Clients only send intentions; every rule, roll and position is decided on the server (World server).
  2. Everything that touches game state runs on the tick thread. After an await, hop back with PlayerManager.EnqueueAction (threading rule).
  3. Content is data. Items, NPCs, skills, loot, quests and doodads are rows in worldserver.db, edited with Content Studio and versioned as SQL patches (worldserver.db).
  4. Player state is saved as whole snapshots through the Persistence server, ordered by a save sequence number, so nothing is ever half-saved or duplicated (Persistence flow).
  5. Server and client share code. Axiom.Network.dll (packets) and Axiom.Movement.dll (the movement simulation) are built once and copied into Assets/AxiomMMOKit/Plugins. Rebuild and copy after every change.
  6. Movement is server-authoritative with prediction. Both ends run the same motor on the same exported collision (Movement).
  7. World geometry is exported from Unity into files the server reads: collision, heightmaps, zones, navmesh (World files).
  8. Bump the protocol version when packets change, so old clients are refused with a clear message (Networking).
  9. One shared secret authenticates the World server to Auth, Persistence and Auction; it must be identical in all four configs (Configuration).
  10. The Axiom menu in Unity is the front door to every tool: start at Tools ▸ Axiom ▸ Home (Tools).

├── src/
│   ├── Servers/
│   │   ├── Axiom.Server.World/     the game server (UDP 7777)
│   │   ├── Axiom.Server.Auth/      accounts, login, world list, gamedata.bin (HTTP 3000)
│   │   ├── Axiom.Server.Persistence/  player data in MySQL (HTTP 7778)
│   │   └── Axiom.Server.Auction/   auction house (HTTP 5090)
│   ├── Shared/
│   │   ├── Axiom.Network/          opcodes, packets, rules            → DLL copied to the client
│   │   ├── Axiom.Movement/         character motor, collision, terrain → DLL copied to the client
│   │   ├── Axiom.Navigation/       navmesh format and baking
│   │   └── Axiom.Plugins.Api/      the C# server plugin contract
│   ├── Tools/                      Axiom.LoadTest (bot fleet), Axiom.Tools.NavBake (navmesh baker)
│   ├── Plugins/                    Axiom.SamplePlugin
│   └── Tests/                      Axiom.Server.World.Checks
├── scripts/                        build and launch .bat files, Build.Docs.bat, MySQL helpers, docs/ (the docs generator)
├── docs/                           this documentation, as Markdown
