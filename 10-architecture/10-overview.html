Architecture

Architecture Overview#

Axiom is five programs plus a few databases. Learn this page well; every other page assumes it.

The five programs#

Program Project Talks Owns Port
Unity client Assets/AxiomMMOKit/Axiom.Client LiteNetLib to World, HTTP to Auth Nothing authoritative. Renders, predicts movement, sends intentions. —
Auth server src/Servers/Axiom.Server.Auth HTTP + JSON Accounts, passwords, sessions, refresh tokens, bans, access levels, the list of worlds. Serves gamedata.bin. 3000
World server src/Servers/Axiom.Server.World LiteNetLib (UDP) to clients, HTTP to the others All game rules and live state. One process = one shard. 7777
Persistence server src/Servers/Axiom.Server.Persistence HTTP + MessagePack, World only Characters, inventories, quests, guilds, mail, placed doodads, shard state, cash shop, community. 7778
Auction server src/Servers/Axiom.Server.Auction HTTP + MessagePack, World only Auction listings and bids. Mails proceeds through Persistence. 5090

Plus tooling: Axiom.LoadTest (bot fleet), Axiom.Tools.NavBake (offline navmesh bake) and the Unity editor suite under Assets/AxiomMMOKit/Editor (Tools).

Shared libraries#

The same C# is compiled into the server and the client, so both sides agree by construction instead of by convention.

Library Target Used by Contents
Axiom.Network netstandard2.1 every server, client (as DLL) Opcodes, every packet class, shared enums and rules, serialisation, dispatchers. Networking
Axiom.Movement netstandard2.1 World, client (as DLL), LoadTest The CharacterMotor: the exact same movement simulation runs on the client (prediction) and the server (authority). Collision world, terrain heightmaps, water volumes. Movement
Axiom.Navigation net10.0 World, NavBake Navmesh tile format and baking (DotRecast). Navigation

Where data lives#

Data Store Written by Read by Page
Game content (items, NPCs, quests, skills, loot, doodads, zones...) worldserver.db (SQLite) Content Studio, wizards, SQL patches World server at boot worldserver.db
Client copy of content gamedata.bin (encrypted) World server at boot (ClientContentExporter) Unity client gamedata.bin
Accounts and sessions MySQL axiom_auth Auth Auth MySQL
Player state (characters, items, quests, guilds, mail...) MySQL axiom_persistence Persistence (on World's request) Persistence MySQL
Auctions MySQL axiom_auction Auction Auction MySQL
World geometry (heightmaps, collision, zones, navmesh) files in the World server's Data/ folder Unity editor exports World server World files
Art (models, textures, scenes) Unity project artists client only Art & assets

The split is deliberate:

  • Content is read-only at runtime and lives in a single SQLite file next to the World server. It's versioned with the code (SQL patches in git), can be diffed, and loads in milliseconds. Changing content means editing the db and restarting the World server.
  • Player state is written constantly and must survive a World crash, so it lives in MySQL behind its own service. The World server never opens a MySQL connection. That keeps the tick thread free of database latency and lets several World shards share one Persistence server later.

Who trusts whom#

client ──(untrusted)──▶ World ──(x-internal-secret)──▶ Auth / Persistence / Auction
  • The client is never trusted. It sends intentions ("use slot 4", "my inputs for ticks 812–815"). The World server validates and simulates everything, including movement.
  • The World server authenticates to the other services with one shared secret in the x-internal-secret header (World:InternalSecret = Auth's Auth:InternalSecret = Persistence's InternalSecret = Auction's Persistence:InternalSecret). It's compared in constant time. If they differ, nothing works: see Configuration.
  • Persistence and Auction should never be reachable from the internet. Auth must be (the launcher and client call it).

One player's session, end to end#

  1. Launcher → Auth POST /login (or /session/launch-token with a remembered refresh token): returns a one-shot launch token valid for 120 s.
  2. The launcher starts the game with -token <token>.
  3. Client → Auth GET /worlds: the world list (each World server heartbeats into Auth every 5 s).
  4. Client → World connects over UDP with key Axiom/45, sends Authenticate { Token }.
  5. World → Auth POST /validate-session: the token is burned and the account id and access level come back.
  6. World → Persistence /characters/list; World sends W2CCharacterList.
  7. Player picks a character: World → Persistence /characters/load; World builds a PlayerSession, spawns it, sends W2CEnterWorld plus catalogues.
  8. The client loads main_world, then plays. Every 50 ms the World server simulates, and sends snapshots.
  9. Changes mark the session dirty; autosave sends World → Persistence /characters/save-full every 120 s and on logout.

Each step is detailed in Login & world entry.

Scaling model#

One World process runs one shard: a seamless open world with no loading screens, plus instanced dungeons (each on its own thread). Inside the process:

  • the world is a grid of tiles (WorldGrid.TileSize), and zones (named regions) are painted on top of it;
  • an interest grid decides which entities each player sees (Interest & replication);
  • movement and interest updates run in parallel per zone; everything else is on the single tick thread (World server);
  • NPCs sleep until a player is close.

More players means more World processes (more shards), all registering with one Auth and sharing one Persistence and one Auction. Each shard has its own ShardName and WorldDirectory:Id.
