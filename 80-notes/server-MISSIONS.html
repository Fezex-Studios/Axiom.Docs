Feature note, kept next to the code it describes. Source: docs/notes/server/MISSIONS.md

Guild and Family Missions#

Guilds and families have a level, XP and (guilds only) Prestige. Members earn them by completing missions. Higher levels unlock perks: more mission slots, more Change Mission attempts, a bigger guild member cap, and better buffs for every member (see GUILD_RECRUITMENT.md).

Individual missions Group missions
Who each member has their own shared by the whole guild/family
Drawn every day (daily reset) every week (weekly reset)
Counts what that member does what every member does, on any zone host
Change Mission the member, using a daily attempt (3 at level 1) the leader only: a guild pays Prestige, a family uses a daily attempt
Personal reward straight into the bag (by mail when it's full) mailed to every member who contributed

Missions arrive sealed (the "?" cards). Opening one (click it, or Open All) starts it counting. Leaving a guild or family clears your individual missions for it.

What counts#

Kind Counts TargetId
1 Kill Npc an NPC you attacked dies NPC template (0 = any)
2 Complete Quest a quest turned in quest (0 = any)
3 Earn XP XP points actually awarded —
4 Harvest items gathered from doodads (per item) item (0 = any)
5 Craft items crafted (per item) item (0 = any)
6 Spend Labor labor points spent —
7 Use Item an item used item (0 = any)
8 Donate Item items handed in with the card's Donate button item (required)
9 Trade Pack Sold a trade pack delivered pack item (0 = any)

Progress comes from the same game events quests and achievements use (LuaEngine.EventFired), so anything that fires them counts - including Lua scripts that call the same paths. Three events were added for this: OnQuestComplete (28), OnXpGained (29), OnLaborSpent (30).

Authoring#

Edit the tables in Content Studio (or SQL) and restart the world server.

Missions - Id, Owner (0 guild, 1 family), Scope (0 individual, 1 group), Name, Description, Kind, TargetId, Count, MinLevel (first level it can be drawn at), Weight (relative chance in its pool; 0 = never), RewardOrgXp, RewardPrestige (guilds only), RewardGold (copper), RewardItemId + RewardItemCount, IconItemId (the card's icon; 0 = the emblem), Enabled.

OrganizationLevels - one row per Owner + Level: XpToNext, MaxMembers (guilds; 0 = the GuildMaxMembers rule), IndividualSlots, GroupSlots, ChangeAttempts, XpBonusPct (ignored once the OrganizationBuffs table exists - the buffs replace it), Perks (the text members see). Levels must run 1, 2, 3... with no gaps; the top level's XP isn't used.

Bad rows are skipped with a warning in the world server log ([Missions] Mission 1234 ... skipped: ...), never a crash. Without the tables (an older database) missions are simply off.

The seed gives guilds 10 levels (100 → 150 members), families 5 levels, 15 guild missions and 9 family missions. Donation missions use Iron Ingot (40) and Lumber (41); change them if your item ids differ.

Rules (CombatRules table)#

Rule Default
MissionsEnabled 1 0 turns missions off (the pages say so)
MissionResetHourUtc 0 the daily reset hour, UTC
MissionWeeklyResetDay 0 the weekly reset day (0 Sunday … 6 Saturday), at that hour
MissionGroupChangePrestige 50 Prestige a guild leader pays to change a group mission

How state is kept#

The registry is in memory for the whole shard and the home host saves what changed every ~10 seconds (and at shutdown) to the persistence server's existing shard_state table - no persistence change was needed:

  • kind mission_org, key g:<guildId> / f:<familyId>: level, XP, Prestige, this week's group missions with every member's contribution, the family's change attempts;
  • kind mission_char, key <characterId>: that character's daily missions and change attempts.

Until the saved state is read at start, nothing counts and the pages say "loading", so a slow persistence server can't wipe progress. Daily rows older than yesterday are deleted at start. Reward mail is sent with an idempotency key, so a retry never pays twice.

Checks#

Tests/Axiom.Server.World.Checks runs the migration's SQL into an in-memory database and checks the seed loads, the reset clock, drawing, counting, level-ups, change attempts, donations, group contributions, day/week rollover and the save/restore round trip (dotnet run).
