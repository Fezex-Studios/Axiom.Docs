Architecture

Networking & Packets#

The game client and the World server talk over LiteNetLib (reliable UDP). Every other link in Axiom is HTTP (see Architecture overview). This page covers the game protocol: what a packet is, how it travels, how it's dispatched, and the rules that keep both ends compatible.

The shared library: Axiom.Network#

Both ends compile against the same packet definitions: src/Shared/Axiom.Network, a netstandard2.1 class library.

  • The servers reference the project directly.
  • The Unity client uses the built DLL: Axiom.Network.dll (and Axiom.Movement.dll) copied into Assets/AxiomMMOKit/Plugins.

Every time you change anything in Axiom.Network or Axiom.Movement, rebuild and copy both DLLs into Assets/AxiomMMOKit/Plugins. A client with an old DLL either gets refused at connect (if you bumped the protocol version) or fails to read packets with Could not read X packet (Axiom.Network.dll out of date?).

Folder Contents
Shared/Opcodes.cs enum Opcodes : ushort: every client↔world message number
Shared/Packets/C2W, W2C Client→World and World→Client packet classes
Shared/Packets/W2P, P2W World→Persistence and Persistence→World request/response classes (HTTP bodies)
Shared/Packets/*.cs DTOs shared by several packets (InventorySlotDto, GuildDto, MarketDtos, ...)
Shared/{Combat,Housing,Items,...} Shared enums and rules both ends must agree on (EquipSlot, CharacterNameRules, housing layouts...)
Shared/PacketChannels.cs Which LiteNetLib channel each opcode uses
Shared/PacketSerialization.cs MessagePack options, client payload limits, pooled writers

The full list of opcodes and packet fields is generated from the code: see the Packet reference.

What a packet is on the wire#

Every message is:

┌────────────┬───────────────────────────────────────────┐
│ ushort     │ MessagePack payload (array of [Key(n)])   │
│ opcode LE  │                                           │
└────────────┴───────────────────────────────────────────┘

LiteNetLib frames the message, so there's no length prefix. The payload is the packet class serialised by MessagePack-CSharp 3.1.12 with integer keys:

// Axiom.Network/Shared/Packets/C2W/...
[MessagePackObject]
public class C2WUseItemPacket
{
    [Key(0)] public int Slot;
}

Keyed by integer, a packet is a MessagePack array: field names never travel. That has two consequences:

  • Never renumber or reuse a key. Key 3 means "Health" forever. To retire a field, leave its number unused.
  • Adding a field at the end is cheap. An older reader ignores extra array entries; a newer reader sees a missing trailing key as the default. That's the only change that is safe without a protocol bump, and you should still bump it if the field matters.

Two packets skip MessagePack because they're sent constantly:

Opcode Format Why
C2WMovementInputs (167) MovementInputCodec: uint epoch, byte count, then count × 22 bytes: uint sequence, float wishX, float wishZ, float yaw, float pitch, ushort buttons. At most 16 commands per packet. Sent every client frame batch; must be tiny and allocation-free.
W2CWorldSnapshot (30) SnapshotWriter / SnapshotReader: header opcode(2) tick(4) origin(12) count(2), then per entity id(4) flags(1) pos(6, 1/64 m) yaw(1) state(1), optionally velocity(3) and tilt(2) (flags say which). 200 000 packets/s at target load; MessagePack's per-field overhead and allocations would dominate.

Snapshots are unreliable and may arrive out of order: the client keeps the highest tick per entity and drops older ones. An entity missing from a snapshot has not despawned (it's on a slower level-of-detail tier, or past the packet cap). Despawns only ever arrive reliably (PlayerLeave, NpcDespawn).

Channels#

LiteNetLib orders reliable messages per channel. With everything on one channel, a big auction page that needed a resend would hold up every combat hit behind it. So PacketChannels.For(opcode) puts each opcode on one of four channels:

Channel Number Carries
World 0 Everything not listed below: spawns, despawns, combat, gold, inventory, enter-world. Order matters here. New opcodes land here by default.
Bulk 1 Windows and lists: auction, mail, cash shop, shop catalogues, quest catalogue/log, gear/status/skill catalogues, character list, guild state, crafting, storage, achievements.
Chat 2 Chat, MOTD, announcements.
Control 3 Movement inputs, movement state and config, spawn acks, NPC collision frames, focus target.

Both NetManagers must be created with ChannelsCount = PacketChannels.Count (4), or messages on the extra channels are dropped. WorldserverPacketSender.SendPacket and ClientPacketSender.SendPacket pick the channel for you.

If your new packet is a large list that should never delay gameplay, add it to the Bulk case in PacketChannels.For.

Sending#

Server → client. Each outbound packet has a static sender in Axiom.Server.World/Core/Packets/W2CSenders. It's a one-liner over WorldserverPacketSender:

public static class W2CItemCooldownPacketSender
{
    public static void Send(NetPeer peer, int[] itemIds, int durationMs) =>
        WorldserverPacketSender.SendPacket(peer, Opcodes.W2CItemCooldown,
            new W2CItemCooldownPacket { ItemIds = itemIds, DurationMs = durationMs });
}

WorldserverPacketSender has SendPacket (one peer), SendToAll (serialises once, then sends the same bytes to every peer; use it for broadcasts), Encode + SendEncoded (serialise once, send later). Writers come from a thread-static pool (PacketSerialization.Rent), so sending doesn't allocate. Outgoing packets are capped at 4 MiB.

Client → server. Each outbound packet has a static sender in Assets/AxiomMMOKit/Axiom.Client/Networking/C2WSenders:

public static class C2WAuthenticatePacket
{
    public static void Send(NetPeer peer, string token) =>
        ClientPacketSender.SendPacket(peer, Opcodes.Authenticate,
            new C2WAuthenticateRequest { Token = token });
}

// Anywhere in the client:
var peer = ClientNetwork.Instance.ServerPeer;
if (peer != null) C2WAuthenticatePacket.Send(peer, token);

Default delivery is ReliableOrdered. Use DeliveryMethod.Unreliable or Sequenced only for data that's replaced by the next send anyway.

Receiving and dispatch#

On the server: attribute + reflection#

A handler is a class with [PacketOpcode] that implements IPacketHandler:

[PacketOpcode(Opcodes.C2WUseItem)]
public class C2WUseItemHandler : IPacketHandler
{
    private readonly PlayerManager _playerManager;
    private readonly ItemManager _items;

    // Exactly ONE public constructor. Every parameter is resolved from the ServiceContainer.
    public C2WUseItemHandler(PlayerManager playerManager, ItemManager items)
    {
        _playerManager = playerManager;
        _items = items;
    }

    public void Handle(NetPeer peer, NetPacketReader reader)
    {
        var packet = MessagePackSerializer.Deserialize<C2WUseItemPacket>(reader.GetRemainingBytesMemory());
        if (!_playerManager.TryGetSession(peer, out var session) || session.CharacterId <= 0) return;
        // ... validate EVERYTHING, then act
    }
}

At boot, PacketDispatcher.AutoRegister scans the World assembly for every non-abstract IPacketHandler, reads the attribute, resolves the constructor parameters from the ServiceContainer and registers one instance. A handler without the attribute is skipped with a warning; a handler with two constructors or an unregistered dependency fails start-up. Several handlers may live in one file (C2WSocialHandlers.cs, C2WMarketHandlers.cs...).

Handlers run on the tick thread, one at a time. The World server page lists the nine checks every packet passes before its handler runs (size, rate limits, known opcode, session, payload complexity).

On the client: manual registration#

Client handlers implement IClientPacketHandler and are registered by hand in ClientNetwork.RegisterHandlers():

dispatcher.Register(Opcodes.W2CItemCooldown, new W2CItemCooldownHandler());

public class W2CItemCooldownHandler : IClientPacketHandler
{
    public void Handle(NetPacketReader reader)
    {
        var packet = MessagePackSerializer.Deserialize<W2CItemCooldownPacket>(reader.GetRemainingBytesMemory());
        // Runs on Unity's main thread (ClientNetwork.Update -> PollEvents). Safe to touch GameObjects.
    }
}

ClientPacketDispatcher.AutoRegister exists and works, but the client doesn't call it. Forget the Register line and the packet is silently dropped, apart from [ClientPacketDispatcher] Unhandled packet: X in the console.

Handlers that touch world objects (spawning players, NPCs, doodads) must not act directly while main_world is still loading. They call WorldLoader.RunWhenReady(() => ...), which queues work in arrival order until the scene and its registries exist. See Client networking.

The client also filters by state: while in character selection it only accepts the character list, create-failed, selection-return, MOTD, announcements, account access and movement configuration; everything else is ignored.

Limits and protection#

Limit Value Where
Max client packet 16 KiB PacketSerialization.MaxClientPayload
MessagePack depth / nodes 32 / 4096 ValidateClientPayload
Array / map length 1024 / 512 ValidateClientPayload
Max outgoing packet 4 MiB PacketSerialization.Writer
Connection request payload 512 bytes OnConnectionRequest
Per-opcode rate token bucket Core/Security/PacketRateLimiter.cs, configured from World:Performance
Gameplay packets per tick Performance.GameplayPacketsPerTick busy gate in OnNetworkReceive

The server deserialises untrusted data with MessagePackSecurity.UntrustedData. Treat every field as hostile: check slot indices are in range, counts are positive, ids exist, the player is close enough, owns the item, isn't dead, isn't trading. The handlers in C2WHandlers show the pattern: look the session up, validate, then call a manager that validates again.

Protocol versions#

ProtocolVersion.Current is part of the LiteNetLib connection key: the client connects with "Axiom/46". The server compares the key exactly. An older or newer client is refused at connect with a message the player can read ("Your client is out of date (protocol 43, server 44). Update the game.") instead of connecting and failing on its first packet.

Bump Current and ConnectionKey together whenever opcodes, packet fields, channels or encodings change in a way the other side can't read, and add a line to the history comment above it. Then rebuild Axiom.Network.dll and copy it to the client.

The other protocols#

Link Transport Format Auth
Client → Auth HTTPS/HTTP (port 3000) JSON login → access + refresh tokens
Client → Auth /gamedata/* HTTP binary file none
World → Auth HTTP JSON x-internal-secret header
World → Persistence HTTP (port 7778) MessagePack bodies (W2P* / P2W* classes) x-internal-secret

Every route is listed with its request and response types in Service endpoints. How the World server uses them is on Persistence flow.

Checklist: adding a packet#

The Add a packet recipe walks through a complete example. In short:

  1. Opcode in Opcodes.cs, the next free number, with a comment.
  2. Packet class in Shared/Packets/C2W or W2C: [MessagePackObject], [Key(n)] fields.
  3. Channel in PacketChannels.For if it isn't World.
  4. Server: handler ([PacketOpcode], one constructor) or sender (W2CSenders).
  5. Client: sender (C2WSenders) or handler, plus its dispatcher.Register line.
  6. Bump ProtocolVersion, rebuild Axiom.Network.dll, copy it to Assets/AxiomMMOKit/Plugins.
