Architecture

Login & World Entry#

This page follows one player from the launcher to the world, naming the code that runs at each step. When login breaks, find the last step that worked.

The tokens#

Axiom never sends the password to the game client or the World server. Three kinds of token exist:

Token Issued by Lives Used for
Refresh token Auth /login 30 days unused (Auth:RefreshTokenDays), replaced on every use What a launcher remembers instead of the password. Traded for a launch token.
Launch token Auth /login, /session/launch-token, /worlds/selection-token 120 s (Auth:LaunchTokenSeconds), one use Passed to the game (-token) and redeemed by the World server.
Session (the launch token is the session row) until redeemed or expired sessions table in axiom_auth; one row per account (REPLACE INTO kills any older one).

A launch token is a bearer credential: whoever holds it is that account until it's used. The World server never logs it.

Step 1: log in (launcher → Auth)#

POST http://127.0.0.1:3000/login
Content-Type: application/json

{ "username": "aidan", "password": "hunter2" }

{ "success": true, "token": "6f1c…", "refreshToken": "a93e…", "username": "aidan" }

Endpoints/LoginEndpoint.cs:

  1. Per-address lockout (LoginThrottle, in memory): 5 failures (MaxLoginAttempts) for one username from one IP lock that pair for 15 min (LockoutMinutes). Typing someone else's name doesn't lock them out everywhere.
  2. Account-wide lockout (failed_logins table): 50 failures from anywhere (AccountLockAttempts) lock the account everywhere.
  3. Password check with BCrypt. For an unknown username it still burns a hash (PasswordService.BurnTime) so response time doesn't reveal which names exist; the message is identical either way.
  4. Ban check, only after the password is right (so bans can't be probed).
  5. REPLACE INTO sessions (token, account_id, expires_at): a new launch token, killing any previous session for the account in one atomic statement.
  6. A new refresh token (RefreshTokens.IssueAsync).

The route is rate-limited (auth-strict policy in Program.cs). POST /register creates an account (username/password rules in RegisterEndpoint.cs).

A launcher that remembers the login calls POST /session/launch-token { refreshToken } instead: it returns a fresh launch token and a replacement refresh token (the old one is revoked). POST /logout { refreshToken } revokes it.

Step 2: start the game with the token#

The launcher runs the client with the token on the command line:

Axiom.Client.exe -token 6f1c... [-auth-url http://my-auth:3000]

ClientNetwork.Awake → ReadCommandLineToken() stores it in SessionManager.Token (client, Scripts/SessionManager.cs). WorldDirectoryClient reads -auth-url (default http://127.0.0.1:3000).

Testing in the Unity editor. There's no launcher in the editor. Select the ClientNetwork object and fill in Editor Login in its Inspector: username, password, Auth server (default http://127.0.0.1:3000), and Log in when I press Play (on by default). Pressing Play then calls /login first and hands the fresh launch token to that session (ClientNetworkEditorLogin, Editor/Project/ClientNetworkLoginInspector.cs); the token is passed through the editor's session store, so nothing is written to the scene. Log in now fills the Editor Token field instead. The login's refresh token is revoked straight away, so Play sessions don't pile up 30-day tokens. Errors (Auth down, wrong password, 429 after 5 logins a minute) show under the button and in the Console, and Play goes on with whatever Editor Token holds.

The username and password are kept in EditorPrefs on that machine, per Unity project, never in the scene; EditorPrefs is plain text, so use a test account. A ParrelSync clone is its own project, so each clone can log in as a different account. Without Editor Login, paste a token into Editor Token by hand (valid 120 s, one use):

powershell (Invoke-RestMethod -Method Post http://127.0.0.1:3000/login -ContentType application/json ` -Body '{"username":"aidan","password":"hunter2"}').token | Set-Clipboard

scripts/Client.Launcher.bat shows the built-client equivalent.

Step 3: the world list (client → Auth)#

The server-select screen (ServerSelectUI) polls GET /worlds through WorldDirectoryClient. The answer comes from WorldDirectoryRegistry in Auth:

  • Worlds are configured in Auth's WorldDirectory:Worlds (Auth.WorldDirectory.json): id, name, host, port, restrictions, maintenance flag, max characters.
  • Each World server heartbeats POST /worlds/heartbeat every WorldDirectory:IntervalSeconds (5 s) from WorldDirectoryReporter with its Id, public host/port, population. A world that hasn't beaten for StaleAfterSeconds (25 s) shows offline.
  • GET /worlds/characters (with Authorization: Bearer <launch token>) returns how many characters the account has on each world, without redeeming the token.

The World's WorldDirectory:Id must match an entry in Auth's list, and PublicHost/PublicPort is what clients are told to connect to. Don't put 0.0.0.0 there.

Step 4: connect and authenticate (client → World → Auth)#

ServerSelectUI.Connect() → ClientNetwork.Connect(host, port):

  1. Refuses if there's no unused token ("Start the game from the launcher to log in").
  2. Creates the NetManager with 4 channels, resets every per-world client state, and connects with key ProtocolVersion.ConnectionKey ("Axiom/45").
  3. On OnPeerConnected it sends Authenticate { Token } and marks the token used.

On the World server:

  • OnConnectionRequest checks the key (World server) and admission limits.
  • C2WAuthenticateHandler: ignores a peer that already has a session; AuthThrottle stops a peer from hammering; Admission.BeginAuthentication caps concurrent logins (MaxPendingAuthentications), else "Login is busy".
  • AuthService.ValidateAccount(token) → Auth POST /validate-session with x-internal-secret. Auth deletes the session row (atomically, so two peers can't redeem one token), checks expiry and that access_level is 1–5, and returns { valid, accountId, accessLevel }.
  • Invalid → disconnect. Valid → Persistence /characters/list.
  • Back on the tick thread: TrackPendingSelection(peer, accountId, accessLevel) and send W2CCharacterList, which carries the roster plus everything character creation needs: playable factions, classes, races, body types and appearance options (all from worldserver.db, so adding a race is data, not code).

A peer that never authenticates is dropped after Performance.AuthenticationTimeoutSeconds (30 s).

Step 5a: create a character#

Client CharacterCreateUI → C2WCreateCharacterRequest { Name, ClassId, FactionId, RaceId, GenderId, Appearance } (opcode 15).

C2WCreateCharacterHandler validates everything again: CharacterNameRules.IsValid, CharacterClassRules.IsValid, the faction is playable, CharacterRaceRules.IsValidChoice (race allowed for that faction and gender), and AppearanceRules.Sanitize clamps the customisation values. Failures send W2CCreateCharacterFailed { Reason } and the player stays on the screen.

Then Persistence /characters/create inserts the row (unique name is enforced there, per shard), and the new character goes straight into world entry with isNewCharacter: true (saved once right after spawning).

Step 5b: select a character#

C2WSelectCharacter { CharacterId } → C2WSelectCharacterHandler:

  1. The peer must have a pending selection (authenticated, not in world).
  2. TryBeginSpawn: one spawn per connection. A double-clicked "Enter World" can't spawn twice.
  3. PlayerManager.PrepareLoginAsync: kicks this account's other session if any, and waits for every save of this character to land (up to 20 s, LoginSaveWait). Loading before the last save finished is how relogging used to restore items that had just been sold.
  4. Persistence /characters/load (filtered by account and character id, so you can't load someone else's).
  5. HandlePlayerConnected queues the world entry.

Step 6: world entry (World)#

Entries are processed a few per tick (Performance.EntriesPerTick) by PumpWorldEntries, so 500 people logging in at once can't stall the world. PlayerSpawnManager.HandlePlayerConnected then:

  1. Re-checks the peer is connected and not already spawned; resolves duplicate logins.
  2. Refuses a stale load (IsLoadCurrent: a newer save already landed).
  3. Validates the loaded data (class, warehouse, inventory capacity).
  4. Sends the MOTD, builds the PlayerSession (SpawnPlayer): inventory, equipment, abilities, labor, proficiency, quests, faction, achievements, dungeon entries. If they logged out inside a dungeon that's still open, they go back into it.
  5. Recalculates stats (health and mana start full; they're not saved).
  6. Sends, in this order:
Packet Why
W2CSpawnPlayer (self) your network id and position
W2CEnterWorld name, level, class, race, gold, full inventory, health, and WorldSettingsData: shard name, tile size, interest radii, tick rate, zone map hash, content hash
catalogue packets (cached, pre-encoded) item gear catalogue, status catalogue, skill catalogue: definitions the HUD needs
abilities, equipment, stats, progression, health this character's state
professions, patron, instances, trade packs, PvP, exploration, achievements, quests each system's SendOnEnterWorld
W2CSpawnPlayer / NPC spawns everything already within the interest radius
  1. Party, guild, family and GM state are restored; Lua OnConnect fires.

Step 7: the client loads the world#

On the client, W2CEnterWorldHandler applies WorldSettings and caches the character in LocalCharacterState (the HUD doesn't exist yet, so events are replayed once it does). The spawn handlers call WorldLoader.RunWhenReady(...); the first call starts loading main_world (the only place that loads it), and every world-object packet that arrives meanwhile is queued and run in arrival order once the scene and its registries exist.

ZoneTracker compares ZoneMapHash with the client's own zones.aczmap; a mismatch logs a warning (your client's zone map is older or newer than the server's). ContentHash/ContentMustMatch are sent too, but the client doesn't compare them yet: keep gamedata.bin in sync yourself, or add the check in W2CEnterWorldHandler (gamedata.bin).

Details: Client networking, World streaming.

Returning to character select#

C2WSelectionReturn { TargetWorldId } → CharacterSelectionReturnService. The character is despawned and saved, in order, while the connection stays open. When the save lands, the player gets the roster again (same world) without logging in again.

Switching worlds#

C2WSelectionReturn with another world's id: after the save, the World server asks Auth for a ticket, POST /worlds/selection-token (internal secret, AccountId, WorldId, TargetWorldId). Auth checks both worlds are registered and the target is available, then mints a 30–300 s launch token. The client gets it, disconnects (ClientNetwork.BeginWorldSwitch) and connects to the other world with it (CompleteWorldSwitch). The launcher's refresh token never touches the game.

Logging out and disconnects#

On disconnect (OnPeerDisconnected) the World server fires Lua OnDisconnect, saves the character (CleanupPeer(save: true)), despawns it for everyone who could see it (W2CPlayerLeave), and keeps party membership for a grace period. The next login waits for that save (step 5b.3).

When it fails#

Symptom Likely cause
"You need to log in again" / "Your session has ended" The token was already used or expired (120 s). Get a new one.
Connection refused, "client is out of date" Client DLL protocol ≠ server's. Copy the new Axiom.Network.dll.
Disconnected immediately after connecting Token invalid (World log: Invalid or expired token), or World can't reach Auth / secrets differ (Auth log: bad or missing x-internal-secret).
World shows offline in the list World's heartbeat isn't reaching Auth: WorldDirectory:Id not in Auth's Worlds, wrong World:AuthServerUrl, or secrets differ.
Character list never arrives Persistence down (World log: Failed to fetch character list).
Stuck after selecting a character PrepareLoginAsync waiting for a save; or Persistence load failed (World log [SelectCharacter]).
"Login is busy" MaxPendingAuthentications concurrent logins in flight.
