Architecture

Interest & Replication#

A seamless world can't send everything to everyone. Three systems decide who hears about what:

System File Answers
Interest Core/Interest/InterestManager*.cs, Spatialgrid.cs Which entities is each player aware of?
Spawn delivery Core/Interest/SpawnDeliveryQueue.cs Has the client created each of those entities yet?
Snapshots Replication/SnapshotDispatcher.cs, SnapshotWriter.cs Where is everything now?

Entity ids#

Every replicated thing has an int network id in one shared id space:

Range Kind
1 … 999 999 players (PlayerSpawnManager)
≥ 1 000 000 (SpawnManager.NpcIdBase) everything else: NPCs, doodads, corpses/ground loot, mounts, vehicles

SpawnManager.IsNpcId(id) means "not a player". Only players observe; NPCs, doodads and corpses are only observed. Two mobs never track each other, which keeps a camp of 30 mobs next to 50 ore nodes from costing O(n²).

Interest: a circle with a dead band#

InterestManager keeps, for every entity, the set of players aware of it, and for every player, the set of entities they know.

  • Broad phase: a uniform SpatialGrid (50 m cells). It cheaply answers "what might be close".
  • Narrow phase: real distance. Awareness starts inside SpawnRadius (75 m) and ends outside DespawnRadius (85 m). The 10 m gap stops something on the edge from strobing in and out every tick.
  • Recompute when an entity crosses a cell or has moved RecomputeThreshold (5 m) since its last recompute.
  • Layers: every entity is in exactly one layer. Layer 0 is the open world; each dungeon instance and each house interior is its own layer with its own grids. Two parties in two copies of the same dungeon, standing on the same spot, never see each other. SetLayer drops all awareness and returns who lost it so the caller sends despawns.
  • Dynamic AoI (InterestManager.Density.cs): in very crowded places the player radius shrinks: 60 m above 128 nearby players, 45 m above 256, 30 m above 512 (Performance.DensityTier*, *PlayerRadius). NPCs and objects keep the full radius.
  • Parallel recompute (InterestManager.Batch.cs): distance checks for players who moved run on worker threads; the resulting enters/leaves are applied on the tick thread, in order.

The radii go to the client in WorldSettingsData on world entry, so its culling matches.

When an entity enters someone's interest, a spawn is queued for them; when it leaves, a despawn is sent (W2CPlayerLeave, W2CNpcDespawn, W2CDespawnDoodad, ...). Despawns are always reliable. Nothing despawns by silence.

Spawn delivery: create, then baseline, then snapshots#

Creating an entity on a client is a small handshake, so a snapshot never refers to an entity the client doesn't have yet:

stage 0  server ─ W2CSpawnNpc { Generation, BirthTick, Baseline = false } ─▶ client creates the object
         client ─ C2WSpawnAck { id, Generation, Baseline = false } ─▶
stage 1  server ─ W2CSpawnNpc { ..., Baseline = true } (fresh position/state) ─▶
         client ─ C2WSpawnAck { ..., Baseline = true } ─▶
stage 2  READY: the entity is now included in this player's snapshots
  • Generation identifies one particular appearance of an entity. An ack for an old generation (the entity left and came back) is ignored.
  • Unacked spawns are retried on a timer.
  • Priority lanes: NPCs, your target, anyone in combat with you or in your party are urgent; other players fill in as budget allows. 500 people arriving at a city at once queue fairly instead of starving each other.
  • Budgets: Performance.SpawnOperationsPerTick (1024), SpawnBytesPerTick (512 KiB), SpawnMilliseconds (6), and per player SpawnOperationsPerPeer (24) and SpawnBytesPerPeer (24 KiB). Anything over budget goes next tick.
  • Parents: a rider needs its mount, a passenger its vehicle. ParentOf makes sure the parent is spawned first.

The client side is ClientSpawnQueue: it creates objects within a frame budget and sends the acks.

Spawns are flushed once per tick in TickStage.Spawns (ReplicationManager.Spawns.Flush).

Adding a new kind of world entity#

Implement IWorldEntitySource (Core/Interest/IWorldEntitySource.cs) and register it with SpawnManager.RegisterEntitySource. When one of your ids enters a player's view, the spawn manager asks each source to send its spawn packet. DoodadManager and LootManager are the two existing examples. Allocate ids above NpcIdBase, put them in the interest grid with InterestManager.UpdatePosition, remove them with RemoveReplicatedEntity.

Snapshots: positions for everyone, every tick#

Movement never leaves the server as individual packets. Once per tick (TickStage.Snapshots), SnapshotDispatcher builds one batched, quantised, unreliable W2CWorldSnapshot per player:

Field Bytes Encoding
header: opcode, tick, origin x/y/z, count 20 origin = a per-packet reference point; positions are relative to it
per entity: id 4
flags 1 which optional fields follow
position 6 3 × int16, 1/64 m relative to origin
yaw 1 256 steps
state 1 MovementState bitfield
velocity (optional) 3 VelocityCodec
tilt (optional) 2 pitch/roll for mounts

13–18 bytes per entity instead of ~40 with MessagePack, and zero allocations (SnapshotWriter writes into pooled 1 KiB buffers).

Not every entity goes in every snapshot. For each observer the dispatcher:

  1. Takes the entities that are ready (spawn stage 2) and in interest.
  2. Scores them: distance, whether they moved, combat, target, party. Far and idle entities are sent less often; in crowds (CrowdTierThreshold) intervals stretch up to MaximumCrowdIntervalMultiplier (4×).
  3. Runs a critical pass first (your target, attackers, party: SnapshotCriticalEntitiesPerPeer) so they're never starved.
  4. Fills up to SnapshotEntitiesPerPeer (220) entities in up to SnapshotDatagramsPerPeer (4) datagrams.
  5. Stops the whole flush at SnapshotBytesPerTick (2 MiB) or SnapshotMilliseconds (16 ms); the next tick starts with the observers that were skipped (rotation).

The build is parallel above ParallelSnapshotMinimumPlayers (64): workers build datagrams per observer, the tick thread sends them.

On the client, W2CWorldSnapshotHandler decodes with SnapshotReader, keeps the newest tick per entity (snapshots can arrive out of order) and feeds each entity's RemoteEntityInterpolator (Movement).

Broadcasting other events#

Anything else that many players should see (a cast starting, a hit, an emote) goes through ReplicationManager (Core/Interest/ReplicationManager.cs):

// Everyone who can see this player, plus the player themselves:
var peers = new List<NetPeer> { peer };
foreach (int observer in _interest.GetKnownBy(networkId))          // who knows about networkId
    if (!SpawnManager.IsNpcId(observer) && _players.TryGetPeer(observer, out var p))
        peers.Add(p);

_replication.Broadcast(Opcodes.W2CPlayerTitle,
    new W2CPlayerTitlePacket { PlayerNetworkId = networkId, Title = "Kraken Slayer" }, peers);

(This is AchievementService.SetTitle.) Broadcast serialises the packet once and sends the same bytes to each recipient, on the channel PacketChannels assigns; BroadcastExcept skips one peer; SendUnreliable is for cosmetic, replaceable data. Interest already respects layers, so building the list from GetKnownBy is all you need. Never loop over all connected peers for a local event.

Spawn and despawn opcodes passing through ReplicationManager are automatically routed into the spawn delivery queue, so always send them through it rather than WorldserverPacketSender directly.

Tuning for crowds#

The defaults in World.Performance.json were first measured with the LoadTest bot fleet at 500 clustered players.

Measured capacity (1 November 2026). On a Ryzen 5 5500 (6 cores / 12 threads) running the World, Auth and Persistence servers, MySQL and the bots on the same PC, a capacity ladder with mixed-fidelity bots spread over two open-world zones gave:

Players Per zone Tick p50 (busiest zone) Worst 5 s window p99 Result
1,000 ~500 ~6 ms 21.9 ms pass
2,000 ~1,000 ~14 ms 31.7 ms pass (limit 40 ms)

Per zone host at ~1,000 players the tick averages about MovementAndAoi 6–8 ms, Snapshots 4.7–6 ms, Spawns 1.5–2.4 ms, Packets 1.4–1.7 ms. Cost grows faster than the player count (about 2.3–4.7x for 2x players), because it scales with players times neighbours (~80 per player in the test). Plan on 700–1,000 players per zone thread at that density; total capacity grows with the number of open-world zones. These are bots on loopback, densely packed and sharing the PC, so treat them as a floor, not a promise.

The end of every step (1,000 players logging out at once) still pushes one zone's tick to a few hundred ms, mostly in MovementAndAoi: every observer recomputes who it can see as the leavers despawn. It only happens on mass logout.

The log's [SpawnWork], [CrowdWork], [AoI] and [ParallelStages] lines (every report window) tell you which budget is the bottleneck:

Log says Means Try
pendingSpawns stays high spawn budget exhausted every tick raise SpawnOperationsPerTick / SpawnMilliseconds
snapshotBytes at the cap snapshot budget exhausted raise SnapshotBytesPerTick, lower SnapshotEntitiesPerPeer, enable dynamic AoI
aoi work many ms interest recompute heavy AoiWorkers, lower density radii
movementMs high motor simulation heavy MovementZoneWorkers, more zones

Every option is listed in the configuration reference.
