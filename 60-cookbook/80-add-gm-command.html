Cookbook (How-To)

Add a GM Command#

Staff commands travel in one packet (C2WGmCommand, opcode 177) with a GmCommand value and generic arguments; the server re-checks the sender's current access level with Auth for every command, refuses staff at or above your own level, and writes each action to the audit log. Background: Staff & GM tools; every command that exists: GM command reference.

Example: support staff need to reset a player's dungeon lockouts ("I disconnected during the boss and lost my run").

1. Shared (Axiom.Network/Shared/Packets/Staff/GmPackets.cs)#

Add the value with a comment saying what the arguments mean (append; values are bytes and stable):

        ResetNpc      = 54,  // the targeted NPC: full health, threat cleared
        ResetDungeonEntries = 55, // the target's dungeon run counts: A = dungeon id (0 = every dungeon)

Give it an access level in GmRules.MinLevel (3 Community Manager, 4 Game Master, 5 Developer; unlisted = 5):

                case GmCommand.Ban: case GmCommand.Unban:
                case GmCommand.ResetDungeonEntries:
                // ...
                    return 4;

If it creates value (items, coins, levels), add it to GmRules.NeedsDebug so it only works where World:AllowDebugCommands is on; if it only reads, add it to IsQuery. This one does neither.

C2WGmCommandPacket already carries TargetCharacterId, TargetNetworkId, TargetName, A, B, C, X/Y/Z and Text - most commands need no new fields, so no packet change. Rebuild Axiom.Network, copy the DLL to the client, and bump the protocol (the enum is shared).

2. A small helper on the component#

Core/Players/Components/DungeonEntryComponent.cs:

        /// <summary>GM: forget runs used (one dungeon, or all with 0). Returns how many were cleared.</summary>
        public int Reset(int dungeonId)
        {
            int n = dungeonId == 0 ? Entries.Count : (Entries.Remove(dungeonId) ? 1 : 0);
            if (dungeonId == 0) Entries.Clear();
            if (n > 0) _dirty = true;        // saved with the next full save
            return n;
        }

3. Server (Core/Staff/GmService.cs)#

Add a case to the command switch, next to the other "the target" commands:

            case GmCommand.ResetDungeonEntries:
            {
                if (!Target(gm, p, true, out var tp, out var t)) { Reply(peer, cmd, false, "That player isn't online."); return; }
                if (!ReferenceEquals(t, gm) && t.AccessLevel >= level) { Reply(peer, cmd, false, "Not staff at or above your own level."); return; }
                if (p.A < 0) { Reply(peer, cmd, false, "Dungeon id must be 0 (all) or a dungeon id."); return; }

                int cleared = t.DungeonEntries.Reset(p.A);
                if (cleared == 0) { Reply(peer, cmd, false, $"{t.Name} has no runs used{(p.A > 0 ? " in that dungeon" : "")}."); return; }

                _players.SaveInBackground(t);                                   // don't wait for autosave
                Done(peer, gm, cmd, t.Name, p.A == 0 ? "all dungeons" : $"dungeon {p.A}",
                     $"Reset {cleared} dungeon lockout(s) for {t.Name}.");
                return;
            }

What the helpers do:

  • Target(gm, p, allowSelf, out peer, out session) resolves the target from TargetCharacterId, then TargetNetworkId (your current target), then (if allowed) yourself. Only online players.
  • Reply(peer, cmd, ok, message) answers the GM panel without auditing (refusals).
  • Done(peer, gm, cmd, target, detail, message) writes the audit row (who, what, target, detail, when) and answers. Every command that changes something must end in Done.
  • level is the GM's current access level, already checked against GmRules.MinLevel before the switch.

Commands that need another service (Persistence for offline characters, Auth for bans) start an async method (see BanAsync) and come back with EnqueueAction before touching sessions.

4. Client (Scripts/Staff/GmPanelWindow.cs)#

On the Target page (BuildTarget), add a line:

            var dungeons = Section(page, "Dungeons", "Clear runs used this period (0 = every dungeon).");
            l = Line(dungeons);
            var dungeonId = Int(l, "Dungeon", 0);
            Command(l, "Reset Lockouts", GmCommand.ResetDungeonEntries,
                () => Confirm("Reset dungeon lockouts for " + TargetName + "?", "They can enter again this period.",
                              () => On(GmCommand.ResetDungeonEntries, a: dungeonId.value)),
                "Give back the dungeon runs they've used.");

Command(...) greys the button out when your access level is below GmRules.MinLevel for that command, so staff only see what they may use. On(cmd, a:, text:) sends it for the selected player via GmPanelState.Send. The answer appears in the panel's status line; the audit page lists it.

5. Test#

  1. A test account with access level 4 (Auth database accounts.access_level, MySQL), log in, F12 opens the GM panel.
  2. Enter a dungeon with a limited-entry character, leave, try again (refused: no runs left).
  3. GM panel → Players → pick them → Target → Reset Lockouts → they can enter again.
  4. Audit page shows the row. A level-3 account sees the button disabled; the server refuses it anyway if sent.

Faster alternative for development#

A Lua chat command is quicker for a private shortcut, but unaudited and unchecked - keep those out of production:

Server:RegisterCommand("resetme", function(player, args)
    if player:GetName() ~= "DevAlice" then return end
    -- ...
end)
