Feature note, kept next to the code it describes. Source: docs/notes/client/CLIENT_CHARACTERS.md

Characters: models, gear, animation, camera#

The client track's first four items, built 10 Oct 2026 (protocol 23): animation driven by combat and ability events, character models with visible equipment, a camera for combat and traversal, and the asset pipeline (ASSET_PIPELINE.md). All of it is presentation. The server decides everything, and these systems only show it.

How the pieces fit#

W2CSpawnPlayer (FactionId, Gear)  ─┐
W2CPlayerAppearance (Gear)        ─┼─> CharacterModel ──> the body prefab (Character_Default / Character_Faction{N})
FactionState (outlawed, amnesty)  ─┘        │
                                            ├─> CharacterAppearance ──> GearVisualCatalog rows on sockets / skinned to the rig
W2CCastStart / W2CCastEnd  ─┐               │
W2CCombatEvent             ─┼─> CharacterAnimator ──> the body's Animator parameters
movement (motor / snapshots)┘

All three components are added at runtime, so no prefab needs editing: PlayerRegistry.Spawn adds them to players, and W2CSpawnNpcHandler adds CharacterAnimator to NPCs.

Character models#

CharacterModel replaces the Player prefab's capsule (its Model child) with a prefab from the WorldObjectPrefabs catalog:

Key Used for
Character_Faction1, Character_Faction2... That faction's players (1 Westmark, 2 Eastreach, 3 Pirates)
Character_Default Everyone else, and any faction without its own key

With neither key assigned, the capsule stays. Faction changes (outlawed to the Pirates, amnesty home) swap the body live.

The model prefab: a rigged character, Humanoid avatar, pivot at the feet, facing +Z, with an Animator using the Axiom controller (see below). Colliders on it are switched off; the player root's collider is the gameplay one. Optionally add CharacterSockets (the prefab maker adds it) to point at sockets and list body-part renderers.

Races and genders (protocol 41) pick the body first. See the next section.

Mounted: if the mount prefab has a child called RiderSeat, the body sits there.

Races, genders and gendered gear#

Added 23 Oct 2026 (protocol 41). The list of races lives in one place, src/Axiom.Network/Shared/Combat/CharacterRaces.cs (CharacterRaceRules.Races), shared by the client, world server and persistence server. It starts as Human, Elf and Fairy; genders are Male and Female. There is one playable faction (Westmark), so the creation screen hides the faction choice. Each race can be tied to one faction (its last argument); the creation screen then picks that faction and greys out the others, and the servers refuse anything else.

The race and gender are saved on the character (characters.race_id, gender_id; characters from before this are Human Male), shown on character select ("Level 12 Elf Female Mage") and sent to everyone in W2CSpawnPlayer.

Bodies: the first of these keys with a prefab in WorldObjectPrefabs wins (CharacterBodyKeys):

Key Example Gear variants it asks for
Character_{Race}_{Gender} Character_Elf_Female Elf_Female, Female
Character_{Race} Character_Elf Elf
Character_Default_{Gender} Character_Default_Female Female
Character_Faction{N} Character_Faction2 none
Character_Default none

So you can add art a little at a time. One Character_Default_Female makes every woman female before any race has its own body. The Asset Audit lists every race/gender key as optional.

Gendered gear: no database change. Keep the item's one row in Gear Visuals (PrefabKey Gear/Chest/IronPlate, say) and put the other versions beside the prefab in Resources with a suffix:

Resources/Gear/Chest/IronPlate.prefab              everyone (the original)
Resources/Gear/Chest/IronPlate_Female.prefab       every female body
Resources/Gear/Chest/IronPlate_Fairy_Female.prefab fairy women only

A body tries its variants in the order in the table, then the plain prefab. The variants follow the body that was actually drawn, not the character's race on paper: until Character_Fairy_Female exists, a fairy woman wears the _Female (or plain) version, because skinned gear must match the rig it's on.

  • Skinned variants (chest, legs, gloves, boots) must be authored on that body's rig, with the same bone names, like any skinned gear.
  • Socket variants (helmets) share the row's socket and offsets. If a female helmet needs to sit differently, move the mesh inside its prefab.
  • HidesBody comes from the row, so give the female body the same CharacterSockets.Body parts.
  • The Audit's Gear tab shows the variants found next to each item's look: own look (+Female, Elf_Female).

Adding a race: give it the next number in CharacterRace, add a line to CharacterRaceRules.Races, raise MaxRaceId, and add a migration widening CK_characters_race (race_id BETWEEN 1 AND <new max>). Never renumber an existing race: the numbers are saved on characters.

Visible equipment#

The server now tells everyone what a player visibly wears:

  • On spawn: W2CSpawnPlayer.Gear.
  • On every change: W2CPlayerAppearance (opcode 155), sent from EquipmentManager to the player and everyone who can see them.

Gear is item ids indexed by EquipSlot. Only the visible slots are filled (Head, Chest, Legs, Hands, Feet, MainHand, OffHand; see EquipSlots.IsVisible). Rings, neck and trinket stay private. The trade pack keeps its own packet.

The look comes from Resources/World/GearVisuals.asset (GearVisualCatalog). Create it with Tools > Axiom > Characters & Gear > Animation > Create Gear Visual Catalog. Each row has:

Field Meaning
ItemId The item. 0 = the default for its Slot: one row per slot and every item shows.
Slot The equipment slot
Prefab The model
Attach Socket: a rigid model on a socket (weapons, shields, helms). Skinned: a skinned mesh on the same skeleton, with bones re-pointed by name (chest, legs, gloves, boots).
Socket / SheathSocket Override where it goes in use or sheathed. - = never sheathed.
HidesBody Base-body parts hidden under it (CharacterSockets.Body lists them)
Offsets, Scale Fine placement on the socket

Sockets: MainHand, OffHand, Back, BackOffHand, HipRight, HipLeft, Head. A socket is found as an explicit CharacterSockets entry, then a child named Socket_<Name>, then the matching Humanoid bone. So a stock Humanoid character works with no setup, and you add Socket_* empties only to fine-tune.

Weapons are sheathed out of combat (on the back) and drawn in combat or while casting.

Skinned gear must be authored on the body's rig, with the same bone names. A bone that doesn't match logs a warning naming it.

The audit (Tools > Axiom > Art & Assets > Asset Audit, Gear tab) lists every wearable item and whether it has its own look, a slot default, or nothing.

Animation#

CharacterAnimator drives the body's Animator. Every parameter is optional: one the controller doesn't have is skipped. Generate a starter controller with all of them wired (Tools > Axiom > Characters & Gear > Animation > Create Character Animator Controller), drop your clips into its empty states, and assign it.

Parameter Type Source
Speed float Planar speed, m/s (the locomotion blend: 0 idle, 1.6 walk, 5 run, 8 sprint)
MoveX, MoveZ float Local-space velocity ÷ 5, for strafe/back blends
VerticalSpeed float Rising or falling
Grounded bool On the ground
Swimming, Mounted, Seated bool Swimming; riding; passenger in a vehicle
Dead bool You (DeathState), anyone killed (W2CCombatEvent.Killed) until respawned or healed
InCombat bool 6 s after any hit given or taken, or while casting. Draws weapons.
Casting bool Held for the length of a cast with a bar
SkillId int The ability playing, for a blend tree or sub-state machine per skill
Jump, Land trigger Leaving and touching the ground
Attack trigger A weapon ability went off (IsSpell = 0), or an NPC swing
CastRelease trigger A spell went off (an instant, or a cast completing)
CastInterrupted trigger A cast was interrupted
Hit, Crit, Miss trigger Taking a hit (rate-limited to 4 a second). Crit falls back to Hit.
Die, Revive trigger Death and coming back

Per-ability animations: put a parameter name in the skill's AnimationParameter (Content Studio, Skills). It's now sent to the client in the skill catalog.

  • If it names a trigger, that fires instead of Attack/CastRelease when the ability goes off.
  • If it names a bool, it's held for the length of the cast (a channel pose).

Add the matching parameter and state to the controller.

Instants are now visible to everyone. The server used to tell only the caster about an instant ability, so nobody else could see a self-buff or a heal. W2CCastStart for instants now goes to everyone who can see the caster. Other clients ignore its GcdMs.

NPCs use the same component and parameters. When an NPC is killed, its model stays for 2.5 s (NpcRegistry.DeathLingerSeconds) to play Die while the corpse appears.

Root motion is always off. The server owns positions, and the clips import "in place" (ASSET_PIPELINE.md).

Camera#

MMOCamera keeps everything it had (free look on left drag, steering on right drag, auto-align, occlusion, first person) and adds context framing:

Context When Framing (defaults)
Explore on foot 6 m, pivot 1.6 m
Combat in combat (CharacterAnimator) 5 m, slight over-the-shoulder offset, swings behind faster
Mounted riding pivot +1 m, 8 m, wider FOV at speed
Vehicle driving or riding a cart pivot +1.2 m, 10 m
Swimming swimming pivot -0.5 m
  • Zoom per context: each context remembers the zoom you chose in it. Zoom steps grow with distance, so zooming far out isn't a hundred scroll clicks.
  • Smooth changes: pivot, shoulder and FOV ease from one context to the next instead of snapping.
  • Above ground: the camera never goes below the ground beneath it.
  • Shake: a small kick when you're hit, scaled by the damage.
  • First person: your own body renders shadows only.

Options (Options > Controls, saved in CameraSettings): ScreenShake, SpeedFov, CombatShoulder and TargetAssist, all on by default.

Since 10 Oct the camera also has mouse look (), vertical follow smoothing, ignores other characters for collision, and in the Modern control scheme leads instead of following. All of it, and the movement schemes and Tab targeting, is inMOVEMENT_AND_CAMERA.md`.

To tune the profiles, open main_world, select the MMOCamera and fill in Profiles. Left empty, it uses the defaults in the table.

What you still need to do in Unity#

  1. Import a Humanoid character into Assets/AxiomMMOKit/Axiom.Client/Art/Characters/. Run Make World Prefab From Selected Model on it. Then open Tools > Axiom > Asset Pipeline > Audit and drag the new prefab onto the Character_Default row. (The maker also registered it under the model's file name; that extra key shows as Unused and can stay or be deleted.)
  2. Run Create Character Animator Controller. Fill its states with clips (Mixamo works), and assign it to the character prefab's Animator.
  3. Run Create Gear Visual Catalog. Add a slot-default row for MainHand (a sword) and OffHand (a shield), then more as art arrives.
  4. Give NPC models (the Orc) the same controller, or their own with the same parameter names.
  5. Play with two clients. Check that equipping shows on the other client, that attacks and casts animate on both, that a kill plays Die, and that the camera reframes on a mount and in a cart.
