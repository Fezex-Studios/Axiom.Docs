Instance zones: every dungeon run on its own thread#

18 Oct 2026. Code: Core/Instances/Zones/, Core/Instances/InstanceManager*.cs.

What changed#

A dungeon instance used to be a layer inside the shared world tick. Its bosses, clock and script (Docs/DUNGEON_SCRIPTS.md) ran inside InstanceManager on the one 20 Hz tick thread. A slow script chain therefore cost every player in the open world a late tick.

Now each open instance has a zone (InstanceZone). The zone owns everything about the run:

The zone owns (its own thread) The world keeps (tick thread)
bosses: total, killed, dormant still to come the NPC and doodad entities, their AI, combat and movement
the clock: time limit, warning, exit after clearing sessions, teleports, packets
the script: events, action chains and delays, timers, rooms, health thresholds, combat start and end spawning, despawning, statuses, chests, doodad phases, Lua
the outcome: cleared or failed, and the messages entry limits and clear counting

The zone never touches a session, an entity or the grid. Everything that crosses the boundary is plain data in ZoneProtocol.cs:

world ──events──▶ zone        RunOpened, PlayerJoined, NpcSpawned, NpcsRemoved, RoomReset,
                              NpcDied, DoodadUsed, ZoneClosing
world ──view────▶ zone        ZoneView every 250 ms (latest wins): NPC health %, alive,
                              in combat; players' positions and alive. Only built for zones
                              whose script reads it.
zone  ──commands▶ world       SpawnTag, DespawnTag, DoodadPhase, Progress (tracker/banner),
                              ApplyStatus, Teleport, ResetRoom, SpawnChest, Complete, Fail,
                              SendOutAndClose, RunLua, RunStatus (the world's mirror)

The world applies commands in InstanceManager.Tick() (WorldSystems stage). It spends at most World:InstanceCommandBudgetMs (2 ms) per tick on them, and starts from a different zone each tick so one busy run can't starve the others.

Threads#

  • ZoneThread: one background thread per open instance. It runs at World:InstanceTickRate (20 Hz), at below-normal priority so the world tick comes first, with a 256 KB stack.
  • Posting an event wakes the thread at once, so a boss kill completes the run within 1–2 ms, not at the next tick.
  • The thread sleeps almost all the time. The number of open instances is bounded by DungeonMaxInstances.
  • The thread ends by itself after ZoneClosing.
  • A step slower than 50 ms is logged as [Zones] … (on its own thread - the open world didn't wait).
  • The tick-health log line [Zones] open=… threaded=… slowestStepMs=… queuedCommands=… shows how the zones are doing.

Inline mode#

World:InstanceThreads: false turns the threads off. Each zone then runs on the world tick: its timers live on the world Scheduler, its view is read fresh, and it is pumped synchronously whenever an event is posted. That reproduces the old behaviour exactly; for example, a boss kill completes the run in the same call. Inline mode is the fallback switch, and it is what tests use (new InstanceManager() defaults to inline).

Tag-wide commands are resolved by the world#

SpawnTag, DespawnTag and ApplyStatus(tag) name a tag, not NPC ids. The world resolves the tag when it applies the command, in order. So a chain like "SpawnTag adds → ApplyStatus adds (delay 0)" reaches the adds that were just spawned, even though the zone hasn't heard about them yet. The world then reports back to the zone (NpcSpawned, NpcsRemoved, RoomReset).

What the threads do NOT isolate (honestly)#

The entities inside a dungeon are still simulated by the shared managers on the world tick: NPC AI, combat, statuses and interest. Moving those onto per-instance threads would mean making about 20 shared managers thread-safe. That is high risk, and the real fix for it is a separate process, not more locks.

The thing the threads do fix is the one the design called out: scripts, timers and run logic. Script chains were already bounded (DungeonScriptMaxSteps, 8 nested triggers). Now even a bounded but heavy one costs only its own thread.

Next step: instance servers#

The protocol is the process boundary. To move instances to their own server process:

  1. Serialize ZoneEvent / ZoneView / ZoneCommand with MessagePack (they are already plain records).
  2. Put a socket where the ConcurrentQueues are.
  3. Move the instance's entities into that process as well. Party, chat and loot then cross the socket in the same way.

Nothing in InstanceZone changes.

Config#

"World": {
  "InstanceThreads": true,          // false = inline on the world tick (old behaviour)
  "InstanceTickRate": 20,           // zone thread Hz (1-120)
  "InstanceViewIntervalMs": 250,    // how often scripted zones get a fresh view (50-5000)
  "InstanceCommandBudgetMs": 2.0,   // world-tick time applying zone commands per tick (0.1-20)
  "InstanceAiBudgetMs": 3.0         // world-tick time for dungeon NPCs per tick (0 = no limit)
}

Dungeon AI budget (19 Oct 2026)#

The problem#

The zone threads above own each dungeon's script, clock and outcome. The dungeon's NPCs did not move with them. Their AI, movement and attacks ran inside the same three loops as every open-world NPC (NpcAiManager.Tick), so one busy dungeon made the whole shard's tick longer.

What changed#

NpcAiManager now splits its work:

  1. Open-world NPCs (interest layer 0) run first, in full, exactly as before.
  2. Dungeon NPCs (any other layer) run in RunInstancePass: - They run one dungeon (layer) at a time. All of a dungeon's NPCs run together, so they never disagree with each other. - Each NPC runs in the same order as before: decide, then move, then attack. - The pass stops when World:InstanceAiBudgetMs of this tick has been used. - InstanceRotation decides who goes first. At least one dungeon runs every tick, and a postponed dungeon leads the next tick. With N dungeons, none waits more than N ticks however small the budget; Axiom.Server.World.Checks covers this. - A dungeon that misses a tick catches up exactly. Each NPC keeps its own LastMoveMs and moves as far as the time that actually passed, up to MaxMoveDelta. Decisions keep the 300 ms cadence through LastDecisionMs. Swings and abilities were already clock-gated.

NpcAiManager.LastInstanceLayersRun, LastInstanceLayersDeferred and InstanceLayersDeferredTotal report what the pass did. If dungeons keep running over budget, a warning is logged at most once a minute.

What it is and isn't#

This bounds what dungeons can cost the open world. It does not yet run dungeon NPCs on the zone threads. Everything stays on the tick thread, single-owner, as PARALLEL_STAGES.md requires.

Next step: dungeon NPCs on their own threads#

Moving dungeon NPCs onto their own threads needs three things made safe for concurrent reads first. Today each of them would race:

  1. WorldCollisionSet.TryGetGroundHeight (Axiom.Movement). It fills a shared unique scratch set even for a read, and IsAreaReady starts loads and writes Used timestamps. Needed: - a read-only query that uses caller-owned scratch; - load and eviction kept on the tick thread, during prepare.
  2. NavMesh corridor queries (NavMeshService, NavAgent.Advance). They use the tick thread's query object and Touch page timestamps. Needed: - one DtNavMeshQuery per worker; - touches deferred to apply; - page in/out only between passes (it already happens only on the tick).
  3. NpcAiManager.ApplyMove and the spawn/despawn broadcasts. They write the interest grid and the snapshot store. Needed: the move step computes a result per NPC (new position, velocity, yaw, state), and the tick thread applies the results in id order. This is the same compute/apply split MovementZoneWorkers already uses for players.

Once those three are done, RunLayer becomes a parallel stage: prepare (warm collision and nav pages around each dungeon), then compute (one dungeon per worker), then apply (tick thread, deterministic order). It needs a byte-identical test like the one in PARALLEL_STAGES.md.
