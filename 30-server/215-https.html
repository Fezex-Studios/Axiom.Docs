Server Systems

HTTPS for Auth#

Short version: for local development you don't need to set anything up. HTTPS matters only when people connect from outside your home. Then Caddy, a free program, gives the Auth server HTTPS in a few minutes.

Why HTTPS at all#

Passwords, saved logins (refresh tokens), login tickets and the World server's internal secret all go to the Auth server. Over plain HTTP, anyone on the network path can read them: café Wi-Fi, an ISP, a hacked router. HTTPS encrypts that traffic.

To protect players, Auth refuses plain HTTP from other machines. Your own PC is always allowed, which is why nothing changes while you develop.

The three ways to connect#

Mode Who Address the game uses Caddy? Set-up
1. Just you you, on your PC http://127.0.0.1:3000 (the default) No nothing
2. Home Wi-Fi friends in your house http://192.168.x.x:3000 No one setting + a Development build
3. Internet players anywhere https://your-name.duckdns.org Yes about 15 minutes, once

You switch modes by changing the address the game connects to (AuthBaseUrl in Resources/UI/Selection/WorldDirectory.json, which -auth-url <address> on the command line overrides, and the launcher's launcher.config.json). Settings you add for Mode 2 or 3 don't break Mode 1, so you can leave them in place.

Mode 1: Just you, on your PC#

Nothing to do. Start the servers and press Play as usual.

Everything talks over 127.0.0.1 ("this computer"), so the traffic never leaves your PC and doesn't need encryption. Auth always lets your own PC through, and the client always allows http:// to localhost, even in release builds.

Mode 2: Friends on your home Wi-Fi#

  1. In Axiom.Server.Auth/appsettings.Local.json, add this line inside "Auth":

json "Auth": { "InternalSecret": "...what you already have...", "PlainHttpAllowedNetworks": [ "private" ] }

"private" means home and office networks (192.168.x.x, 10.x.x.x, 172.16–31.x.x). Without it, your friend's login gets "only accepts secure (HTTPS) connections", and Auth's log shows the refused address.

  1. Find your PC's local address: run ipconfig in Command Prompt and read IPv4 Address, e.g. 192.168.1.50.

  2. Build the game with Development Build ticked in Build Settings. A release build refuses plain HTTP to another machine on purpose, so it can never send a login over an unencrypted connection by accident.

  3. Point your friend's copy at your PC: - in the build's WorldDirectory.json, "AuthBaseUrl": "http://192.168.1.50:3000"; - in the Axiom Launcher's launcher.config.json, "authServerUrl": "http://192.168.1.50:3000" and "worldServerIp": "192.168.1.50".

Your friend logs in through the launcher as usual.

  1. Make sure Auth listens on the network, not only on your PC. The default appsettings.json uses http://0.0.0.0:3000, which is correct for this mode. If you changed it to 127.0.0.1 for Mode 3, set it back while you test on the LAN.

Remove PlainHttpAllowedNetworks before you put the server on the internet.

Mode 3: Players over the internet (Caddy)#

What Caddy does#

Player's game / launcher
        │  https://axiom.duckdns.org   (encrypted)
        ▼
  ┌─────────────┐   your PC
  │   Caddy     │   ports 80 + 443, holds the certificate
  └─────┬───────┘
        │  http://127.0.0.1:3000   (never leaves your PC)
        ▼
  ┌─────────────┐
  │ Auth server │
  └─────────────┘

Caddy sits in front of Auth. - Players talk to Caddy over HTTPS. Caddy decrypts each request, passes it to Auth on the same PC, and encrypts the answer on the way back. - Auth itself doesn't change. - The certificate is automatic. On first start, Caddy gets a free one from Let's Encrypt and renews it by itself.

Only Auth goes through Caddy. The World server (UDP 7777) does not.

Why Caddy#

For production choices beyond this (a cloud load balancer on AWS, DDoS protection, a recommended launch set-up): Production Hosting: HTTPS, DDoS and AWS.

Option Certificate Renewal Notes
Caddy (recommended) gets it itself automatic one program, a 3-line config file
nginx + certbot certbot certbot timer + nginx reload more config; fine if you already run nginx
Cloudflare Tunnel Cloudflare's automatic no open ports needed (good behind CGNAT); covers Auth only, not UDP 7777
Certificate on Kestrel you bring it manual, restart Auth see below

Step 1: Get a domain name#

Let's Encrypt gives certificates only to names, not to bare IP addresses.

  • Free: at duckdns.org, sign in and create a subdomain, e.g. axiom.duckdns.org. It fills in your current public IP. Home IPs change, so install the DuckDNS updater, or turn on DuckDNS updates in your router if it has them.
  • Your own domain: add an A record (e.g. auth.yourgame.com) pointing at your public IP.

Step 2: Open the ports#

In your router's admin page (often 192.168.1.1), under Port Forwarding:

External port Forward to Protocol For
80 your PC's LAN IP, port 80 TCP Let's Encrypt's ownership check, and the http→https redirect
443 your PC's LAN IP, port 443 TCP HTTPS (logins)
7777 your PC's LAN IP, port 7777 UDP the World server (needed in any case)

Allow the same ports in Windows Firewall.

Check first: some ISPs block port 80, or use CGNAT, so you have no public IP of your own. To check, compare the WAN IP in your router with what whatismyip.com shows. If they differ, port forwarding can't work. Use Cloudflare Tunnel for Auth, or host on a VPS.

Step 3: Install Caddy#

  • Windows: download caddy_windows_amd64.exe from caddyserver.com/download, rename it caddy.exe, and put it in C:\caddy\.
  • Linux: sudo apt install caddy.

Step 4: The Caddyfile#

Copy src/Servers/Axiom.Server.Auth/deploy/Caddyfile to C:\caddy\Caddyfile (on Linux, /etc/caddy/Caddyfile). Replace {$AXIOM_AUTH_DOMAIN} with your domain. Without the comments it is:

axiom.duckdns.org {
    encode gzip
    reverse_proxy 127.0.0.1:3000
}

That reads: "for this domain, get a certificate and send everything to Auth on port 3000".

Optional: if every World server runs on this same PC, uncomment the @internal block in the shipped file. That hides the World-only routes from the internet. They're protected by the internal secret either way.

Step 5: Tell Auth it's behind Caddy#

In Axiom.Server.Auth/appsettings.Local.json, add TrustForwardedFor and the Kestrel block:

{
  "ConnectionStrings": { "Auth": "...what you already have..." },
  "Auth": {
    "InternalSecret": "...what you already have...",
    "TrustForwardedFor": true
  },
  "Kestrel": {
    "Endpoints": { "Http": { "Url": "http://127.0.0.1:3000" } }
  }
}
  • TrustForwardedFor: true. To Auth, every request now comes from Caddy at 127.0.0.1, so this tells Auth to read each player's real IP from the header Caddy adds. Without it, all players share one address, and one person's failed logins rate-limit everyone. Auth logs a warning if it sees Caddy's header while this is off.
  • 127.0.0.1:3000 instead of 0.0.0.0:3000. Auth stops listening on the network directly, so the only way in is through Caddy and nobody can skip HTTPS.

Neither setting gets in the way of Mode 1, so they can stay on permanently. The 127.0.0.1 binding does block Mode 2; switch it back to 0.0.0.0 for a LAN session.

Restart Auth. Its start-up log says: HTTPS: expected from a reverse proxy (Auth:TrustForwardedFor)...

Step 6: Start Caddy and test#

cd C:\caddy
caddy run

On the first start you'll see it obtain the certificate, which takes about 10–30 seconds. Then test on your phone, on mobile data (not your Wi-Fi):

https://axiom.duckdns.org/worlds

If you see your world list as JSON, with a padlock in the address bar, everything up to Auth works.

Step 7: Point everything at the new address#

What Setting
Game client the Axiom Launcher passes its authServerUrl (-auth-url); AuthBaseUrl in Resources/UI/Selection/WorldDirectory.json is the fallback
Axiom Launcher authServerUrl in launcher.config.json
World server on the same PC nothing (World:AuthServerUrl stays http://127.0.0.1:3000)
World server on another machine World:AuthServerUrl = https://axiom.duckdns.org
World's public address WorldDirectory:PublicHost = axiom.duckdns.org (or your public IP), so clients know where to send UDP
Unity Editor login (Play Mode) can stay http://127.0.0.1:3000

The same client build works in every mode; only the address changes.

Step 8: Keep Caddy running#

caddy run stops when you close its window. To make it permanent:

  • Windows: install it as a service with NSSM: nssm install Caddy C:\caddy\caddy.exe run, with the start-up folder C:\caddy. Or use a Task Scheduler task "At startup".
  • Linux: apt install caddy already created a service. Put the file in /etc/caddy/Caddyfile and run sudo systemctl restart caddy.

Troubleshooting#

What you see Cause
Caddy: "timeout during connect" / "challenge failed" Port 80 doesn't reach your PC: router forwarding, Windows Firewall, the ISP blocking 80, or CGNAT. Or DuckDNS still points at an old IP.
Browser: 502 Caddy works, but Auth isn't running on 127.0.0.1:3000.
Launcher / game: "This login server only accepts secure (HTTPS) connections" Something still uses http://your-ip:3000. Change it to the https:// address.
Server Select: "The login server address … isn't secure (http://)" A release build was given an http:// address to another machine. Use https://, or a Development build for Mode 2.
Works from your PC, not from outside Testing by the public name from inside your own Wi-Fi fails on some routers ("NAT hairpin"). Test from your phone on mobile data.
Auth logs "TrustForwardedFor is off" Step 5's "TrustForwardedFor": true is missing.

Without Caddy: a certificate on Kestrel#

If you already have a certificate (from certbot, say), Kestrel can serve it directly. See the commented block in appsettings.Local.example.json:

"Kestrel": { "Endpoints": {
  "Http":  { "Url": "http://127.0.0.1:3000" },
  "Https": { "Url": "https://0.0.0.0:443",
             "Certificate": { "Path": "/etc/letsencrypt/live/auth.example.com/fullchain.pem",
                              "KeyPath": "/etc/letsencrypt/live/auth.example.com/privkey.pem" } } } }

A .pfx file works too ("Path" plus "Password"). Two things are left to you, which Caddy otherwise handles: - Renewal: restart Auth after the certificate renews. - Port 443 on Linux: this needs root, or setcap 'cap_net_bind_service=+ep' on the dotnet binary.

Reference: the guards#

Where Rule
Auth (HttpsGuard, Auth:RequireHttps = true) Plain HTTP from another machine gets 403 with Message: "This login server only accepts secure (HTTPS) connections…". Your own PC, and a trusted proxy's own requests (such as a load balancer's health check), are always allowed. Behind a trusted proxy, the proxy's X-Forwarded-Proto decides. The first refusal each minute is logged with the address and a count.
Auth start-up (TransportReport) One line saying where Kestrel listens and what the guard will do.
World (AuthService) Warns at start-up when World:AuthServerUrl is http:// to another machine.
Client (AuthServerAddress) https:// always works, and http:// to this PC always works. http:// to another machine works in the editor and Development builds (with a Console warning). A release build refuses it and shows why on Server Select.
Setting Default Meaning
Auth:RequireHttps true Refuse plain HTTP from other machines.
Auth:PlainHttpAllowedNetworks [] Allowed plain HTTP anyway. "private" = home and office ranges. Mode 2 only.
Auth:TrustForwardedFor false Believe the proxy's forwarded headers (Mode 3).
Auth:TrustedProxies [] Proxies on other machines ("10.0.0.5", "10.0.0.0/24"). Your own PC is always trusted.

Also in Unity: Player Settings > Other Settings > Allow downloads over HTTP. Once Auth is on HTTPS, set it to Not allowed for release builds. Note that it blocks http://localhost too.

What is and isn't encrypted#

Traffic Encrypted
Launcher / client ↔ Auth: passwords, saved logins, login tickets, the game data download Yes, in Mode 3
World ↔ Auth on another machine (internal secret) Yes, with an https:// AuthServerUrl
Client ↔ World game traffic (UDP) No

The login ticket the client sends to the World server crosses UDP unencrypted. That's acceptable because the ticket: - can be used once, and is deleted the moment the World redeems it; - lives at most Auth:LaunchTokenSeconds (120 s); - is redeemed by the real client's first packet, so a copy read off the network is already spent.

It can't reveal the password or the saved login. Encrypting the game traffic itself is a separate, later change, planned for before launch.

Code#

  • Services/HttpsGuard.cs: the guard, first in the request pipeline.
  • Services/ClientAddress.cs: trusted proxies, the right-most untrusted X-Forwarded-For entry, and the forwarded scheme.
  • Services/NetworkRules.cs: address and network lists ("private", CIDR, IPv4-mapped IPv6).
  • Services/TransportReport.cs: the start-up summary.
  • World Core/Services/Authservice/Authservice.cs: the AuthServerUrl warning.
  • Client Axiom.Client/Networking/AuthServerAddress.cs: the one Auth address, used by WorldDirectoryClient and GameDataBootstrap.
