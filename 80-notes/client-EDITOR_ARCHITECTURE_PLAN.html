Feature note, kept next to the code it describes. Source: docs/notes/client/EDITOR_ARCHITECTURE_PLAN.md

Axiom Editor Architecture: Assessment and Plan#

An honest review of the Editor tooling as of 25 Oct 2026, and a staged plan to bring it to professional standard.

Scope reviewed: Assets/AxiomMMOKit/Editor (115 C# files, about 26,400 lines) plus Axiom.Client/Editor, against the server source (src.zip) and the client.

1. Verdict#

The tooling is genuinely strong in capability. It is not yet strong in structure.

What you have is closer to a custom game-engine toolchain than a pile of scripts: a data layer with undo and validation (Content Studio), wizards that write transactional patches, an incremental, byte-verified collision exporter, a navmesh pipeline, server control and a release builder. Many commercial MMO teams do not have an in-editor suite this complete. Do not throw it away or rewrite it.

What holds it back from "professional" is maintainability, not features:

Strength Weakness
Content flows through numbered, transactional SQL patches, so content is in git and reproducible About 47 hard-coded "Assets/..." paths in 29 files. This is why moving folders breaks tools
Tabs, wizards and checks are discovered by reflection, so adding a tool means adding a file No assembly definitions: all 26,000 lines recompile together on every edit
Safety nets: backups, lock checks, delete guards, atomic commits Checks are menu items, so they cannot run in CI or on a build machine
Code comments explain why (rare and valuable) Two editor namespace styles: Axiom.EditorTools.* and Axiom.Client.Editor.* (the project's old name is gone since 26 Oct 2026)
Shared settings object so tools cannot disagree about the database Four overlapping front doors (Home, Dev Tools, Tool Browser, Studio)

2. Findings, with evidence#

2.1 Hard-coded paths are the biggest practical risk#

  • 47 string literals beginning "Assets/", in 29 files. The references are spread across Maps, Furniture, Housing, Lua, UI, World, AssetPipeline, DevTools, Netcode, Shops and Checks.
  • Each tool decides for itself where Resources, Prefabs, Housing and so on live. When you reorganized folders this session, about 25 files had to be edited to follow.
  • Only one Application.dataPath-style central helper exists (AxiomPaths for the server and project root). Asset locations have no equivalent.

Fix: one static class, AxiomAssetPaths, that is the single place that knows where things are. Every tool reads from it. A future reorganization becomes a one-file change.

2.2 No assembly definitions#

  • Everything under Assets/AxiomMMOKit/Editor compiles into Assembly-CSharp-Editor. A one-line edit to any tool recompiles all 26,000 lines. Domain reloads get slower as the suite grows.
  • Axiom.Client has an asmdef, but the Editor side does not, so there is no enforced layering. Nothing stops a Checks file from depending on a DevTools tab.

2.3 Naming#

The project's old name is gone (26 Oct 2026). Every namespace, class, file, settings asset, preference key, log rule, connection key and MySQL database now says Axiom, on the client, in the editor tools and on the servers. The old name survives in exactly three places, all one-time migration helpers that can be deleted once they have run on every machine:

  • Assets/AxiomMMOKit/Editor/Core/AxiomLegacyMigration.cs (editor settings file, Library folder, editor preferences)
  • Assets/AxiomMMOKit/Axiom.Client/Scripts/ClientConfig/LegacyNameMigration.cs (camera settings and key bindings)
  • scripts/MySQL/migrate_databases_to_axiom.sql on the server (moves your MySQL data)

What remains is cosmetic: two editor namespace styles (Axiom.EditorTools.* for most tools, Axiom.Client.Editor.* and Axiom.Editor.* for the UI checks, furniture and shops) and the doubled Axiom.Client.Axiom.Client.* namespace across the client runtime. Unifying them is optional tidying for later.

2.4 Checks are not real tests#

AxiomCheckRunner finds menu items under Tools/Axiom/Validation/ and calls them. That is clever, but: - They run only inside an open Unity Editor, never in CI. - Pass and fail depend on exceptions, with no structured report. - They cannot be run on a build machine before a release.

Fix: move them to the Unity Test Framework as EditMode tests ([Test] methods), keep the menu runner as a thin wrapper, and run them headless with Unity -batchmode -runTests.

2.5 Mixed UI technologies and duplicate front doors#

  • 27 files use IMGUI (OnGUI), 29 use UI Toolkit. Both are fine, but the suite looks and feels inconsistent (Dev Tools and Server Control and Build are IMGUI; Content Studio, Hub and Create are UI Toolkit).
  • Four entry points overlap: Home (status and shortcuts), Dev Tools (workbench), Tool Browser (every menu item) and the Axiom menu itself. A new developer does not know where to start.

2.6 Settings are split three ways#

  • ProjectSettings/AxiomDevTools.asset (shared, committed),
  • EditorPrefs (about 50 keys, per machine), and
  • Library/Axiom/... (per machine, not committed).

That split is reasonable, but it is undocumented and uses the old name. There is no single "show me all my tool settings" page.

2.7 Large files#

ZonesTab (1,274 lines), WorldTilesTab (785), TileProxyBaker (778), CharactersTab (659). They work, but each mixes UI, logic and file formats. They are the most expensive files to change safely.

2.8 The server databases#

  • Auth: axiom_auth
  • Persistence: axiom_persistence
  • Auction: axiom_auction
  • World: SQLite file worldserver.db (not MySQL)

Renamed on 26 Oct 2026; see section 6 for moving existing data.

3. Target structure#

Assets/
|- Editor/                               (tooling that is not game code)
|  |- Axiom.Editor.Core/                 asmdef. Paths, settings, DB status, styles, service probe
|  |- Axiom.Editor.Data/                 asmdef. Content Studio data layer (no UnityEditor dependency where possible)
|  |- Axiom.Editor.ContentStudio/        asmdef. Windows and UI, references Data
|  |- Axiom.Editor.Create/               asmdef. Wizards, references Data
|  |- Axiom.Editor.DevTools/             asmdef. Shell and tabs
|  |- Axiom.Editor.Pipeline/             asmdef. Asset import, prefab maker, gear, animator, audit
|  |- Axiom.Editor.World/                asmdef. Tiles, zones, maps, HLOD, navmesh, heightmaps
|  |- Axiom.Editor.Netcode/              asmdef. Collision exporters, build validator
|  |- Axiom.Editor.Project/              asmdef. Health, Build and Release, Server Control, Tool Browser
|  |- Axiom.Editor.Python/               asmdef. PythonRunner
|  \- Axiom.Editor.Tests/                asmdef. EditMode tests (the checks, moved here)
|
Tools/                                   (beside Assets/, never imported)
|  \- Python/
Docs/ (or Assets/AxiomMMOKit/Axiom.Client/Docs)
|  |- EDITOR_TOOLS_REFERENCE.md
|  \- EDITOR_ARCHITECTURE_PLAN.md

Dependency rule (enforced by the asmdef references, which fail compilation if broken):

Core  <--  Data  <--  ContentStudio
                 <--  Create
Core  <--  Pipeline, World, Netcode, Project, Python
DevTools --> Core, Data, Pipeline, World, Netcode   (shell may see everything)
Tests --> everything
Nothing depends on DevTools or Project.

One naming scheme#

Everything becomes Axiom.Editor.<Area>. Never use a segment named Editor by itself inside a namespace that also uses UnityEditor types (it collides with UnityEditor.Editor); Axiom.Editor.Core is fine as long as no type is named Editor.

One central paths class#

namespace Axiom.Editor.Core {
  public static class AxiomAssetPaths {
    public const string Client      = "Assets/AxiomMMOKit/Axiom.Client";
    public const string ArtResources= Client + "/Art/Resources";
    public const string WorldTiles  = Client + "/World/Tiles";
    public const string Entities    = Client + "/Entities";
    public const string Doodads     = Client + "/Doodads";
    public const string Housing     = Client + "/Housing";
    public const string Furniture   = Client + "/Furniture";
    public const string Docs        = Client + "/Docs";
    public const string Art         = Client + "/Art";
    // ... one line per location any tool needs
  }
}

Every "Assets/..." literal in the Editor folder is replaced by one of these. A future reorganization is then a one-line change per folder.

One front door#

Home stays the front door and becomes the only place that lists tools. Tool Browser's search and favourites merge into Home. Dev Tools remains the workbench. The Axiom menu keeps the tools you reach for by shortcut.

5. Staged plan#

Each stage ships on its own, leaves the project working, and can be stopped after.

Stage Work Risk Effort Payoff
1. Central paths Add AxiomAssetPaths; replace the 47 literals Low (mechanical) Small Reorganizing never breaks tools again
2. Docs and Python The reference you now have; Python runner; mask-map packer None Done Onboarding, repeatable asset steps
3. Single editor assembly One Axiom.Editor.asmdef over Assets/AxiomMMOKit/Editor, referencing Axiom.Client, MoonSharp, NuGet DLLs as needed Low Small Separate compile, clearer boundary, faster iteration
4. Rename the old project name Namespaces, settings class and file, Library folder, preference keys, stylesheets, server namespaces and MySQL databases, with one-time migrations Medium Medium Done 26 Oct 2026
5. Split into the asmdefs above Break the single assembly into the layered set Medium (a few hidden cross-dependencies will surface and need an interface) Medium Enforced layering, much faster compiles
6. Checks become tests Port to [Test] in Axiom.Editor.Tests; keep the Run All Checks menu as a wrapper; add a headless command and a CI step Low to Medium Medium Checks run before every release and in CI
7. Consolidate front doors Merge Tool Browser into Home Low Small One obvious starting point
8. Break up the biggest files ZonesTab, WorldTilesTab, TileProxyBaker into model, logic and view Medium Larger Safer future changes
9. Structured logging and reports One logger with levels and a file sink, shared by tools and checks Low Small Useful bug reports

Recommended order: 1, 3, 6, 4, 5, 7, 8, 9. Do stage 1 first: it removes the failure you actually hit this week.

Honest constraint#

None of these stages can be compiled and tested outside Unity, and I cannot open your project in the editor. Each stage must be applied and compiled on your machine. I will do each in small steps, name every file changed, and verify with text searches (every old path or namespace string accounted for) before you open Unity. Expect to spend a few minutes after each stage reading the Console for compile errors. Do not apply several stages at once.

6. The MySQL databases (renamed)#

The servers now use axiom_auth, axiom_persistence and axiom_auction (appsettings*.json, and the USE lines in the server's SQL/*.sql scripts).

Moving your existing data: stop every server, back up, then run scripts/MySQL/migrate_databases_to_axiom.sql (mysql -u root -p < migrate_databases_to_axiom.sql, or open it in MySQL Workbench). It moves every table into the new database with RENAME TABLE: instant, keeps all rows, indexes, foreign keys and the EF migration history, and is safe to run twice. The old databases are left empty; drop them once everything works.

Schema creation is unchanged: Auth applies EF migrations at startup (MigrateAsync), Auction uses EnsureCreatedAsync, Persistence is migrated with dotnet ef database update. On a brand-new machine, create the three axiom_* databases first.

7. What I recommend you do next#

  1. Keep what you have. Do not rewrite it.
  2. Adopt the two documents (this and EDITOR_TOOLS_REFERENCE.md) as the standing reference. Put both in Axiom.Client/Docs.
  3. Install the reorganized Editor folder (stages 1, 2 and 7 are in it), let it compile, and run Run All Checks. Then stage 3.
  4. Run the MySQL migration (section 6) before starting the renamed servers.
