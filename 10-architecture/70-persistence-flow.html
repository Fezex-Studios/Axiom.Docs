Architecture

Persistence Flow#

Player state lives in the World server's memory while the player is online (the PlayerSession), and in MySQL (axiom_persistence) the rest of the time. The World server never talks to MySQL. It sends HTTP requests with MessagePack bodies to the Persistence server, which owns the database.

This page explains how that works without ever losing or duplicating an item, which is the hardest problem in an MMO backend. The rules were written after an audit found every item-dupe bug came from saves racing each other.

The five rules#

  1. Every save is a full snapshot. Level, position, gold, every bag slot, everything worn, the quest log, the warehouse, abilities, labor, faction, achievements, dungeon entries, Patron: all of it, in one request (/characters/save-full), written in one MySQL transaction. Never diffs: a diff is only correct relative to what the database holds, and a lost or reordered request makes that unknowable.
  2. Every save carries a SaveSeq, strictly increasing per character. Persistence locks the characters row (SELECT … FOR UPDATE) and only writes if the request's SaveSeq is higher than the stored save_seq. An older or duplicate save is answered Stale and writes nothing.
  3. One request in flight per character (CharacterSaveChain). The next save starts only when the previous one has a definite answer. Queued saves coalesce: only the newest state is sent.
  4. An unknown outcome is never guessed. A timeout is retried with the same SaveSeq until the database answers. If the first attempt had landed, the retry gets Stale, CurrentSeq = yours, and that is the success answer.
  5. Login waits for saves. Loading a character waits until every save of that character (and, for account-wide data like labor, of the account's last character) has settled (PrepareLoginAsync, up to 20 s).

The pieces#

Piece Where Job
IPersistentComponent Core/Players/Components A saved part of a session: IsDirty, WriteTo(snapshot), MarkSaved().
PlayerSession.PersistentComponents Core/Players/PlayerSession.cs The list: Inventory, Warehouse, Quests, Equipment, Abilities, Labor, Proficiency, Pvp, Achievements, DungeonEntries, Patron.
CharacterPersistence Core/Players/Saving The one place that saves: Capture builds the snapshot, three entry points send it.
CharacterSaveChain Core/Players/Saving Per-character ordered, retried, coalesced requests. Outlives the session.
AutosaveScheduler Core/Players/Saving Spreads periodic saves across ticks.
PersistenceClient Core/PersistenceServer HttpClient with the internal secret, MessagePack bodies, a bounded request gate.
W2P* / P2W* Axiom.Network/Shared/Packets/W2P, P2W Request/response classes.
Persistence Program.cs Axiom.Server.Persistence Minimal-API routes; ApplyFullSaveAsync writes a snapshot.

When a character is saved#

Trigger Call Notes
Autosave PlayerManager.RunAutosave(tick) → AutosaveScheduler Every World:AutosaveIntervalSeconds (120 s). Player n is saved on tick n % intervalTicks, so 2 400 players at 20 Hz is about one save per tick. Only dirty sessions.
Disconnect CleanupPeer(save: true) The chain keeps running after the session is gone.
Level up OnLevelledUp → SaveInBackground
Return to selection / world switch CharacterSelectionReturnService Waits for the save before showing the roster.
Server shutdown WorldServer.StopAsync All online characters, 10 s budget.
Write-through SaveNowAsync Before something irreversible happens elsewhere (see below).

tick thread                                   thread pool                        Persistence / MySQL
───────────                                   ───────────                        ───────────────────

  snapshot.SaveSeq = ++seq
  foreach component: WriteTo(snapshot)
  foreach component: MarkSaved()   ◀── marked saved NOW (the chain guarantees it lands)
chain.Enqueue(snapshot) ───────────────────▶  POST /characters/save-full ──────────▶ BEGIN

                                                                                   DELETE + bulk INSERT inventory,
                                                                                     equipment, quests, warehouse…
                                                                                   ItemUidAudit (duplicate gear?)

Answers (CharacterSaveResult):

Result Meaning World does
Saved written done
Stale (with CurrentSeq ≥ ours) an equal or newer save is already in treated as success
NotFound no such character for that account log
MailGone the mail this save claimed no longer exists; nothing written caller refunds nothing (it never got the mail)
StorageConflict a coffer changed since it was read; nothing written re-read the coffer
Invalid the request is malformed (validated before touching the db) mark dirty, log loudly
500 / timeout rolled back or unknown retry the same request

Persistence validates every snapshot (ValidateFullSave): row counts, duplicate slots, negative quantities. A malformed save is answered Invalid (not 500), so the World server doesn't retry it forever.

Write-through saves: when the world must wait#

Most saves are fire-and-forget (SaveInBackground). But some actions hand something to another service, and a crash between "took it from the player" and "the other service has it" must not lose or duplicate it.

SaveNowAsync(session) returns a Task<SaveOutcome>; the caller waits for the database before continuing. Two variants carry extra work in the same transaction:

  • SaveClaimingMailAsync(session, mailId): the snapshot already contains the mail's items, and the save deletes the mail row. The items appear exactly when the mail disappears.
  • SaveWithStorageAsync(session, storage): moves items between the player and a coffer atomically (optimistic storage_seq check).

A player trade uses /characters/save-pair: both characters' full snapshots in one transaction.

The outbox: what the world still owes#

Core/Services/WorldOutbox.cs. When an operation takes something from a player and needs another service to finish it (listing an item on the auction house, paying for an auction, placing a building, mailing a refund), the obligation is written into the same save that takes the item (OutboxEntryDto on the save request) → world_outbox table. Both land or neither does.

When the other service confirms, the World server deletes the obligation (/outbox/done). On start-up, and every couple of minutes, anything still owed (/outbox/pending) is run again. Every downstream operation is idempotent by key (auction create receipts, purchase keys, doodad placement keys, mail delivery keys), so running one twice is safe.

Rule for new features: if your feature moves value between a player and another service, put the obligation in the save (SaveNowAsync(session, outboxAdd)) and make the downstream call idempotent by a key you generate.

Loading#

/characters/load returns P2WCharacterLoadResponse: the row plus inventory, equipment, quests, abilities, warehouse, labor (account), proficiency, PvP, achievements, dungeon entries, Patron, SaveSeq and appearance. PlayerSpawnManager hands each part to its component's Load/LoadInto. A load with a SaveSeq older than one already seen is refused (IsLoadCurrent).

Fields that are null in the response mean "this Persistence server is older than that feature": the component marks itself not loaded and doesn't save. That's how the World server and Persistence can be upgraded independently.

What isn't in the character save#

Data How it's stored
Health, mana, cooldowns, buffs Not saved. Health/mana start full at spawn.
Vehicle being driven Not saved; the vehicle parks and its doodad is saved.
Guilds /guilds/command: every guild change is a command answered with the whole guild. World caches.
Mail /mail/list, /mail/claim, /mail/send.
Player-placed doodads (crops, crates, houses, furniture) /doodads/create|update|delete|storage, restored at boot by DoodadStore with /doodads/list. A Version column makes out-of-order updates safe.
Trade pack demand per outlet /trade/demand/list|set
Territories, sieges, world event schedule /shard/state/list|set (key/value rows per shard and kind)
Friends, blocks, families /community/command
Cash shop /cashshop/catalog|buy|gift: charged and mailed in one transaction.
Auctions the separate Auction service (Auction server)

The full route list with request and response types is in Service endpoints; the tables in MySQL databases.

Adding saved data#

Two shapes:

  • Per-character data that changes with play (a new currency, a reputation table, a collection): add an IPersistentComponent, fields on W2PCharacterSaveFullRequest and P2WCharacterLoadResponse, a table and migration in Persistence, and code in ApplyFullSaveAsync and the load route. Worked example: Add a persisted field.
  • Shard-wide state (a world boss's next spawn, a server-wide event): store it in shard_state with ShardStateStore, no schema change needed.
