Client Publish & Launcher Updates#

Players download only the launcher. The launcher installs the game, keeps it up to date, and repairs broken files. You publish each new client build once; the launcher fetches only the files that changed.

There is no update server to run. A release is plain files, so any host that serves files over HTTP(S) works: a cloud bucket, a CDN, GitHub Releases, or a folder on your own web server.

Unity build ──► axiom-publish ──► publish folder ──► your upload command ──► any static host
                 (hash + sign)    manifest.json                               ▲
                                  manifest.json.sig                           │ HTTPS GET
                                  objects/…                          Axiom Launcher (checks the signature
                                                                     and every file's SHA-256)

How it works#

  • manifest.json lists every file in the build with its size and SHA-256, plus the version, the protocol number and the game's .exe.
  • manifest.json.sig is the manifest's signature (ECDSA P-256). The launcher has your public key built into its config and refuses any manifest that wasn't signed with your private key. A hacked host or a tampered download can't push files to players.
  • Objects are the files themselves, named by their hash (objects/3f/3f59…). A file that didn't change keeps its name, so each release uploads only what's new, and players download only what's new.
  • Nothing changes in the game folder until every file has downloaded and checked out. A cancelled or failed update leaves the installed game as it was, and the next attempt resumes the partial downloads.

One-time setup#

1. Make a signing key#

In Unity: Tools ▸ Axiom ▸ Build and Release ▸ tick Publish the client for the launcher ▸ Settings ▸ Create signing key. Do this once, ever: the button greys out when the key exists.

Or from the server repo:

dotnet run --project src/Tools/Axiom.Tools.ClientPublish -c Release -- keygen --out ~/.axiom/keys/MyGame

You get two files:

File What to do with it
publish-key.private.pem Secret. Back it up (password manager, encrypted USB). Never commit it, never upload it. Anyone with it can ship files to your players.
publish-key.public.txt Goes in launcher.config.json as patchPublicKey. Safe to share.

If you lose the private key, launchers you've already shipped can't accept updates signed with a new key. Players would need a new launcher. Back it up.

The default key location in Unity is ~/.axiom/keys/<product name>/, outside the repo on purpose. The tool refuses to overwrite an existing key.

2. Point the launcher at your host#

In launcher.config.json (next to the launcher's .exe):

{
  "authServerUrl": "https://auth.example.com",
  "worldServerIp": "world.example.com",
  "patchUrl": "https://cdn.example.com/client",
  "patchPublicKey": "BHal…(from publish-key.public.txt)…",
  "installDir": "game"
}
Field Meaning
patchUrl The URL of the folder that holds manifest.json. Empty = the launcher doesn't install or update, and starts the game at gamePath as before.
patchPublicKey The text from publish-key.public.txt.
installDir Where the game is installed, relative to the launcher's folder unless absolute. Default game. AXIOM_INSTALL_DIR overrides it.

Then build the launcher (npm run tauri build) and ship the installer. The NSIS installer installs per user (%LOCALAPPDATA%), so the launcher can write the game next to itself. If you ship the MSI (installs to Program Files, which needs admin rights to write to), set installDir to an absolute, writable folder.

Each release#

From Unity#

Tools ▸ Axiom ▸ Build and Release:

  1. Press Run all checks and wait for the report (optional, recommended).
  2. Set the Version (or press Bump patch). Every release needs a new version.
  3. Tick Build the client and Publish the client for the launcher to download.
  4. Open Settings once and fill them in:
Setting Meaning
Publish folder Default Builds/Launcher. Keep it between releases: unchanged files stay and only new ones are added. Must not be inside the client build.
Signing key Your publish-key.private.pem.
Object names Default objects/{h2}/{hash}. Use {hash} for hosts without folders (GitHub Releases).
Objects URL Only if the files live somewhere other than next to manifest.json.
Upload command Runs after publishing; {out} is the publish folder. Examples below. Empty = upload the folder yourself.
  1. Press Build release. The protocol number (ProtocolVersion.Current) and the game's .exe name (product name) are filled in for you.

Publish last build publishes Builds/<version>/Client again without rebuilding (handy after fixing the upload command).

The settings are saved per machine (EditorPrefs), because the key path and the upload credentials are personal.

From the command line (CI, scripts)#

dotnet run --project src/Tools/Axiom.Tools.ClientPublish -c Release -- publish \
  --build  "C:/MyGame/Builds/1.2.0/Client" \
  --out    "C:/MyGame/Builds/Launcher" \
  --key    "C:/Users/me/.axiom/keys/MyGame/publish-key.private.pem" \
  --version 1.2.0 --protocol 46 --exe MyGame.exe \
  --then "rclone sync \"{out}\" r2:my-bucket/client"
Option Meaning
--build The client build folder (the one with the .exe).
--out The publish folder. Re-use it every release.
--key The private key.
--version Shown in the launcher; must change every release.
--protocol ProtocolVersion.Current. Recorded in the manifest.
--exe The game's .exe, relative to the build folder. The launcher starts this.
--product Optional name recorded in the manifest.
--pattern Object names: {hash}, {h2} (first two hex digits), {path} (the file's path in the game).
--objects-url Objects live elsewhere: an absolute URL, or a path relative to the manifest's folder (../store).
--exclude <glob> Leave files out (repeatable). Unity's *_DoNotShip/**, *_BackUpThisFolder_ButDontShipItWithYourGame/** and **/*.pdb are left out by default; --no-default-excludes turns that off.
--then "<cmd>" Run a command afterwards (cmd /c on Windows, sh -c elsewhere). Exit code 3 if it fails.

Check a publish folder, before or after uploading:

dotnet run --project src/Tools/Axiom.Tools.ClientPublish -c Release -- verify --folder Builds/Launcher --pubkey ~/.axiom/keys/MyGame/publish-key.public.txt

The release loop, once it's set up#

  1. Bump patch (0.1.1 → 0.1.2). Always bump: launchers decide "update or not" by comparing versions.
  2. Build release. It builds the client, adds the changed files to Builds/Launcher, writes the new signed manifest, and runs your upload command.
  3. Players' launchers show Update · size. That's it: nothing is sent to players by hand.

If the release changes the protocol, netcode or collision data, tick Publish servers too and redeploy the servers at the same time; players on the old client are told to update and reconnect after pressing Update. Client-only changes (UI, art) don't need a server restart.

The folders under Builds/#

Folder What it is Keep it?
Builds/Launcher/ The game download. Hashed copies of every file you've ever published (objects/) plus the signed manifest for the current version. Build release updates it in place every time. Yes, always. Never replace or delete it; it's what you upload. (If you lose it, the next publish starts a fresh one and uploads everything again.)
Builds/<version>/Client/ That version's normal client build, playable directly. Keep the newest one or two (testing crash reports, Publish last build); delete older ones. Nothing depends on them.
Builds/<version>/Server/ The servers published with that release (when ticked). Keep the version you're running in production.

The objects are your build's files byte for byte, only renamed to their SHA-256. Rename one back and it's the original file. The names are what make updates small (an unchanged file has the same name, so it's never uploaded or downloaded twice), let old and new versions sit side by side, and let the launcher check every download. Nothing is compressed: the first install is the full size of the build.

StreamingAssets (movement and NPC collision, the zone map, gamedata.bin, Entities scenes) ships like every other file. The client loads it at runtime, and the collision must match the World server's, which is why the client and servers go out together after a collision export.

What's in the publish folder#

Builds/Launcher/
├── manifest.json        upload LAST
├── manifest.json.sig    upload second to last
├── objects/ab/ab12…     the files, named by hash
├── upload-new.txt       what this publish added, in upload order
└── upload-all.txt       everything the current release needs, in upload order

Upload order matters on a live host: objects first, then manifest.json.sig, then manifest.json. If the manifest goes up first, a player who checks in that moment is told to download objects that aren't there yet (the launcher stops with a clear error and nothing is changed, but it's avoidable). Sync tools like rclone and aws s3 sync upload in no particular order; for a busy game, upload objects/ first, then the two manifest files:

rclone copy "{out}/objects" r2:my-bucket/client/objects && rclone copy "{out}" r2:my-bucket/client --include "manifest.json*"

Old objects are never deleted by the tool, and leaving them on the host is harmless. They also let a player who's mid-download finish.

Where to host#

Which should I pick?

  • Most games: Cloudflare R2 with a custom domain. Downloads (egress) are free, the free tier (10 GB of storage a month, 1 million writes and 10 million reads) covers an alpha, and rclone uploads only what changed. You need a Cloudflare account and a domain on Cloudflare.
  • No domain or card yet: GitHub Releases. Free, no bandwidth bill. More manual (flat names, one release you keep adding to, a 1000-file limit per release). Fine for a closed alpha.
  • You already rent a server (VPS) with a web server: use it. No extra account; watch your bandwidth allowance, since every player downloads the whole game once.
  • Already on AWS: S3 + CloudFront. Works well, but you pay for every GB players download, so it gets expensive as the player count grows.
  • Avoid: Google Drive, Dropbox, OneDrive, Mega. They don't give stable direct links to individual files, rate-limit downloads and sometimes return a web page instead of the file.

Rough sizing: total download = game size × players × releases that touch big files. A 2 GB game and 100 testers is about 200 GB for the first install alone: free on R2 or GitHub, a real bill on a pay-per-GB host. Check each provider's current pricing and limits before you commit.

The common choices in detail:

Host patchUrl Pattern Upload command (--then) Notes
Cloudflare R2 https://cdn.yourgame.com/client (a custom domain on the bucket) default rclone sync "{out}" r2:my-bucket/client Free egress, and a free tier that covers a small game. The r2.dev address is rate-limited and meant for development; use a custom domain for players.
AWS S3 (+ CloudFront) https://dxxxx.cloudfront.net/client default aws s3 sync "{out}" s3://my-bucket/client Pay for egress. CloudFront in front lowers cost and speeds up downloads.
Backblaze B2, DigitalOcean Spaces, Wasabi, any S3-compatible store the bucket's public or CDN URL default rclone sync "{out}" b2:my-bucket/client rclone speaks to all of them.
GitHub Releases https://github.com/<you>/<repo>/releases/download/client {hash} see below Free bandwidth. Files must be under 2 GiB, and a release holds at most 1000 files.
Your own server (Caddy, nginx, IIS, Apache) https://yourgame.com/client default robocopy "{out}" \\server\www\client /E or rsync -a "{out}/" me@host:/var/www/client/ Any web server that serves static files. Range requests (resume) work out of the box on all four.
Any FTP or shared web host the folder's URL default rclone sync "{out}" ftp-host:public_html/client (or upload by hand) Works as long as it serves the files unchanged.
itch.io, Steam not used They have their own patchers. Ship the game there directly.

GitHub Releases#

Use one release that you keep adding to (tag client), with flat names:

  1. Create the release once: gh release create client --title "Game files" --notes "Downloaded by the launcher".
  2. In Unity set Object names to {hash}, or pass --pattern "{hash}".
  3. Upload what's new, overwriting the manifest. In PowerShell:

powershell cd Builds/Launcher; gh release upload client --clobber (Get-Content upload-new.txt)

As an upload command (runs through cmd): powershell -NoProfile -Command "cd '{out}'; gh release upload client --clobber (Get-Content upload-new.txt)"

  1. patchUrl = https://github.com/<you>/<repo>/releases/download/client.

When the release nears 1000 files, start a new tag (client2), publish into a fresh publish folder, upload everything (upload-all.txt), and update patchUrl in the next launcher build. Keep the old release until players have updated their launcher.

Caching#

Objects never change (their name is their content), so they can be cached forever. manifest.json and manifest.json.sig must not be cached for long, or players won't see a new release until the cache expires. On a CDN, give the two manifest files Cache-Control: no-cache (or a max age of a minute), or purge them after each upload:

rclone copy "{out}" r2:my-bucket/client --include "manifest.json*" --header-upload "Cache-Control: no-cache"

Try it locally#

cd Builds/Launcher
python -m http.server 8080

Set "patchUrl": "http://127.0.0.1:8080" and start the launcher. launcher.config.json is read at start-up, so restart the launcher (or tauri dev) after editing it. With tauri dev, the default installDir (game) is next to the dev launcher's exe, in src-tauri/target/debug/game; the account menu's Open game folder shows it. (Python's server doesn't support resuming; the launcher then restarts a cancelled file from the beginning, which is fine.)

What players see#

  • Install · 1.4 GB the first time, Update · 23 MB when there's a new version, Play when the game is up to date. The game can't be started while an update is pending.
  • A progress bar with speed and time left, and Cancel. Cancelling keeps what's downloaded; the next Install or Update picks up where it stopped.
  • Verify game files in the account menu re-checks every file against the manifest and repairs anything that's wrong or missing.
  • Check for updates in the same menu. The launcher also checks every 10 minutes while open.
  • If the update host can't be reached, an installed game can still be played; the launcher says it couldn't check for updates.
  • Files that a previous version installed and the new one doesn't have are deleted. Anything else in the game folder (settings, logs, screenshots) is left alone.

The launcher keeps its record of the install in <installDir>/.axiom/install.json, and partial downloads in <installDir>/.axiom/staging/.

Troubleshooting#

Message Cause
"The update's signature doesn't match…" patchPublicKey isn't the public half of the key you published with, or manifest.json / .sig were changed or uploaded from different publishes. Re-upload both from the same publish.
"The update server answered 404 Not Found for …/manifest.json" patchUrl points at the wrong folder, or the files aren't uploaded (or aren't public). Open that URL in a browser.
"Downloading X failed: the server answered 404 …" The manifest is up but an object isn't: wrong upload order, an incomplete upload, or the wrong Object names / Objects URL. Run verify on the publish folder, then upload objects/.
"X downloaded with the wrong content…" The host serves something other than the published file (an old cached copy, an HTML error page, or a host that rewrites files). Check caching; nothing was changed on the player's PC.
"Can't write to the game folder…" The launcher was installed somewhere players can't write (Program Files via the MSI). Use the NSIS installer or an absolute installDir.
"Couldn't replace X. Is the game still running?" Close the game. The launcher refuses to update while it started the game, but a game started some other way can still hold files open.
"\"patchPublicKey\" is missing…" Add it to launcher.config.json.
Installed, but the game disconnects right after loading ("…collision versions differ. Please update your client.") Not a launcher problem: the World server runs an older collision export than the client. Re-export, restart World, and ship client and servers from the same Build release.
The game itself crashes Its log, not the launcher's: see Troubleshooting ▸ Client logs and crashes.
Players don't see a new release manifest.json is cached by your CDN. See Caching.

Releasing as a team#

Only someone with both the private key and the host's upload credentials (the R2 token, for example) can ship to players. Everyone else can build and test freely.

  • Small team: one or two release owners. Keep the key and the upload token in a shared password-manager vault only they can open. Everyone else commits to git; the release owner pulls, bumps the version and presses Build release. One owner avoids two people publishing at once (the last manifest.json uploaded wins) and colliding version numbers.
  • Later: CI (GitHub Actions or a build machine) with the key and token stored as secrets, so nobody has them on their PC. A release becomes "push a version tag". It needs a Unity license on the build machine.
  • Build and Release's launcher settings are saved per machine, so each release owner fills them in once. Each PC has its own Builds/Launcher; that's fine, because the objects are named by content and the upload skips anything already on the host.
  • If the key leaks, anyone can sign releases, and the only fix is a new key and a new launcher build for every player. Keep it in as few hands as possible.

What the signature protects, and what it doesn't#

  • Protects against: a compromised or misconfigured host, a man-in-the-middle, a corrupted download. The launcher installs nothing it can't verify.
  • Doesn't protect against: someone who has your private key, or a malicious build you published yourself. Guard the key like a password, and keep it off build servers you don't control (on CI, store it as a secret and write it to a temporary file).
  • Serve over HTTPS anyway: it keeps the download private and stops networks that inject content.
