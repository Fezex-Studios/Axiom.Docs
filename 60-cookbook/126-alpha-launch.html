Alpha Launch: Run the Servers and Let Players In#

This page takes you from "it works on my PC" to "testers in other homes are playing". Every step links to the deeper page if you need it. It's written for a Windows host, which is what most first alphas run on; for Linux, use the same steps with Deploy a Shard for services and paths.

What an alpha needs#

 Tester's PC                                     Your server machine
┌────────────────────┐                          ┌───────────────────────────────────────────┐
│ Axiom Launcher     │──https──► Caddy :443 ───►│ Auth          127.0.0.1:3000   ─► MySQL   │
│                    │                          │ World         UDP 7777 (public)            │
│ Axiom.exe ─────────┼──────── UDP 7777 ───────►│ Persistence   127.0.0.1:7778   ─► MySQL   │
└────────────────────┘                          │ Auction       127.0.0.1:5090   ─► MySQL   │
                                                └───────────────────────────────────────────┘
Piece What it is
Four servers Persistence, Auth, World and Auction on one machine, plus MySQL
Two public addresses Auth (HTTPS through Caddy) and the World server (UDP 7777)
A client build a normal (not Development) Unity build pointed at your Auth address
The launcher the Axiom Launcher (Tauri). It logs players in and starts the game with a login ticket.
Testers accounts you create for them (step 10)

1. Choose where to host#

Your own PC A rented server (VPS / game server)
Cost free about $10–80/month
Good for a small closed alpha: friends, about 5–30 people, a few evenings a longer alpha, more players, or one that must stay up 24/7
Up time only while your PC is on and the servers are running always
Your home IP players can see it; an attack takes down your home internet stays private
DDoS protection none OVH game servers include UDP protection (Production Hosting)
Upload speed your home upload limits how many can play data-centre bandwidth

Recommendation: run the first alpha weekend on your own PC with friends. If it goes well and you want strangers in, move to an OVH game server; the steps below are the same.

Rough bandwidth: each player needs about 20–60 KB/s of your upload while playing, more in crowded areas. Test your upload at speedtest.net. 10 Mbit/s up comfortably carries a small group of friends.

2. Prepare the machine#

  1. Install: - .NET 10. Your own PC has the SDK already. On a fresh server, install the ASP.NET Core Runtime 10 (Auth needs it) and the .NET Runtime 10. - MySQL 8, if it isn't on this machine yet. - Caddy (HTTPS for Auth, Mode 3).
  2. Clock: Windows time sync on. Sieges, festivals and world events run on UTC times.
  3. Power: on your own PC, turn off sleep while the alpha runs: Settings → System → Power → Screen and sleep → Never.
  4. Firewall: in PowerShell, run as Administrator:

powershell New-NetFirewallRule -DisplayName "Axiom World (UDP 7777)" -Direction Inbound -Protocol UDP -LocalPort 7777 -Action Allow New-NetFirewallRule -DisplayName "Caddy HTTP (80)" -Direction Inbound -Protocol TCP -LocalPort 80 -Action Allow New-NetFirewallRule -DisplayName "Caddy HTTPS (443)" -Direction Inbound -Protocol TCP -LocalPort 443 -Action Allow

  1. Router (own PC only): forward TCP 80, TCP 443 and UDP 7777 to your PC's LAN IP. In your router, also give your PC a fixed LAN IP ("DHCP reservation"), so the forwarding doesn't break when the PC gets a new address. - Do not forward 3000, 7778, 5090 or 3306. Those stay private. - Check your ISP doesn't use CGNAT (HTTPS guide, Step 2).
  2. Names: create two DuckDNS names, or two records on your own domain, both pointing at your public IP: - axiom-auth.duckdns.org, for Auth (through Caddy); - axiom-world.duckdns.org, for the World server.

You can also use one name for both. Two names make it easy to move one server later.

3. Databases#

If you've been developing on this machine, the databases already exist; skip to step 4. Back them up first if you want a fresh alpha, then decide whether testers start on a clean database (recommended) or your dev one.

On a new machine:

  1. Create a MySQL user for the servers (Deploy a Shard, step 2 has separate users per database; root works for a small alpha).
  2. That's it: Persistence, Auth and Auction each create their database and tables on first start. The World server builds Data/worldserver.db from its migrations and patches.

4. Build the servers#

In Unity: Tools ▸ Axiom ▸ Build and Release. Untick "Build the client" for now, tick "Publish servers" and press Build. The four servers land in Builds/<version>/.

Copy each server's folder to its place on the server machine (for example C:\Axiom\World, C:\Axiom\Auth and so on). On your own PC you can run them straight from Builds/<version>/.

Keep the World's Data/ folder: worldserver.db, collision, terrain, navmesh, zone map. The client must ship with the same collision export (step 8).

5. Alpha settings for each server#

Put these in each server's appsettings.Local.json, next to its .exe. Never edit the committed appsettings.json. Every service must have the same InternalSecret (openssl rand -base64 48, or any 48+ random characters).

Auth (C:\Axiom\Auth\appsettings.Local.json)#

{
  "ConnectionStrings": {
    "Auth": "Server=127.0.0.1;Port=3306;Database=axiom_auth;User=axiom_auth;Password=...;"
  },
  "Auth": {
    "InternalSecret": "...the shared secret...",
    "TrustForwardedFor": true
  },
  "Kestrel": { "Endpoints": { "Http": { "Url": "http://127.0.0.1:3000" } } },
  "WorldDirectory": {
    "Worlds": [
      { "Id": "alpha", "Name": "Dawnmere", "Host": "axiom-world.duckdns.org", "Port": 7777,
        "Restrictions": "Alpha", "Maintenance": false, "MaxCharacters": 6 }
    ]
  }
}
  • TrustForwardedFor + 127.0.0.1: Auth sits behind Caddy (why).
  • WorldDirectory:Worlds: what testers see on Server Select. Host is the public World address. The Id must match the World server's WorldDirectory:Id.

World (C:\Axiom\World\appsettings.Local.json)#

{
  "World": {
    "InternalSecret": "...the shared secret...",
    "AuthServerUrl": "http://127.0.0.1:3000",
    "AllowDebugCommands": false,
    "AllowLoadTestBypass": false,
    "AllowContentReload": false
  },
  "WorldDirectory": {
    "Id": "alpha",
    "PublicHost": "axiom-world.duckdns.org",
    "PublicPort": 7777
  }
}
Setting Alpha value Why
AllowDebugCommands false Turns off the developer test levers and the GM panel's Grants page (giving items, coins, levels, mail). Moderation, teleports, announcements and world events still work by access level (step 10). Turn it on only if you want to hand out test gear, and remember any staff member can then do it.
AllowLoadTestBypass false Otherwise anyone could log in as a load-test bot without a password.
AllowContentReload false (or true if the server runs on your dev PC and you want to push fixes live) Content Hot Reload
AuthServerUrl http://127.0.0.1:3000 Auth is on the same machine; this never leaves it.
PublicHost your World name or public IP sent to the world list; never 0.0.0.0 or 127.0.0.1

Also add the ClientContent key (World:ClientContent:KeyHex, matching the client) and OutputPaths including Auth's gamedata.bin, as on your dev setup. Then testers download new item names without a new client build (Deploy a Shard, step 4).

Persistence and Auction#

  • Persistence: its connection string and the shared InternalSecret, and bind it to this machine only:

json "Kestrel": { "Endpoints": { "Http": { "Url": "http://127.0.0.1:7778" } } }

Its default 0.0.0.0:7778 listens on your whole network. - Auction: its connection string and Persistence:InternalSecret.

6. HTTPS (Caddy)#

Follow HTTPS for Auth, Mode 3, steps 3, 4, 6 and 8, with your Auth name (axiom-auth.duckdns.org). You did steps 1, 2 and 5 above.

7. Start everything, in this order#

  1. MySQL (normally already running as a Windows service).
  2. Persistence: wait until it has started and shows no errors.
  3. Auth: look for Database Ready, Auth Server Ready and HTTPS: expected from a reverse proxy….
  4. World: wait until it's listening on 7777 and has sent its first heartbeat. The first screen should show migrations, patches, catalogues, [Rules], [NavMesh], [Zones], with no warnings about your rows.
  5. Auction.
  6. Caddy.

The World server calls Persistence while it starts, which is why Persistence goes first.

Stopping: press Ctrl+C in the World window and wait. It saves every character and territory (about 15 s) before closing. Never close the window with the X or kill it in Task Manager during an alpha: that skips the save. Then stop the others in reverse order.

Keep them running unattended (optional): install each one as a Windows service with NSSM (nssm install AxiomWorld C:\Axiom\World\Axiom.Server.World.exe, start-up folder C:\Axiom\World). Set the services' start order with dependencies (World depends on Persistence and Auth). NSSM's stop sends Ctrl+C, but by default it only waits 1.5 s before killing the process, which would skip the save. Raise it: nssm set AxiomWorld AppStopMethodConsole 45000.

8. Build the client#

  1. Auth address: in Resources/UI/Selection/WorldDirectory.json, set json { "AuthBaseUrl": "https://axiom-auth.duckdns.org", "RefreshSeconds": 10 } The launcher also passes its own Auth address to the game; this setting is the fallback when the game is started some other way. Use the same address as the launcher's authServerUrl.
  2. Build Settings: Development Build off. A release build refuses plain http:// to other machines, which is what you want for players.
  3. Tools ▸ Axiom ▸ Build and Release: press Run all checks and wait for the report, then tick "Build the client" and press Build release. The netcode check runs automatically before the build, which goes into Builds/<version>/Client/.
  4. Collision and zone map: the client must carry the same movement-collision export and zone map as the server's Data/. Both come from the same export; rebuild both if you changed the world.
  5. Bundled game data: StreamingAssets/GameData/gamedata.bin is the starting copy. Testers get newer ones from Auth automatically.
  6. Unity's own HTTP switch: Player Settings → Other Settings → Allow downloads over HTTP → Not allowed.

9. The launcher#

The game only logs in when a launcher starts it with a one-use login ticket. That's the Axiom Launcher, a Tauri app kept in its own repository (Axiom.Client.Launcher).

What it does: - Sign in or Create account (testers register themselves). - Remember me keeps the session, so the next start signs in by itself, and the password, so an expired session needs one click. Both are kept in Windows Credential Manager, encrypted for that Windows user. - Shows each world's status and player count. - Every Play swaps the session for a fresh one-use ticket, and starts the game with -token <ticket> -ip <world> -auth-url <Auth>. Play turns back on when the game closes. - Sign out revokes the session on the server; Sign out and forget me also removes the saved password. - Shows the Auth server's own messages (an HTTPS refusal, a ban reason) instead of bare status codes. - Optional: installs and updates the game itself from any static host, so testers download only the launcher and every new build reaches them automatically (Client publish).

1. Build it (once per change), on your dev PC with Node.js and Rust installed:

cd Axiom.Client.Launcher
npm install
npm run tauri build

The launcher .exe is in src-tauri/target/release/; installers are under src-tauri/target/release/bundle/.

2. Set launcher.config.json. It sits next to the launcher .exe. Every field is optional; missing fields use the defaults.

{
  "authServerUrl": "https://axiom-auth.duckdns.org",
  "worldServerIp": "axiom-world.duckdns.org",
  "gamePath": "game/Axiom.Client.exe",
  "discordUrl": "https://discord.gg/…",
  "websiteUrl": ""
}
Field Meaning
authServerUrl your Auth address. Use https:// for players outside your home. The game is started with the same address.
worldServerIp the World server's public IP or name. Without it the game connects to 127.0.0.1, which only works on the host PC.
gamePath the game .exe, relative to the launcher's folder (default game/Axiom.Client.exe)
discordUrl, websiteUrl optional buttons on both screens; empty hides them

3. Folder layout to ship:

Axiom/
├── Axiom Launcher.exe        (the launcher; the name comes from the launcher's build)
├── launcher.config.json
└── game/
    ├── Axiom.Client.exe      (your client build: the whole build folder)
    └── …

Or let the launcher download the game. Instead of shipping game/ yourself, publish each build with Tools ▸ Axiom ▸ Build and Release ▸ Publish the client for the launcher, upload the publish folder to any static host (Cloudflare R2, S3, GitHub Releases, your own web server), and add these to launcher.config.json:

  "patchUrl": "https://cdn.yourgame.com/client",
  "patchPublicKey": "…from publish-key.public.txt…"

Testers then get just the launcher; it shows Install, then Update whenever you publish a new version. Setup, hosting choices and upload commands: Client publish & launcher updates.

The launcher passes its authServerUrl to the game (-auth-url), so the game always uses the same Auth server. AuthBaseUrl in the build (step 8) is the fallback when the game is started some other way.

The ticket works for about two minutes, once. If a tester leaves the game sitting on Server Select longer than that before connecting, they close the game and press Play again.

10. Accounts and staff#

  • Creating accounts. Testers use Create account in the launcher. Usernames are 3–20 letters, numbers or _; passwords are 8+ characters. There's no "change password" yet. To make an account yourself, from PowerShell on any PC:

powershell Invoke-RestMethod -Method Post -Uri https://axiom-auth.duckdns.org/register ` -ContentType application/json -Body '{"Username":"tester1","Password":"pick-a-password"}'

  • Registration is open: anyone who has your launcher (or your Auth address) can create an account. For a closed alpha, only share the download with your testers.
  • Make yourself staff: create your own account the same way, then in MySQL:

sql UPDATE axiom_auth.accounts SET access_level = 5 WHERE username = 'yourname';

Log in again. The GM panel (F12) opens for levels 3–5 (Staff & GM tools). - Works with AllowDebugCommands off: players, target actions (go to, summon, unstuck, revive), moderation (kick, mute, freeze, ban), account look-up, announcements and world events. - Needs it on: Grants (items, coins, set level, mail). - Give trusted helpers level 3 or 4. Moderation never works on staff at or above your own level. - Problem testers: the GM panel's Moderation page can kick, mute, freeze and ban. A ban ends the account's session everywhere and its saved launcher login, and they see the reason when they try to log in.

11. Test it yourself from outside first#

Before you send anything to testers:

  1. On your phone, on mobile data (not your Wi-Fi), open https://axiom-auth.duckdns.org/worlds. You should see your world with a padlock.
  2. On a second PC on a different network (a laptop on your phone's hotspot is perfect), unzip the launcher folder, start Axiom Launcher, log in with a test account, and press Play. - Check that the world shows Online and you can create a character and move. - Check that a second account sees the first: log in on two PCs.
  3. Watch the server windows while you do it, for errors or warnings.

Testing from the server PC itself through the public names often fails ("NAT hairpin"). To play on the host PC, play from the Unity Editor against 127.0.0.1 as usual.

12. Give it to testers#

  1. Zip the launcher folder from step 9: the launcher, launcher.config.json and game/. (With patchUrl set, send the launcher installer instead; it downloads the game.)
  2. Upload it somewhere testers can download: Google Drive, OneDrive, Dropbox, itch.io (restricted page) or Discord for small builds.
  3. Send them these instructions:
  1. Download and unzip the whole folder (don't run it from inside the zip).
  2. Start Axiom Launcher.
  3. Windows may say "Windows protected your PC". The game isn't signed yet: click More info → Run anyway.
  4. Log in with the username and password you were sent. Tick Remember me to skip it next time.
  5. Pick the world and play. Report bugs in #alpha-bugs (or wherever you collect them).
  1. Tell them when the servers are up: for example "Saturday 18:00–23:00 UTC". Use UTC or name your time zone; testers live in different ones.

13. During the alpha#

Task How
Watch for problems keep the server windows visible; Auth and World log warnings with the reason
Staff GM panel (F12) at access level 3–5
Content fix (items, quests, loot…) edit, then restart World (patches apply at boot). Or push live if AllowContentReload is on and the server runs on your dev PC. Testers get new gamedata.bin on their next start.
Code fix, same protocol rebuild the servers, stop with Ctrl+C, replace, start again in order
Fix that changes packets (protocol bump) set the world to "Maintenance": true in Auth's WorldDirectory, stop World, deploy the servers and a new client together, and send testers the new zip. Old clients are refused with a version message.
Backups every night of the alpha: mysqldump --single-transaction of axiom_auth, axiom_persistence and axiom_auction, plus the World's Data/worldserver.db and Data/lua_data.json (copy them while World is stopped)
Taking it down announce in chat, Ctrl+C the World server, wait for the save

Before a bigger alpha, run a load test against the real machine with the number of players you expect, and practise restoring last night's backup once.

14. Troubleshooting#

What the tester sees Cause and fix
Launcher: "Can't reach the login server" Caddy or Auth isn't running, port 443 isn't forwarded, or DuckDNS points at an old IP. Test https://…/worlds from your phone.
Launcher: "Unexpected response from the login server (403)" Auth refused plain HTTP: authServerUrl in launcher.config.json is http://. Use the https:// address.
Launcher: "Invalid username or password" as it says. Five failures lock that name for that PC for 15 minutes.
Launcher: "Too many attempts" rate limit (5 a minute). Wait a minute. If everyone gets it, Auth doesn't see real player IPs: TrustForwardedFor is missing.
Game: Server Select says the world list is unavailable the client's AuthBaseUrl or -auth-url is wrong, or Auth is down
Game: the world shows Offline the World server isn't running, its InternalSecret differs from Auth's, or its WorldDirectory:Id doesn't match Auth's world entry
Game: "Start the game from the launcher to log in" the game was started directly from its .exe. Use the launcher.
Game: "Your session has ended…" / "You need to log in again" the ticket expired (more than two minutes) or was already used. Close the game and press Play again.
Game: connecting… then times out UDP 7777 isn't reaching the server (router forwarding, Windows Firewall), or PublicHost / $WorldIp is wrong
Game: refused with a version message the tester has an old client after a protocol change. With launcher updates they press Update; otherwise send the new zip.
Game: "Client and server world collision versions differ. Please update your client." the World server's collision export isn't the one the client was built with. Re-export Movement Collision, make sure the server's Data/world_collision got it, restart World. Ship the client and the servers from the same Build release.
Game: stuck or rubber-banding, falling through the world the client's collision export doesn't match the server's Data/. Rebuild both from the same export.
Item names show as #1234 the client's gamedata.bin is older than the server's content; it updates from Auth on the next start. Check World's ClientContent:OutputPaths reaches Auth's GameDataPath.
Windows: "Windows protected your PC" the build isn't code-signed. More info → Run anyway. Code signing is a later step.

Alpha-day checklist#

  • [ ] Backups taken; the World database is the one you mean to use (fresh or dev)
  • [ ] All four appsettings.Local.json have the same InternalSecret
  • [ ] World: AllowDebugCommands, AllowLoadTestBypass (and normally AllowContentReload) off; PublicHost = public name
  • [ ] Auth: TrustForwardedFor on, 127.0.0.1:3000; the world entry's Host = public World name and Id matches
  • [ ] Persistence bound to 127.0.0.1:7778
  • [ ] Router: TCP 80/443 and UDP 7777 forwarded; nothing else
  • [ ] Caddy running; https://…/worlds works from a phone on mobile data
  • [ ] Client: release build, AuthBaseUrl = https address, the same collision export as the server
  • [ ] Launcher: launcher.config.json has the https Auth address, the World address and the right gamePath; AuthBaseUrl in the build matches
  • [ ] Tester accounts created; tested from a second PC on another network: log in, character created, two players see each other
  • [ ] Your account is level 5; the GM panel opens
  • [ ] Testers have the zip, the instructions and the play times (with a time zone)
