Feature note, kept next to the code it describes. Source: docs/notes/server/CLASS_BASED.md

Axiom: Warrior, Healer and Mage#

This source refactor replaces combinable skillsets with one permanent class chosen during character creation: Warrior (1), Healer (2), or Mage (3). It changes the Unity client, shared network contracts, World server, Persistence server, content editor, stat calculations, ability progression, and equipment rules together.

This is updated source, with database/content checks completed. The .NET and Unity builds still need to run on your machine. This workspace cannot initialize CoreCLR because /proc is unavailable, and has no Unity editor or live MySQL server. Run the included build and verification runner before deploying. No old compiled DLL is included as a purported new build.

Package contents#

  • src/: complete server source from the supplied archive, updated for classes. Build caches, old nested backup ZIPs, local secret configuration, and compiled outputs are excluded.
  • Assets/: an overlay of changed/new Unity assets and their existing .meta files. Apply this to your existing Unity project; the unchanged models, scenes, plugins and third-party assets stay in that project.
  • README.md: installation, migration, gameplay rules, and testing instructions.
  • VALIDATION.md: checks completed here and checks requiring your environment.
  • CHANGED_FILES.json: changed/new source paths with before/after SHA-256 values.

The supplied source databases and original input archives were left unchanged. The server applies its own pending migrations and SQL patches to the database you configure when you run it. The verification tools use disposable copies.

Install and build#

  1. Stop your existing servers and close Unity. Back up your source/project, the live MySQL persistence database, and the live world SQLite database, including any active WAL/SHM files through a proper database backup. First rehearse this upgrade on copies.
  2. Merge src/ into your existing server source directory. Keep your own appsettings.Local.json files, connection strings, service secrets and deployment configuration. Do not replace a live world database with the sample src/Axiom.Server.World/Data/worldserver.db in this package; configure the upgraded server to use your backed-up live database.
  3. Install/use the .NET 10 SDK, matching the projects' existing target frameworks, and restore their NuGet packages. The shared Network and Movement assemblies still target netstandard2.1 for Unity.
  4. Build all projects and run the class harness. From the updated server source directory, run the Windows command below, passing the existing Unity Assets directory. The script rebuilds all servers, executes the checks against a temporary world DB, and copies the freshly built shared DLLs into Assets/AxiomMMOKit/Plugins only after the checks succeed.
.\Tools\Build-ClassBased.ps1 -UnityAssetsPath 'C:\YourUnityProject\Assets'

On Linux/macOS with the .NET SDK:

bash Tools/build-class-based.sh /absolute/path/to/YourUnityProject/Assets

Omit the Unity path if you want to build/check first and copy Axiom.Network.dll and Axiom.Movement.dll manually from their bin/Release/netstandard2.1/ directories to your existing Assets/AxiomMMOKit/Plugins/ directory. Preserve the DLL .meta files. Keep your existing MessagePack/LiteNetLib plugin dependencies.

  1. Merge the package's Assets/ contents into the existing project's Assets/, preserving the supplied .meta files. Reopen Unity and let it recompile. No new scene component is required: the existing character creation panel and spellbook implementations were updated in place.
  2. Apply the persistence migration explicitly, using EF Core CLI 9.x, which matches the project's EF packages. Your project's local configuration/environment must point to the intended test database for the rehearsal and the intended live database for deployment.
dotnet ef database update --project Axiom.Server.Persistence --startup-project Axiom.Server.Persistence

If you do not have the EF CLI, install dotnet-ef version 9.0.0 or use a compatible 9.x installation. The persistence process now refuses to serve the old class-less schema until 20261010180000_ClassBasedCharacters is applied.

  1. Start the rebuilt Persistence/Auth/Auction services and then World using your existing deployment setup. World first runs EF migrations, then SQL patches, then loads its catalogs. Its new 20261010180000_ClassBasedContent EF migration is a model snapshot marker; patch 056 owns the world class schema and content. Keep pending patches 054 and 055 in their original order. Patch 054 requires its matching earlier EF migration, so do not run these SQL files out of sequence by hand.
  2. Build the Unity client with the newly rebuilt shared DLL. Deploy client and services together: the shared protocol is now 24, connection key Axiom/24. An old client cannot connect to the upgraded World server. Remove stale packaged server binaries from your deployment process so they cannot overwrite the rebuilt assemblies.

Existing character migration#

The MySQL migration adds characters.class_id, defaulting to Warrior, and enforces IDs 1–3. It preserves the old school selections by renaming character_skillsets to legacy_character_skillsets for audit/backup purposes. New runtime code never reads or writes that legacy table.

Existing selection Migrated class
Vitalism only Healer
Battlerage, Defense, or both Warrior
Hybrid containing melee/tank plus Vitalism Warrior
No selected skillset Warrior
Existing characters automatically becoming Mage None; Mage is a new character choice

The first World login removes foreign, removed, over-level, and over-budget learned ranks and invalid ability hotbar entries. Skill points are derived from level and valid purchased ranks, so removed ranks/old selection costs return to the available budget. Item hotbar bindings remain. Free starter skills are added to empty hotbar slots. When an old save is over budget, valid owned skills are retained in ascending skill ID order until the budget is exhausted; excess ranks are refunded.

Old owned equipment is preserved. Class-incompatible or over-level worn gear moves to free inventory slots. If the bag is full, it stays saved in its worn slot but contributes no stats and cannot satisfy a skill's weapon requirement; free bag space and log in again or unequip it to move it. Main/off-hand conflicts are also reconciled. Trade packs keep their existing separate backpack behavior.

Existing characters do not receive duplicate starter kits. New characters receive their bound class kit in the same persistence transaction that creates the character. Class is immutable through gameplay; ability reset does not change it. If you want different assignments for individual old hybrid characters, make that explicit in a separately reviewed data migration while those characters are offline; do not expose a class-change packet or change IDs casually.

Rollback requires the coordinated old source/binaries and both database backups. World patch 056 has no safe gameplay rollback: resetting learned skills and newly created Mage characters cannot be reversed by merely dropping a column. The new World EF migration refuses Down with this instruction.

Classes, stats and resources#

Warrior combines the existing melee and tank abilities. Healer keeps healing/support and gains a free offensive Holy Bolt for solo play. Mage gains ranged damage, elemental control, a defensive ward, and its own progression/passives. Each class has distinct level growth, a starter kit, and weapon/armor proficiencies.

All three currently use the project's existing mana resource. This change does not add rage, energy, block chance, dual wield damage, or a second resource system. Class armor and weapon types control eligibility; actual attack power/armor/spell/healing bonuses still come from the item's stats, rather than a hidden bonus merely for having a type.

The five primary stats use class base + growth × (level - 1) before gear, learned passives and status modifiers. Primary order below is Strength / Agility / Vitality / Intelligence / Spirit.

Class ID Class Level-one bases Gain each level
1 Warrior 16 / 10 / 16 / 6 / 6 3 / 1.5 / 3 / 0.8 / 1
2 Healer 6 / 8 / 10 / 12 / 18 0.8 / 1 / 2 / 2 / 3
3 Mage 5 / 8 / 9 / 18 / 12 0.5 / 1 / 1.5 / 3.5 / 2

StatBase/StatPerLevel remain as a fallback for callers without a class template; normal player sessions use class-specific growth. CombatRules continues to own the derived coefficients and can be tuned without changing class IDs.

All original stat IDs 0–24 stay stable. Healing Power is appended at 25, and Count becomes 26. The client character window and gear tooltips show it. NPC template stat construction stays separate from player class growth. Existing fixed-value item/NPC heals with coefficient zero retain fixed-value healing.

Modifier order remains deterministic: primary flats/percentages first; derive combat stats; then apply derived flats/percentages. Percentage modifiers for a stat add together, and passive modifiers are multiplied by learned rank. Learning/resetting a passive recalculates immediately; changing a max-health or max-mana bonus preserves current percentage rather than refilling it. Spawn/level-up retain the existing fill behavior.

These are coherent starting values, not a claim of finished PvP/raid balance. The supplied progression cap remains 30; the starter active kits and passives focus on the current early-game content, with further ranks at their existing level intervals.

Learning and passive rules#

Class choice is free. Each class's starter abilities provide rank 1 without spending points; buying higher starter ranks costs points normally. The supplied point budget is 3 at level 1, +1 per later level. Purchased ranks/passives share that budget.

Each row uses RequiredLevel + (rank - 1) × RankLevelStep. Active damage/healing ranks keep existing RankBonusPct scaling. Passives use their separate modifier rows once per learned rank, not the active damage-rank multiplier. Passive skills cannot be cast or assigned to the hotbar, and cannot be learned from another class.

Reset refunds purchased active/passive ranks and retains the class, free starter ranks and item hotbar bindings. It costs the existing AbilityResetGoldPerLevel × level in copper (default 10 copper/level), and is refused while dead, casting, or in combat. The historical field name contains “Gold”; the amount uses your existing copper-based currency system.

Weapons, armor and starter kits#

Class Weapons Armor New-character equipment
Warrior Sword, Axe, Spear, Mace, Shield Cloth, Leather, Plate 6001 sword; 6002 shield; 6003 plate chest
Healer Mace, Staff, Wand, Shield Cloth, Leather 6010 mace; 6011 support shield; 6012 cloth robe
Mage Staff, Wand Cloth 6020 two-handed staff; 6021 cloth robe

The general merchant (Shop 1) gains the class starter-tier gear, level-five upgrades, and a shared level-three Traveler Wand 6040 / two-handed Pilgrim Staff 6041 usable by Healer and Mage. The old ring 26 also gains +6 Healing Power. Existing swords, spear, nodachi, leather armor and buckler now declare explicit class/type metadata.

Axes are a supported Warrior proficiency but the supplied content does not contain an authored axe item. Armor and weapon prefab mappings are a separate art task: this package reuses your supplied icons/animation framework and does not fabricate robe, staff, mace or plate meshes. Add those item IDs to your actual GearVisualCatalog and prefabs to display new equipment meshes. The supplied Assets snapshot does not include that catalog asset. Gameplay stats and tooltips work from the server catalog even before new item IDs are exported into gamedata.bin.

AllowedClasses is a bitmask, not the class ID:

Class Class ID Equipment mask bit
Warrior 1 1
Healer 2 2
Mage 3 4
Warrior + Healer — 3
Healer + Mage — 6
All explicitly allowed — 7

Mask 0 means no additional class lock; it still enforces weapon/armor proficiency. WeaponKind: None 0, Sword 1, Axe 2, Spear 3, Mace 4, Staff 5, Wand 6, Shield 7. ArmorKind: None 0, Cloth 1, Leather 2, Plate 3. Accessories use None/None, while armor and hand slots must declare real types. An unknown type/mask is rejected at catalog startup.

Two-handed gear uses Main Hand and displaces Off Hand into the bag. Equipping an off-hand item while a two-handed main-hand is equipped displaces that main-hand. Every displacement is planned on copies before committing: a full bag refuses the swap without losing either item. Existing binding is preserved. Gear changes and skill learning/reset are blocked during a cast.

Authoring future class content#

Use the updated Unity Content Studio against a database that has completed the upgrade. Its Combat section now exposes Classes, class ownership/flags/weapon requirements on Skills, and AbilityPassiveModifiers. ItemStats exposes class masks, armor/weapon kinds, two-handed status and Healing Power. Validation checks the same key restrictions used by the server.

  • Add an active skill as a Skills row with ClassId 1, 2 or 3 plus Effects rows owned by the skill (OwnerType 2). Keep NPC/internal interaction skills at ClassId 0 with their existing flags. ClassId=0 with neither flag is a common automatic basic skill, so do not use it for a class-exclusive ability.
  • Add a passive as a class-owned Skills row with IsPassive=1, IsStarter=0, TargetRule=Self, no cast/mana/cooldown/GCD/hotbar/weapon requirement, and one or more AbilityPassiveModifiers rows. Stat uses the shared StatId; Flat and Percent multiply by learned rank. Damage/healing/threat percentage stats generally use Flat to add percentage points to that multiplier.
  • Set IsStarter=1 only for active level-one skills. Set RequiredWeapon=Shield (7) where a shield is required. A weapon restriction must agree with the class proficiency.
  • Add gear using Items + ItemStats. Set a correct EquipSlot, AllowedClasses mask and WeaponKind/ArmorKind; TwoHanded is only allowed on Main Hand. Validate new starter IDs at level 1 and the correct hand/chest slot.
  • Publish later SQL changes as 057 or later, with their own filename/version tracking. Never edit or rerun 056 after it is recorded in a deployed database. Keep EF snapshots/models synchronized when changing columns.
  • Adding a fourth class requires coordinated changes to the shared enum/mask/proficiencies, catalog validation, MySQL class constraint, Unity choices and content, with a new protocol version where the wire changes. A fourth database row alone is deliberately rejected.

Verify on your machine#

The PowerShell/bash runner builds all six existing projects and the new Axiom.ClassVerification console project. The harness runs the actual world EF migrations and patch runner on a temporary database; runs the patch runner twice; loads real catalogs and checks creation serialization, starter kits, ownership, points, healing scaling, passive application/reset, health preservation, saved-rank cleanup, hotbar restrictions, proficiency, shield requirements, atomic full-bag two-hand swaps and saved equipment reconciliation; checks SQLite integrity/FKs; and checks the persistence EF snapshot and MySQL migration SQL without opening MySQL.

A standard-library Python content check is also included and was run here:

python Tools/verify_class_content.py

It validates SQL/content and the actual legacy CASE expression on copies. It explicitly reproduces the prerequisite world EF schema changes; it does not execute EF, compile C#, launch Unity, or test live MySQL.

Before deployment, rehearse the MySQL migration on a copy of your real persistence DB and confirm the eight legacy selection combinations map as documented. Then use Unity to complete this smoke test:

  1. Create one Warrior, Healer and Mage. Confirm class in roster/character window, bound kit, correct starter hotbar, and distinct primary/derived stats.
  2. Learn active and passive ranks, level up, relog, and reset. Confirm points, immediately updated bonuses, persistent ranks, and unchanged class. Passive cards cannot drag to/cast from the hotbar.
  3. Attack/heal with each kit. Confirm Mage spells, Healer Holy Bolt and Healing Power-based heals, and Warrior shield skills requiring a shield. Check target types, cast bars, cooldowns, mana use and CC.
  4. Try foreign-class learning/casting and wrong armor/weapons. Check rejection by the server, including modified packets.
  5. Test two-handed swaps with zero and one additional free bag slot; verify both displaced items and binding survive. Test invalid legacy worn equipment with a full bag.
  6. Return to character selection and create another character; ensure class/faction options repopulate. Verify old characters' mapping and relog/save cleanup.
  7. Reconnect with a protocol-23 build and verify it is rejected; rebuild every shipped service/client with the same protocol-24 Network DLL.
